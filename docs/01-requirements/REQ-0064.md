## 内容

製造データ生成の失敗を、**原因の性質で 2 つに分ける。**

- **VM に届かない**（接続不能・タイムアウト・VM の停止中）→ `pending` に戻して後で再試行する
- **入力が悪い**（必須レイヤー不足・未対応の商品種別／サイズ）→ いまどおり `failed` で終える

## 背景・理由

### いまは 1 つのハンドラが両方を終端にしている

`generate()` は例外を種類で区別せず、**すべてを `failed` として確定させる**
（`api/app/services/manufacturing_data_service.py`）。

```python
except Exception as exc:  # noqa: BLE001 - 失敗は必ず行に記録して終える
    await self._finish(md, lease_token, status=MfgDataStatus.FAILED.value, ...)
```

ところが 2 つの原因は、**正しい対応が正反対である。**

| 原因 | 再試行すると | いまの扱い |
|---|---|---|
| VM に届かない | **次には成功する**（VM が戻れば） | `failed`。ワーカーは拾い直さない |
| 入力が悪い | **何度やっても成功しない** | `failed`。**これは正しい** |

`claim_next_generation` は `pending` しか取らず、`reclaim_expired_leases()` が戻すのは
リースの切れた `generating` だけなので、**`failed` になった行はワーカーの視界から消える。**

戻す道はあるが、どちらも人の操作が要る。

- `POST /manufacturing-data/{id}/retry`（**1 件ずつ。一括は無い**）
- 同じキャッシュキーでの再受注（`_resolve_or_create()` が `pending` に戻す）

### 実際に何が起きるか

VM が数分止まるだけで、**1 回の起動あたり最大 20 件**（`worker_max_items`）が
`failed` に落ちる。**画面にエラーは出ない。** 気づく手段が無く（REQ-0063）、
戻すには管理者が落ちた行を探して 1 件ずつ叩くことになる。

**一瞬の瞬断では落ちない。** `IllustratorVmClient` が接続エラーと 503 を
3 回まで再試行する（1 秒・2 秒のバックオフ）。効いてくるのは、**サーバーの再起動や
VM の停止のように数分単位で止まるとき**である。

### この欠陥を、いまは運用で埋めている

`infra/README.md`「VM の中のアプリを更新する」は、**アプリを更新する前に
Cloud Scheduler を止め、走っている実行が空になるまで待つ**ことを求めている。
**これはこの欠陥への対処である。** 分けられれば、その手順は必須ではなくなり、
「止めたほうが速い」という程度の保険に格下げできる。

**手順を無くすことが目的ではない。** 手順は忘れられるが、仕組みは忘れない。

### なぜ不具合ではなく要件か

**違反していると引用できる受入基準が無い。** REQ-0052 が約束したのは
「前プロセスで中断された `generating` の製造データが、ワーカーの起動時に再駆動される」
であり、これはリース失効の話で、**到達不能時の再試行ではない。**
`nfr.md` の可用性節も同じ範囲しか書いていない。
`AGENTS.md`「不具合か、仕様変更か」の判定に従い、**新しい約束＝要件**として扱う。

## 詳細

### 業務フロー

1. 生成に失敗したとき、原因が到達性か入力かを判定する
2. 到達性なら `pending` に戻し、試行回数を数える
3. 一定回数を超えたら `failed` にする（**無限に再試行しない**）
4. 入力の誤りは、いまどおり即座に `failed` にする

### 例外・エッジケース

- **VM が長時間落ちていると、再試行が空回りし続ける。** 上限と間隔をどう決めるかは
  この要件の中で決める。REQ-0063（死活監視）と組み合わせるのが自然である
- **`attempts` 列は既にある。** どう数えるか（到達性の失敗も 1 回と数えるか）を決める
- 到達性の判定は `IllustratorVmError` の中身に依存する。
  **いまの実装は接続エラーもバリデーションエラーも同じ例外型に畳んでいる**ので、
  例外を分けるところから要る可能性がある
- リースとの関係に注意する。`pending` に戻す操作は、
  **リースを保持している間だけ**書き戻す条件付き UPDATE を通すこと（ADR-0029）

## スコープ外

- 死活監視と通知（REQ-0063）
- 生成そのものの機能変更（REQ-0020）
- 一括リトライの管理画面（必要なら別途）

## 実装メモ

**運用手順を先に消さないこと。** この要件が入るまで、
`infra/README.md` の「先にワーカーを止める」は有効である。
