## 内容

本番用のコンテナイメージは、**起動のたびに依存パッケージを取り直している。**
アプリが動き出すまでに約 15 秒かかり、そのうち約 9 秒がこの取り直しである。

イメージの中で依存の導入は済んでいるのに、起動コマンドが再度それを行う。
しかも開発用のツール（`mypy` / `ruff`）まで入れ直している。

## 背景・理由

ステージングを GCP に構築した際（REQ-0053）に実測して判明した。

```
00:36:46  インスタンス起動
00:36:47  Building pod-admin-api @ file:///app
00:36:47  Downloading mypy (13.0MiB) / ruff (13.6MiB) / pygments (1.2MiB)
00:36:50  Installed 17 packages
00:36:56  Bytecode compiled 3768 files in 6.08s
00:37:01  Uvicorn running          ← 起動から 15 秒
```

原因は `api/Dockerfile` の起動コマンドが `uv run ...` である点にある。
`uv run` は実行前に環境を同期し直す。イメージのビルド時は `uv sync --no-dev` で
開発用を除いているが、起動時の `uv run` は既定で開発用も含めるため、
**イメージから消したはずのものが起動のたびに戻ってくる。**

これは Railway 時代から続く性質であり、今回の移行が持ち込んだものではない。
ただし、コンテナ実行基盤ではインスタンスが頻繁に作り直されるため、影響が大きくなる。

## 詳細

放置した場合の影響は 3 つある。

1. **コールドスタートが 15 秒を超える。**
   移行設計書 9.4 は「外部販売サイト側のタイムアウトが 10 秒未満なら
   `min-instances=1`（約 ¥6,000/月）にする」としている。
   **アプリが動き出す前にその 10 秒を使い切っている。**
   これを直せば、費用をかけずに済む可能性がある
2. **起動が PyPI に依存する。** 取得に失敗するとコンテナが起動しない。
   外部サービスの障害が、こちらの起動失敗として現れる
3. 本番の実行環境に開発用ツールが入る

想定される直し方（実装時に確認する）:

- 起動コマンドを仮想環境の実行ファイル直呼び（`/app/.venv/bin/uvicorn` など）に変える
- または `uv run --no-sync` を使う
- 併せて `UV_COMPILE_BYTECODE` の効き方を確認する（起動時に 3768 ファイルを
  コンパイルしているため、ビルド時のコンパイルが使われていない可能性がある）

**`api/Dockerfile` だけを直しても終わらない。** Cloud Run Job の起動コマンドが
Terraform 側にも書かれており（`infra/envs/staging/main.tf` の migrate / worker）、
そちらは `uv run ...` のままなので、**Job だけが古い経路で動き続けて何も壊れない。**
イメージ側に入口（`api` / `migrate` / `worker` を振り分ける仕組み）を持たせ、
Terraform からは役割名だけを渡す形にすると、この重複自体が無くなる。
