## 内容

Railway と Vercel を止める前に、**GCP 側で製造データが実際に作れること**を確かめておきたい。

ステージングと本番のそれぞれで受注を 1 件通し、製造データ生成 VM（illustrator-vm）が呼ばれて
成果物が生成され、管理画面からダウンロードできるところまでを確認する。

## 背景・理由

REQ-0053（ステージング構築）と REQ-0054 の PR 1（本番構築）で、GCP 上の API・フロント・DB・
マイグレーション・ファイル保管までは疎通を確認した。しかし **製造データ生成だけは、どちらの
環境でも一度も動かしていない。**

- ステージングは `ILLUSTRATOR_VM_BASE_URL` を空にして、生成機能ごと無効にしてある（REQ-0053 の例外）
- 本番は URL を設定済みだが、ワーカーの定期起動を止めてある（REQ-0054 のカットオーバー手順 11 で有効化する）

製造データ生成は POD の業務の根幹であり、**ここが動かないと発注に進めない。**
生成が `ready` にならない限り、注文明細は「発注準備中」で止まる。

### 確認の順序が逆になっている

REQ-0054 のカットオーバー手順では、**切り戻しの判断は手順 7〜8 の間**で行う。ところが
製造データ生成の確認は **手順 11** に置かれている。このままだと、
**戻れなくなった後に初めて生成を試すことになる。**

さらに、生成の実行方式はカットオーバーで変わる。移行元の Railway は **REQ-0052 より前の
コード世代**で動いており、受注のレスポンス送出後に `BackgroundTasks` で生成している。
移行先ではこれが **定期起動のワーカー** に変わる。
**一度も動かしたことのない方式へ、戻れない状態で切り替わる。**

移行元の世代は次の 2 点から分かる。

- PR #117 のデータ移送リハーサルで、ダンプのスキーマに `manufacturing_data.lease_expires_at`
  が無かった。この列は REQ-0052（ADR-0029）が追加したものである
- REQ-0052 より前の本番起動コマンドは `alembic upgrade head && uvicorn ...` だったため、
  REQ-0052 以降のイメージがデプロイされていれば、起動時にこの列が作られていたはずである

Railway を止めてしまうと戻れないので、止める前に確認する。

## 詳細

### 業務フロー

環境ごとに次を行う。**ステージングで通してから本番に進む。**

1. 実受注で使われている元画像（PNG レイヤー）の URL を使い、v2 受注 API にテスト注文を 1 件登録する
2. 製造データ行が `pending` で作られることを確認する
3. ワーカーの Job を **手動で 1 回だけ** 実行する（ADR-0034）
4. 行が `ready` になり、成果物が当該環境の Cloud Storage に保存されることを確認する
5. 管理画面から成果物をダウンロードできることを確認する
6. テストデータを片付ける

### 例外・エッジケース

- **Cloud Scheduler は停止したままにする。** 手動実行なら VM に投入されるのは自分が作った
  テスト注文の分だけで、illustrator-vm の待ち行列を継続的に埋めない（ADR-0034）
- **illustrator-vm は 1 件ずつの直列処理**（最大約 300 秒）である。移行元の Railway では
  製造データ生成が現に動いているため、テストジョブはその生成を待たせる。**業務時間外に実施する**
- 元画像は **公開 https の URL** である必要がある。`SOURCE_IMAGE_ALLOWED_HOSTS` が空のため、
  https 必須・パブリック IP のみ許可・リダイレクト追従なしの検証が効く
- **本番の DB は空である。** テスト注文の前に、管理者ユーザーと受注元（`order_sources`）を
  1 件ずつ入れる必要がある。**`api/scripts/seed_operation_test.py` は `order_sources` を含む
  テーブルを一掃するので使わない**
- 本番 DB のテストデータはカットオーバー時の `DROP SCHEMA` で消えるが、
  **Cloud Storage の成果物は消えない。** 手で削除する

## 受入基準

- [ ] ステージングで v2 受注を 1 件登録し、製造データが `ready` になり、管理画面から成果物を
      ダウンロードできる
- [ ] 本番で v2 受注を 1 件登録し、製造データが `ready` になり、管理画面から成果物を
      ダウンロードできる
- [ ] 成果物が各環境の Cloud Storage バケットに保存されている
      （ステージングの成果物が本番バケットに入っていない）
- [ ] 確認の前後で、ステージング・本番とも `terraform plan` に差分が出ない
      （確認のためにインフラ定義を変更していない）
- [ ] ワーカーの Cloud Scheduler が、確認の前後を通じて停止したままである
- [ ] 確認に使ったテストデータ（受注・製造データ・Cloud Storage 上の成果物）が両環境から
      削除されている
- [ ] 確認手順が文書として残っており、カットオーバー当日に同じ手順を再実行できる

## スコープ外

- illustrator-vm の移送・閉域化（REQ-0055）
- 本番カットオーバーそのもの（REQ-0054）
- ワーカーの定期起動の有効化（REQ-0054 のカットオーバー手順 11）
- ステージングから製造データ生成を**恒常的に**使えるようにすること。
  本要件は確認が目的であり、繋いだ状態を維持するかは移送後に判断する（REQ-0055 のスコープ外）
