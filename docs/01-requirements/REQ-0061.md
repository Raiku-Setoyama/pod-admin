## 内容

Railway と Vercel を止める前に、**GCP 側で製造データが実際に作れること**を確かめておきたい。

ステージングと本番のそれぞれで受注を 1 件通し、製造データ生成 VM（illustrator-vm）が呼ばれて
成果物が生成され、管理画面から取り出せるところまでを確認する。

## 背景・理由

REQ-0053（ステージング構築）と REQ-0054 の PR 1（本番構築）で、GCP 上の API・フロント・DB・
マイグレーション・ファイル保管までは疎通を確認した。しかし **製造データ生成だけは、どちらの
環境でも一度も動かしていない。**

- ステージングは `ILLUSTRATOR_VM_BASE_URL` を空にして、生成機能ごと無効にしてある（REQ-0053 の例外）
- 本番は URL を設定済みだが、ワーカーの定期起動を止めてある
  （REQ-0054 のカットオーバーで有効化する。**2026-09-01 に有効化済み**）

製造データ生成は POD の業務の根幹であり、**ここが動かないと発注に進めない。**
生成が `ready` にならない限り、注文明細は「発注準備中」で止まる。

### 確認の順序が逆になっている

REQ-0054 のカットオーバー手順では、**切り戻しの判断は判断ポイント**で行う。ところが
製造データ生成の確認は、その先のワーカー有効化に置かれている。このままだと、
**戻れなくなった後に初めて生成を試すことになる。**

さらに、生成の実行方式はカットオーバーで変わる。移行元の Railway は **REQ-0052 より前の
コード世代**で動いており、受注のレスポンス送出後に `BackgroundTasks` で生成している。
移行先ではこれが **定期起動のワーカー** に変わる。
**一度も動かしたことのない方式へ、戻れない状態で切り替わる。**

移行元の世代は次の 2 点から分かる。

- PR #117 のデータ移送リハーサルで、ダンプのスキーマに `manufacturing_data.lease_expires_at`
  が無かった。この列は REQ-0052（ADR-0029）が追加したものである
- REQ-0052 より前の本番起動コマンドは `alembic upgrade head && uvicorn ...` だったため、
  REQ-0052 以降のイメージがデプロイされていれば、起動時にこの列が作られていたはずである

Railway を止めてしまうと戻れないので、止める前に確認する。

## 詳細

### 業務フロー

環境ごとに次を行う。**ステージングで通してから本番に進む。**

1. 実受注で使われている元画像（PNG レイヤー）の URL を使い、v2 受注 API にテスト注文を 1 件登録する
2. 製造データ行が `pending` で作られることを確認する
3. ワーカーの Job を **手動で 1 回だけ** 実行する（ADR-0034）
4. 行が `ready` になり、成果物が当該環境の Cloud Storage に保存されることを確認する
5. 管理画面の発注資料 ZIP を取得し、生成物が入っていることを確認する
6. テストデータを片付ける

**成果物を管理画面から直接ダウンロードするエンドポイントは存在しない。**
生成物が人の手に渡る経路は発注資料 ZIP であり（`manufacturer_order_service` の
`_load_manufacturing_content` が `manufacturing_data.file_path` を読んで ZIP に入れる）、
`GET /api/v1/orders/{id}/manufacturing-data` は v1 用の別系統である（v2 の行は 404 になる）。
**したがって「成果物が取り出せる」ことの確認は ZIP で行う。**

### 例外・エッジケース

- **Cloud Scheduler は停止したままにする。** 手動実行なら VM に投入されるのは自分が作った
  テスト注文の分だけで、illustrator-vm の待ち行列を継続的に埋めない（ADR-0034）
- **illustrator-vm は 1 件ずつの直列処理**（最大約 300 秒）である。移行元の Railway では
  製造データ生成が現に動いているため、テストジョブはその生成を待たせる。**業務時間外に実施する**
- 元画像は **公開 https の URL** である必要がある。`SOURCE_IMAGE_ALLOWED_HOSTS` が空のため、
  https 必須・パブリック IP のみ許可・リダイレクト追従なしの検証が効く
- **本番の DB は空ではない。** REQ-0054 PR 1 の時点では空だったが、PR 2（データ移送リハーサル）で
  Railway の本番ダンプが流し込まれており、実データの写しが入っている。
  したがって確認は**実データの写しが入った DB に対して行う**ことになる。
  - **既存の行を使わない。** 専用の受注元（`order_sources.code = 'SMOKE_REQ0061'`）と
    管理者を 1 件ずつ足し、それ経由で受注を入れる。製造データのキャッシュキーは
    `(order_source_id, product_code, size, variant)` なので、受注元を分ければ
    実データのキャッシュに触れない
  - **`api/scripts/seed_operation_test.py` は `order_sources` を含むテーブルを一掃するので使わない**
- **ワーカーを流す前に、その環境の `pending` / `generating` を必ず数える。**
  ワーカーはキュー全体を古い順に浚うので、自分が作った行以外も処理される。
  本番の写しには `pending` が無い（`ready` と `failed` だけ）ことを確認してから流す
- 本番 DB のテストデータはカットオーバー時の `DROP SCHEMA` で消えるが、
  **Cloud Storage の成果物は消えない。** 手で削除する

## 受入基準

- [x] ステージングで v2 受注を 1 件登録し、製造データが `ready` になり、管理画面の
      発注資料 ZIP に生成物が入っている
- [x] 本番で v2 受注を 1 件登録し、製造データが `ready` になり、管理画面の
      発注資料 ZIP に生成物が入っている
- [x] 成果物が各環境の Cloud Storage バケットに保存されている
      （ステージングの成果物が本番バケットに入っていない）
- [x] 確認の前後で、ステージング・本番とも `terraform plan` に差分が出ない
      （確認のためにインフラ定義を変更していない）
- [x] ワーカーの Cloud Scheduler が、確認の前後を通じて停止したままである
- [x] 確認に使ったテストデータ（受注・製造データ・Cloud Storage 上の成果物）が両環境から
      削除されている
- [x] 確認手順が文書として残っており、カットオーバー当日に同じ手順を再実行できる

| 製造データ行 | `pending` で作成、明細は `preparing_order` | 同左 |

| 発注資料 ZIP | 200 / 生成 PDF 437,108 B を含む | 200 / 生成 PDF 436,975 B を含む |

| Scheduler | 前後とも `PAUSED` | 前後とも `PAUSED` |
| `terraform plan` | 差分なし | 差分なし |

**確認できた連鎖**（両環境で同一）:

```
v2 受注 → 製造データ行 pending → claim_next_generation（1 文で確保 + リース）
→ 元画像 DL → VM へ投入 → 完了までポーリング → 成果物 DL → GCS へ自前保存
→ ready → 参照明細を「発注準備中」→「発注済み」へ波及 → 発注資料 ZIP に同梱
```

### 途中で分かったこと

- **ステージングには着手時点で `pending` が 2 件残っていた**（REQ-0053 以降の検証データ）。
  ワーカーはキュー全体を浚うので一緒に処理された。`example.com` を指す 1 件は
  元データを取得できず `failed`（元から失敗する行）、`placehold.co` を指す 1 件は
  実際に生成されて `ready` になった。**他人が作った行は削除していない**
- 実行時オーバーライドは Job の定義に残らなかった（確認後も
  ステージングの `ILLUSTRATOR_VM_BASE_URL` は空のまま）。ADR-0034 の前提どおり

## スコープ外

- illustrator-vm の移送・閉域化（REQ-0055）
- 本番カットオーバーそのもの（REQ-0054）
- ワーカーの定期起動の有効化（REQ-0054 のカットオーバー）
- ステージングから製造データ生成を**恒常的に**使えるようにすること。
  本要件は確認が目的であり、繋いだ状態を維持するかは移送後に判断する（REQ-0055 のスコープ外）
