## 内容

製造データの生成をワーカーの中へ移したこと（REQ-0067）で、VM の頃には無かった止まり方が 2 つ生じた。
これを VM の頃と同じ程度まで戻す。

1. **生成の最中にワーカーごと落ちた行を、上限なく取り出し直さない。** 取り出した回数が上限に達していたら、
   リースが切れたときに生成待ちへ戻さず `failed` にして人に渡す
2. **生成の時間切れは 1 回だけやり直す。** やり直しても終わらなければ `failed` にする
3. **やり直し中の行が、ほかの生成の先頭を塞がない。** 取り出しは試行回数の少ない行から行う

## 背景・理由

### ワーカーごと落ちる

VM の頃は、Illustrator が固まったり落ちたりしても、落ちるのは VM の中だけだった。ワーカーは結果を
受け取って行を書き換えられた。今は生成がワーカーのプロセスの中で動くので、生成がメモリを使い切ると
ワーカーのコンテナごと落ちる（Cloud Run Job のメモリは 1GiB）。

落ちた行は `generating` のまま残り、リースの失効（40 分）で `pending` に戻って、次の起動でまた最初に
取り出される（最も古い生成待ちから取り出すため）。同じ入力なら同じように落ちるので、これが上限なく続く。
その間、その行を取った起動はほかの生成を進められない。

`attempts` は取り出しのたびに増えているが、上限で `failed` にする判定は「生成処理を起動できなかった」
経路（REQ-0067 の `_defer_or_fail`）にしか無い。落ちた起動は何も書き戻せないので、この判定に届かない。

同じことは、VectorCraft だけが途中で落ちた（ワーカーは生きている）ときにも起きる。この場合は生成待ちへ
戻して再試行する（生成処理の不調とみなす。REQ-0067）が、戻した行は最も古い生成待ちのままなので、
次の起動もまずそれを取り、また落ちて、その起動を打ち切る。上限の 5 回に達するまで、ほかの生成が止まる。

実データで測った生成のメモリの最大は約 290MB で、普段は起きない。起きるとすれば極端に大きな画像である。

### 時間切れ

VM の生成 API は、Illustrator が 300 秒で終わらなければ強制終了し、10 秒おいて 1 回だけやり直していた
（illustrator-vm の `MAX_RETRIES=1`）。今は 120 秒で VectorCraft を止めて、すぐ `failed` にしている。
VectorCraft の生成は 1〜4 秒なので時間切れはまず起きないが、起きたときに 1 件の入力のせいで人の手を
待つ状態にするのは、VM の頃より後退している。

## 詳細

- 1 の上限は、生成処理を起動できなかったときの上限（`WORKER_MAX_GENERATION_ATTEMPTS`）と同じ回数を使う。
  判定は、リースの切れた行を戻すとき（`reclaim_expired_leases`）に行う。取り出してから判定すると、
  上限に届くまでにリースの失効（40 分）を 1 回余分に待つ
- 2 は、1 件の上限（`GENERATOR_TIMEOUT_SECONDS`）の中でやり直す。1 回目に上限の半分を使い、
  時間切れならもう半分でもう 1 回作る。**1 件にかかる時間の上限は変えない**ので、Job のタイムアウトと
  リースの計算（`infra/modules/stack` の `locals`、`lease_margin_warning`）は変わらない
- 2 のやり直しは同じ取り出しの中で行う。生成待ちへ戻すと、遅い入力 1 件のためにその起動の残りが止まる
- 3 は、取り出しの順を「試行回数 → 作成日時」にする。初回の行はこれまでどおり古い順に取られる

## 受入基準

- [ ] 取り出した回数が `WORKER_MAX_GENERATION_ATTEMPTS` に達した行は、リースが切れても生成待ちへ戻らずに `failed` になり、管理画面にその理由が出ること
- [ ] 1 の `failed` は、ほかの失敗と同じく「製造データの生成が失敗した」アラートの対象になること
- [ ] 生成が時間切れになったとき、同じ取り出しの中で 1 回だけやり直し、2 回とも時間切れなら `failed` になること
- [ ] 1 件の生成にかかる時間の上限（`GENERATOR_TIMEOUT_SECONDS`）が、やり直しを含めても超えないこと
- [ ] やり直し中の行より、初回の行が先に取り出されること
- [ ] 本番で製造データの生成が動き続けていること（デプロイ後、ワーカーの死活確認が OK）

## スコープ外

- メモリの上限（1GiB）の見直し。実データでは余裕があり、落ちる入力が見つかってから決める
- 落ちた原因の特定（どの入力で落ちたかは、`failed` の行と Cloud Run Job の実行ログで追える）
