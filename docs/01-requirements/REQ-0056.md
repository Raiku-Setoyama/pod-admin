## 内容

コード上のテーブル定義と、実際に動いているデータベースの構造が食い違っている。
どちらも同じ動作にはなっているが、**マイグレーションを自動生成すると、その差を「直すべき差」と
みなして削除の命令が出る。**気づかずに適用すると、索引や制約が意図せず作り直される。

## 背景・理由

REQ-0052 の実装中に発見した。`alembic revision --autogenerate` を実行すると、
何も変更していないのに以下の差分が生成される（2026-08-27 時点、`main` + REQ-0052 の変更）。

| テーブル | 生成される命令 |
|---|---|
| `order_sources` | `code` / `api_key` の UNIQUE 制約を削除し、索引をユニークに作り替える |
| `company_holidays` | `date` の UNIQUE 制約を削除し、索引をユニークに作り替える |
| `products` | 部分ユニーク索引 `uq_products_type_size_position_color` を削除する |
| `manufacturing_data` | キャッシュキーの索引を削除し、UNIQUE 制約として作り直す |
| `order_items` | `uid` を NOT NULL から NULL 許容へ変更する |
| `order_items` | `product_type` に索引を追加する |

原因は書き方の違いである。たとえば `order_sources` はモデル側が
`mapped_column(String(50), unique=True, index=True)` と書いており、これは 1 本の
ユニーク索引を意味する。一方、実際のデータベースには非ユニークな索引 `ix_order_sources_code` と
別建ての UNIQUE 制約 `order_sources_code_key` が存在する。**一意性はどちらでも保たれるため
現在の動作に問題はないが、定義としては一致していない。**

`products` の部分ユニーク索引の削除は、とくに影響が大きい
（REQ-0015「同一仕様の有効な商品を二重登録できない」を支えている索引である）。

## 判断が出ないと止まるもの

- **どちらに合わせるか。** 実際のデータベースに合わせてモデルを書き直すのか、
  モデルに合わせてマイグレーションを 1 本入れて作り替えるのか。
  後者は本番で索引の作り直しが発生する

## 詳細

**現時点で動作に不具合は出ていない。** 自動生成を使わず、マイグレーションを手で書いている限りは
表面化しない。解消の価値は「自動生成を安全に使えるようにすること」にある。

## スコープ外

- マイグレーションの自動生成を CI に組み込むこと（別の話）
