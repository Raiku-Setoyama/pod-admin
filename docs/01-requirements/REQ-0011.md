## 内容
外部の販売サイトは、完成デザインの代わりに元データ（PNGレイヤー画像）を添えた受注を登録できる。受注を受け付けたあと、システム側が元データをもとに製造用データを生成する。

## 背景・理由
背景は未確認（既存実装からの逆算のため）。外部サイト側で完成デザインを用意できない場合でも、元データ（レイヤー画像）を渡せば製造データの生成までシステムが引き受けられるようにするため、v1とは別の取り込み方式が必要となる。

## 判断が出ないと止まるもの
なし

## 詳細
外部販売サイトは、受注明細に元データとなるレイヤー画像（source_images、1〜8枚）を添えて受注登録APIを呼び出す。明細は最大100件まで受け付ける。受注を受け付ける時点で、生成に必要な対応付け（ビルドVMマッピング）が成立するかを同期的に検証し、生成できない注文が登録されてしまうのを防ぐ。受注登録が成功した明細は初期状態「preparing_order（製造準備中）」となり、その後にシステムが製造用データを生成する（生成処理の本体はこの要件の範囲外）。元データ（source_images）はJSONB形式で保持される。

主なエンドポイント:
- `POST /api/v2/orders` — 元データ（PNGレイヤー）付きの受注を登録する（source_images 1〜8枚、明細最大100件、同期の取り込み検証、初期状態 preparing_order）

## 受入基準
- [x] 受注明細に元データのレイヤー画像（source_images）を1〜8枚添えて `POST /api/v2/orders` すると、受注が登録される
- [x] 受注明細は最大100件まで受け付けられる
- [x] 受注受付時に生成の対応付け（ビルドVMマッピング）が同期的に検証され、生成できない注文の受理を防ぐ
- [x] 登録された明細の初期状態は preparing_order（製造準備中）となる
- [x] 元データ（source_images）はJSONB形式で保持される

## スコープ外
- 製造用データの生成処理そのもの（生成本体）はこの要件の範囲外
