## 内容

ステージングで動作確認が取れたあと、本番環境を GCP へ移す。

本番には既存のデータ（受注・製造データ・アップロード済みファイル）があるので、
**失わずに移す**ことが最優先である。移行には枠を取るが、**旧環境は止めない**（ADR-0035）。
枠の間に止めるのは旧管理画面での作業であって、サービスではない。

外部販売サイトが API を叩いているため、**接続先 URL の変更を相手方と調整する必要がある。**

## 背景・理由

現在の本番は API が Railway、フロントが Vercel に分かれている。
`docs/00-charter/nfr.md` は可用性について「本番 API は Railway 単一構成（HA・冗長化の有無は未確認）」
と記録しており、本格運用の前提として構成を作り直す必要がある。

あわせて、ファイル保管に使っている Cloud Storage バケット `pod-admin-prod` は
**会社組織ではない個人の Google アカウント配下**（プロジェクト `lively-transit-334610`、
請求先も会社とは別）にある。移行を機に会社組織へ寄せる。

## 詳細

### 業務フロー（カットオーバー）

**旧環境は止めずに切り替え、停止は最後に回す**（ADR-0035）。次の順で行う。

1. メーカー日次発注ダイジェストのワークフローを止める（**自動の書き込みを先に塞ぐ**）
2. 旧管理画面での作業を止めてもらう。**Railway は動かしたまま**
3. データベースを移送する
4. マイグレーションを実行し、整合を確認する
5. ファイルを移送する
6. 動作確認を行う
7. **2 回目のダンプを取り、1 回目と件数を突き合わせる**（移送の間に旧環境へ書き込みが
   入らなかったことの機械的な確認）

**★ 判断ポイント。** ここまで旧環境は無傷で動いており、**何もしないことが切り戻しになる。**

8. 外部販売サイトに新しい URL を適用してもらい、疎通を確認する
9. 内部バッチの呼び出し先を切り替える。**`API_BASE_URL` だけでなく
   `INTERNAL_API_SECRET` も差し替える**（環境ごとに Terraform が乱数で作るので移送では移らない）。
   そのうえでダイジェストを再開する
10. 製造データ生成ワーカーの定期起動を有効にする
11. Railway の API と Vercel を停止する。**削除はしない**
12. 観察期間を置き、問題が出なければ旧環境を撤去する（別作業）

**2 回目のダンプは判断ポイントより前に取る。** ADR-0035 が停止しない方式を選べたのは、
**失敗しても検知して 15〜30 分でやり直せる**からである。判断ポイントを越えたあとに
突合すると、外部販売サイトは既に新環境を向いており、ワーカーも書き込んでいるので、
**`reset` してやり直すと切替後の受注を壊す。** 検知はできても直せない位置になり、
この方式を選んだ根拠そのものが消える。

**判断ポイントを越えると元に戻せない。** 外部販売サイトが新しい URL を向いたあとの受注は
移行先にしか存在しないためである。

**この境界は番号ではなく「判断ポイント」という名前で指す。** 手順の順序は現に一度
組み替わっており、番号で参照すると、組み替えるたびに他の文書の参照が黙ってずれる。
**ずれた参照は「後戻りできない手順」として戻せる手順を指す**ので、いちばん危ない箇所で嘘になる。

**当初は Railway の停止が手順 2 にあった。** 停止の目的は書き込みの凍結であって
URL 切替の前提ではないため、停止を最後尾へ移した。判断と、代わりに置いた検証は ADR-0035。

### 例外・エッジケース

- 移行先の API は普段インスタンスを起動していないため、外部販売サイトからの最初のリクエストが
  遅くなる。相手方のタイムアウト値を事前に確認し、必要なら常時 1 インスタンスを起動しておく
- ファイルの保存先バケット名は変わるが、データベースが持つファイルパスは保存先に依存しない
  形式のため、データの書き換えは不要である

手順を当日その場で組み立てないよう、`infra/scripts/migrate-data.sh` に落とした

- `restore` は `--single-transaction`、最後に `VACUUM ANALYZE`。
  **統計が無いまま動作確認に入ると「壊れている」のか「統計がまだ無い」のかを区別できず、
  後戻りできない切替（判断ポイントの先）の判断材料が濁る**

#### ファイル（完了）

旧バケット `gs://pod-admin-prod`（個人プロジェクト）から新バケットへ **10 ファイル・
約 29MB を複製し、全件の名前と CRC32C の一致を確認した。** 旧バケットは
複製の前後で 30,415,579 バイトのまま変わっていない。

**`gcloud storage rsync` は使えない。** 個人プロジェクトのサービスアカウント
（`pod-admin-storage@`、`key.json`）はオブジェクトを読めるが `storage.buckets.get` を

#### データベース（**移送先の検証は完了。移送元が未検証**）

移送元を Railway にできなかったため、**ステージングの Cloud SQL を仮の移送元にして、
移送先側の機構を通しで検証した。**

| 確かめたこと | 結果 |
|---|---|
| `pg_dump --no-owner --no-acl` が Cloud SQL 16 に流し込める | ✅ |
| 全テーブルの件数が移送元と一致する（15 テーブル） | ✅ `compare` が機械的に判定 |
| **`alembic_version` が一緒に移る**（当日の migrate Job が no-op になる） | ✅ `add_mfg_generation_lease` |
| `reset` → `restore` を通した**あともアプリが動く** | ✅ ログイン・受注 5 件・商品 12 件 |
| 破壊的な操作が移送元で止まる（ホスト名／IP／空文字／DB 名違い） | ✅ 4 経路すべて拒否 |

**破壊的な経路は、使い捨てのステージングを対象に通しで確かめた。**
`reset` で public を落としてから自分のダンプを流し戻し、
**そのあともログインと一覧取得ができることまで確認している**
（`CREATE SCHEMA public` は初期状態の権限を持たないので、
`AUTHORIZATION` と `GRANT USAGE` を明示しないとアプリが読めなくなる。
`--no-acl` のダンプは権限を戻してくれない）。

移送先の機構の確認は、本番インスタンス上の**使い捨ての別データベース**で行い、
検証後に破棄した。**本番の `pod_admin` には触れていない**（15 テーブル・
alembic は PR 1 と同じまま）。アプリに他人のデータを一瞬でも配信させないためである。

**まだ確かめられていないのは、実物のダンプでしか判らないことだけである** —
本番の実データ量・文字コード・`pg_dump` の所要時間、
および移送後の管理画面からのファイルダウンロード。
**ダンプを受け取った時点で、当日を待たずに通しで確認できる。**

#### 移送元（Railway）のダンプは人間が手元で取る（決定）

Railway の Postgres には **TCP プロキシが有効化されておらず、外から接続できない。**
`DATABASE_PUBLIC_URL` はホストとポートが空のまま解決されず、`railway connect` は
「Connection URL should point to the Railway TCP proxy」で終了する。
`PGHOST` は `postgres.railway.internal` で外部からは名前解決できない。

有効化には Postgres サービスの再デプロイが伴いうる（＝**本番が一時的に止まる**）。
**そこまでして自動化する価値がないので、ダンプの取得は依頼者が手元で行い、
ファイルを受け渡す**（2026-08-30 の依頼者判断）。
**このリポジトリから移送元へ接続する経路は作らない。**

```bash
pg_dump "$RAILWAY_DATABASE_URL" --no-owner --no-acl --format=plain > prod.sql
```

3 つのオプションはすべて必須である（無いと restore が落ちるか、
`restore` / `counts-dump` が形式を読めない）。手順は `infra/README.md`。

**受入基準「移行前後で各件数が一致する」は、これでも機械的に検証できる。**
`counts-dump` がダンプファイルから直接 COPY ブロックの行数を数えるので、
**移送元に接続しなくても移送元の件数が出る。** ダンプは 1 つの断面なので、
そこから数えた値は「実際に移送したもの」の数そのものになる。

**ただし、それだけでは「移送できた」ことの証明にならない。**
移送元の件数をダンプから取ると、突合の両側が同じダンプから派生してしまい、
`compare` が確かめるのは「ダンプ → 移送先」の一段だけになる。
**「移送元 → ダンプ」で落ちたものは両側から等しく消え、一致と報告される**
（`pg_dump -t` / `-T` を付けて取ると実際に起きる。検証で再現した）。

そこで `counts-dump` は、**ダンプの外にある正本**＝`api/app/models/*.py` の
`__tablename__` と突き合わせ、足りないテーブルがあれば異常終了する。
一覧は手で並べず、モデルから読む。

`reset` は破壊的で後戻りできない。**その手前に立つ唯一の関門がここ**なので、
形式の異常もまとめてここで落とす。ステージングで実測した挙動:

| 渡したもの | 結果 |
|---|---|
| 正しいダンプ | ✅ 15 テーブル。DB から数えた結果と一致 |
| `-T` でテーブルを 1 つ落とした | ❌ 「ダンプに無いテーブル: ['chat_messages']」 |
| `--data-only` | ❌ `reset` の**前に**落ちる |
| 転送で途中まで欠けた | ❌ 「ダンプが完結していません」 |
| CRLF に書き換えられた | ❌ 信用せず取り直しを求める |

### 実物のダンプで判明したこと（2026-08-30・PR 2）

依頼者が手元で取得した本番ダンプ（91,951 バイト）を検証したところ、
**当日に遭遇していたら詰んでいた問題が 2 つ出た。**

#### 1. 移送元が PostgreSQL 17、移送先が 16 だった（**移送先を 17 に上げて解消**）

| | バージョン |
|---|---|
| 移送元（Railway） | **17.11** |
| 移送先（Cloud SQL・当初） | 16 |

**PostgreSQL は上位メジャーのダンプを下位に流し込めない。**
加えて 17 系のダンプは `\restrict` / `\unrestrict` を含み、psql 16 は解釈できない。
**このまま当日を迎えていたら、メンテナンス枠の中で初めて気づくことになっていた。**

原因は `docs/00-charter/constraints.md` が「PostgreSQL 16」と記録しており、
**その記載に従って移送先を作ったこと**である。本番は 17.11 なので、記載が実態と
食い違っていた。憲章を訂正し、Cloud SQL を 17 へ上げた（インスタンスの
作り直しは不要で、その場で更新された）。

**ローカル開発は 16 のままである**（`api/docker-compose.yml`）。
本番とメジャーが違う環境でテストしている状態なので、**REQ-0058 として起票した。**

#### 2. `railway ssh` の出力が CRLF になる

`railway ssh` は擬似端末を割り当てるため、**出力の改行がすべて CRLF に書き換わる。**
そのまま流し込むと各行の最後の列に `\r` が入る。
`counts-dump` の改行コード検査がこれを捕まえた（1,070 行すべてが CRLF、孤立した CR は 0）。

`| tr -d '\r'` を挟めば復元できる。pg_dump のテキスト形式はデータ中の CR を
`\r`（2 文字）に逃がすので、**生の CR は本来存在せず、一律に削ってよい。**
手順は `infra/README.md` に反映した。

#### 本番の実データ量（LF に直したあとの検証結果）

| テーブル | 件数 | テーブル | 件数 |
|---|---|---|---|

#### 移送直後にアプリが 500 になった（原因と対処を script に反映）

流し込んだ直後、受注一覧が 500 になった。

```
column manufacturing_data.lease_expires_at does not exist
```

**移送元の Railway が動かしているコードは、`main` より古い世代である。**
復元された `alembic_version` は `cancel_order_items` で、`main` の head
（`add_mfg_generation_lease`）より手前だった。移送先では新しいコードが動くので、
まだ存在しない列を触って落ちる。

**対処はカットオーバーの migrate Job そのものである。** 実行したところ
head まで進み、エラーは止まった。**行数は 1 件も変わっていない。**

**問題は、手順を飛ばしても何も言われなかったことである。**
`compare` は全 15 テーブルの一致を報告しており、**突合が通っているのに
アプリは全滅していた。** 件数はスキーマの世代を何も語らない。

そこで `restore` の最後に、**流し込んだ `alembic_version` と
`api/alembic/versions/` の head を突き合わせる**ようにした（`infra/scripts/alembic-head.py`）。
ずれていれば「このままではアプリが 500 になります」と出して migrate Job を促す。
**手順書に書くだけでは、飛ばした人を止められない。**

head の判定は正規表現ではなく `ast` で行う。`down_revision` は文字列とは限らず、
マージマイグレーションではタプルになる。**素朴な正規表現はタプルを読み落とし、
マージ済みのリビジョンをヘッドだと誤検出する**（実際に誤検出し、
存在しない多重ヘッドを報告した）。多重ヘッドの検出も兼ねる
（AGENTS.md「Alembic のマイグレーションは多重ヘッドに注意」）。

**残るは管理画面での目視確認だけである** — ログインし、受注一覧を開き、
製造データのファイルをダウンロードする。**本番利用者の資格情報が要るため、
依頼者にお願いする。**

### 本番への反映ワークフローを足す

`.github/workflows/deploy.yml` が反映手順の本体で、`workflow_call` で呼ばれる。
本番用にやることは `deploy-prod.yml`（呼び出し側）を足すだけである。
**`deploy.yml` を複製しない。**

- 契機は手動実行にする（`workflow_dispatch`）。ADR-0028 が定めた「本番は人間の承認を挟む」
- 承認を機械的に強制したいなら、呼び出し側に GitHub Environment の
  承認付きジョブを置き、`needs` で繋ぐ。**`deploy.yml` 側には入れない**
  （リポジトリの設定画面が正本になり、Terraform の管理下から外れるため）
- `workload_identity_provider` と `service_account` は本番の
  `terraform output` から取る
- **`allowed_ref` は既定（`refs/heads/main`）のままにする。** 本番の反映は
  `workflow_dispatch` だが、`main` から起動するかぎり ref は `refs/heads/main` である。
  ブランチから起動すると GCP の認証で落ちる。**それが意図した動作である**（ADR-0031）

**管理画面のイメージは環境ごとに別物になる。** `NEXT_PUBLIC_API_URL` は
ビルド時にバンドルへ焼き込まれるため（`web/Dockerfile`）、
ステージングで確認したイメージをそのまま本番に持っていくことはできない。
**本番のフロントは、カットオーバー当日に初めてビルドされる。**
リハーサルでは、本番の URL を指す build-arg で一度ビルドが通ることまで確認しておく。

### `modules/stack/` の切り出し（PR 1 で完了）

アプリ固有の合成層を `infra/modules/stack/` へ切り出した。
`infra/envs/<env>/` は値だけを持つ薄い呼び出しになり、
`diff infra/envs/staging/main.tf infra/envs/prod/main.tf` が
そのまま「ステージングと本番の違い」の一覧になる。

state のアドレスは `module.api` → `module.stack.module.api` に変わるが、
`terraform state mv` は使わず `infra/envs/staging/moved.tf` の `moved` ブロックで宣言した。
**`terraform plan` が `0 to add, 0 to change, 0 to destroy` を返すことで、
純粋な移設であることを機械的に確認できる。**

`moved.tf` は適用済みの state に対しては no-op になるが、**消してはならない。**
切り出し前の state を持つ環境がまだあり得るあいだは、移設の経路として要る。

`google_service_account_iam_member.deployer_act_as` と
`modules/service-accounts` の `ids` 出力は**そのまま残した。**
「env 直下の裸のリソース」という指摘は切り出しそのもので解消しており
（合成層が持つ配線として `modules/stack/` にある）、
デプロイ用 SA を `github-oidc` 側へ移すと state の移設が 4 件増える。
**得られるのは `ids` 出力が消えることだけで、割に合わない。**

#### 凍結は機械的に確かめた（2 回目のダンプ）

移送の前後で旧環境が動いていないことを、**判断ポイントに入る前に**確かめた。

| | 1 回目 | 2 回目 |
|---|---|---|
| 取得 | 2026-08-31 21:58 | 2026-09-01 10:19 |
| サイズ | 94,007 B | 94,007 B |
| 15 テーブルの件数 | — | **一致** |

**「取り直したもの」であることを先に確かめる。** 同じファイルを 2 度渡されても
突合は当然通るので、それでは何も証明できない。`pg_dump` は実行ごとに
`\restrict` のトークンを変えるので、**そこが違えば別の実行である**
（`tfK0qCkD…` → `EUcoJ7h1…`）。

そのうえで、**件数ではなく中身を突き合わせた。** 件数は行が書き換わっても動かないためである。
揮発する `\restrict` / `\unrestrict` の 2 行を除くと、**2 つのダンプはバイト単位で同一**だった。
**1 行も動いていない。**

#### 宙吊りの製造データは無かった

ワーカーを有効にする前に `manufacturing_data` 13 件の内訳を数えた。
**`ready` 10 / `failed` 3 で、`pending` と `generating` はゼロ**である。

移送元の Railway は REQ-0052 より前の世代で、レスポンス送出後の `BackgroundTasks` で
生成している。**その最中にダンプを取れば `generating` のまま移ってくる**が、
今回は無かった。**有効化の瞬間にまとめて VM へ流れる事故は起きない。**

#### `INTERNAL_API_SECRET` も差し替えが要る

カットオーバーの手順は内部バッチについて `API_BASE_URL` の差し替えしか書いていなかった。
**`INTERNAL_API_SECRET` は環境ごとに Terraform が乱数で作っている**
（`random_password.internal_api_secret`）。移送では移らない。

差し替えないと、ダイジェストのワークフローは新 URL に対して 401 で落ち続ける。
**気づけるので実害は「届かない」だけだが、当日に原因を探す時間になる。**

同じ理由で **`SECRET_KEY` も環境ごとに違う。** JWT の署名鍵なので、
**切り替えた瞬間に利用者のログインがすべて無効になる。** 再ログインが要ることを事前に伝える。
