## 内容

ステージングで動作確認が取れたあと、本番環境を GCP へ移す。

本番には既存のデータ（受注・製造データ・アップロード済みファイル）があるので、
**失わずに移す**ことが最優先である。移行にはメンテナンス枠を取り、その間はサービスを止める。

外部販売サイトが API を叩いているため、**接続先 URL の変更を相手方と調整する必要がある。**

## 背景・理由

現在の本番は API が Railway、フロントが Vercel に分かれている。
`docs/00-charter/nfr.md` は可用性について「本番 API は Railway 単一構成（HA・冗長化の有無は未確認）」
と記録しており、本格運用の前提として構成を作り直す必要がある。

あわせて、ファイル保管に使っている Cloud Storage バケット `pod-admin-prod` は
**会社組織ではない個人の Google アカウント配下**（プロジェクト `lively-transit-334610`、
請求先も会社とは別）にある。移行を機に会社組織へ寄せる。

## 詳細

### 業務フロー（カットオーバー）

メンテナンス枠を取り、次の順で切り替える。

1. メンテナンスを告知し、外部販売サイトからの送信を止めてもらう
2. Railway の API を停止する（新規書き込みを止める）
3. データベースを移送する
4. ファイルを移送する
5. マイグレーションを実行し、整合を確認する
6. GCP 上の API とフロントを公開する
7. **動作確認を行う。ここまでは Railway / Vercel を再開するだけで元に戻せる**
8. 内部バッチの呼び出し先を新しい URL に切り替える
9. 外部販売サイトに新しい URL を適用してもらい、疎通を確認する
10. Vercel を停止する
11. 製造データ生成ワーカーの定期起動を有効にする

**手順 9 以降は元に戻せない。** 外部販売サイトが新しい URL を向いたあとの受注は
移行先にしか存在しないためである。**続行の判断は手順 7 の結果を見て、手順 8 に入る前に行う。**

### 例外・エッジケース

- 移行先の API は普段インスタンスを起動していないため、外部販売サイトからの最初のリクエストが
  遅くなる。相手方のタイムアウト値を事前に確認し、必要なら常時 1 インスタンスを起動しておく
- ファイルの保存先バケット名は変わるが、データベースが持つファイルパスは保存先に依存しない
  形式のため、データの書き換えは不要である

## 受入基準

- [ ] 本番環境の `terraform apply` が完走し、再実行したとき差分が出ない
- [ ] 移行前後で、受注・受注明細・製造データ・配送・メーカー・商品の各件数が一致する
- [ ] 移行前に存在していたファイルが、移行後の管理画面から同じ手順でダウンロードできる
- [ ] 本番の API とフロントが公開 URL で応答し、ログイン・受注一覧・発注・配送・請求書PDF・
      チャットが動作する
- [ ] 外部販売サイトが新しい URL で受注を登録でき、v1 と v2 の両方で疎通する
- [ ] メーカー日次発注ダイジェストが新しい URL に対して実行され、二重送信しない
- [ ] 製造データ生成ワーカーが定期起動し、本番の受注から製造データが生成される
- [ ] データベースの自動バックアップと時点復旧が有効になっている
- [ ] Railway と Vercel を停止しても、本番の機能に影響が出ない
- [ ] ファイル保管用バケットが会社組織のプロジェクト配下にある

## スコープ外

- 外部 VM（illustrator-vm）の移送（REQ-0055）
- 独自ドメインの割り当て
- 監視・アラートの本格整備

## 実装メモ

カットオーバーは 1 回の作業で行う。事前準備（本番リソースの構築・イメージの用意・
データ移送のリハーサル）は先行して別の PR で進めてよい。
受入基準がすべて埋まるのはカットオーバー完了時である。

手順とロールバックの詳細は
`docs/superpowers/specs/2026-08-27-gcp-migration-design.md` の「9. 本番カットオーバー手順」。
