## 内容

製造データ生成 VM（`illustrator-vm`）が落ちたことに気づき、自動で復旧する仕組みを、
**外部 IP を前提としない形で用意する。**

## 背景・理由

### 既存の仕組みは、移送によって前提を失った

`illustrator-vm` リポジトリには、次の復旧経路を構築するスクリプトが既にある
（`infra/setup_monitoring.sh` と `infra/deploy_auto_restart.sh`）。

```
Cloud Monitoring の Uptime Check（/health を 1 分間隔）
  → 2 回連続失敗でアラート → Pub/Sub → Cloud Function
  → VM を reset（IP とデータは維持）＋ Slack 通知
```

**この Uptime Check は公開 URL に対するものである。** スクリプトは
`--resource-type=uptime-url --hostname=<VM の外部 IP>` で作り、冒頭にも前提が明記してある。

```
# - VM に外部IPがあり、ポート8000がファイアウォールで許可済み
```

**REQ-0055 でその外部 IP を外した。** Uptime Check の probe は公衆網から来るので、
`10.20.0.10` には原理的に到達できない。**移送先の VM に死活監視と自動復旧は無い。**

**これは机上の話ではない。** 旧プロジェクトには Uptime Check `illustrator-api-health`
（`34.84.121.166:8000/health` を 60 秒間隔）と、それを受ける Alert policy
`illustrator-api-down` → Pub/Sub → Cloud Function による自動再起動が**実際に構築されていた**
（`illustrator-vm` リポジトリの Issue #5 に実測の記録がある）。
**イメージはディスクを運ぶだけで、これらは運ばない。**

### 気づけないことの重さ

VM が止まっても、**pod-admin 側は静かに壊れる。**
ワーカーは `generate()` の例外を捕まえて行を `failed` にする（`manufacturing_data_service.py`）。
**ワーカーはそれを拾い直さない** — `claim_next_generation` は `pending` しか取らず、
`reclaim_expired_leases()` が戻すのはリースの切れた `generating` だけである。
戻す道はあるが、**どちらも人の操作が要る**（管理画面からの `retry` は 1 件ずつ、
あるいは同じキャッシュキーでの再受注）。
落ちる量は **1 回の起動あたり最大 20 件**（`worker_max_items`）である。

画面にはエラーが出ない。気づく手段は、いまのところ「発注できないという問い合わせ」しかない。

### なぜ不具合ではなく要件か

**違反していると引用できる受入基準が無い。** `nfr.md` の可用性節が定めているのは
pod-admin 自身の構成であり、VM の監視について約束した文書は無い。
REQ-0055 の受入基準にも入っていない（移送と閉域化が対象だった）。
`AGENTS.md`「不具合か、仕様変更か」の判定に従い、**新しい約束＝要件**として扱う。

**ただし、この欠落は REQ-0055 の作業が持ち込んだものである。** 気づいたのは移送の後であり、
移送前は（設定されていれば）働いていた可能性がある。

## 詳細

### 業務フロー

1. VM の生成 API が応答しないことを検知する
2. 一定回数続いたら復旧を試みる（VM の reset）
3. 人に通知する

### 例外・エッジケース

- **「VM は動いているが Illustrator が固まっている」を検知できるか。**
  `/health` は `illustrator_running` と待ち行列を返すので、単なる TCP 疎通より深く見られる
- 復旧の reset がジョブの処理中に走ると、その 1 件は失われる。
  リースが切れれば `pending` に戻る（ADR-0029）ので、**戻せる設計にはなっている**
- **VM は 1 件ずつの直列処理である。** 監視の投入するジョブが本番を待たせない形にする

### 検討の材料

外部 IP を戻さずに済む案が少なくとも 3 つある。**どれを採るかはこの要件の中で決める。**

| 案 | 中身 | 論点 |
|---|---|---|
| A | ワーカー側のログベースアラート（`IllustratorVmError` / `failed` の増加） | **すでに VPC 内から VM を叩いている唯一の経路を使う。**追加の到達手段が要らない。ただし「5 分間隔で誰かが受注しないと分からない」 |
| B | Cloud Monitoring の非公開 Uptime Check | 公開 URL 以外を対象にできるが、構成が増える |
| C | 小さな定期ジョブ（Cloud Run Job）が VPC 経由で `/health` を叩く | 既存の Direct VPC egress の仕組みをそのまま使える |

自動復旧（VM の reset）まで戻すかも同時に決める。**検知だけ先に入れる**選択もある。

## スコープ外

- 生成そのものの機能変更（REQ-0020 の範囲）
- VM のディスクのバックアップ（REQ-0062）

## 実装メモ

**`illustrator-vm` リポジトリ側のスクリプトが外部 IP を前提にしたままである。**
そちらの是正は別リポジトリの Issue として起票した。
