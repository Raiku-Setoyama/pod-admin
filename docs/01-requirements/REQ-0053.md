## 内容

本格運用に向けて、インフラを**コードで管理できる状態**にしたい。手作業でコンソールを触って
作った環境は、何がどう設定されているか誰にも分からなくなり、同じものをもう一度作れない。

そのうえで、**本番と同じ形のステージング環境**を先に作る。本番を触る前に、そこで動作確認を取る。

ステージングには移行するデータが無いので、まっさらな状態から立ち上げる。

## 背景・理由

現在、API は Railway、フロントは Vercel でホスティングされており、設定はそれぞれの管理画面に
散らばっている。ステージング環境は存在しない。**本番でしか動作確認ができない状態**である。

GCP プロジェクトは会社組織 `tosyoworkspace.tokyo` の下に 2 つ用意されている
（本番 `tosyo-api-504104` / ステージング `tosyo-api-stg`）が、いずれもリソースは未構築である。

## 詳細

### 構成

Terraform のコードを `infra/` に置き、共通モジュールと環境ごとの薄い定義に分ける。
state は環境ごとに別の Cloud Storage バケットへ保存する（ADR-0027）。

デプロイは GitHub Actions から行う。認証には Workload Identity 連携を使い、
**サービスアカウントの鍵 JSON をリポジトリに置かない**（ADR-0028）。

構築するもの（ADR-0026）:

- Cloud Run（API / フロント）
- Cloud Run Job（マイグレーション / 製造データ生成ワーカー）
- Cloud SQL（PostgreSQL 16）
- Cloud Storage（ファイル保管）
- Secret Manager（機密情報）
- Artifact Registry（コンテナイメージ）
- Cloud Scheduler（ワーカーの定期起動）

### 前提

**着手前に、両 GCP プロジェクトへの IAM 権限の付与が必要である。**
現在の作業者は `roles/editor` であり、`resourcemanager.projects.setIamPolicy` /
`iam.workloadIdentityPools.create` / `run.services.setIamPolicy` /
`iam.serviceAccounts.setIamPolicy` を持たない。これが無いと `terraform apply` は必ず失敗する。

### 例外・エッジケース

- ステージングの製造データ生成は、外部 VM を本番と共有すると本番のジョブ待ち行列に混ざるため、
  当面は無効にしておく（外部 VM の移送後に繋ぎ直す。REQ-0055）
- ステージングの DB は最小構成のため同時接続数の上限が小さい。API の最大インスタンス数と
  接続プールのサイズを、その上限に収まるよう設定する

## 受入基準

- [x] `infra/` に Terraform のコードがあり、ステージング環境の `terraform apply` が完走する
- [x] 同じ状態で `terraform plan` を再実行したとき、差分が出ない
- [x] Terraform の state がバージョニング有効の Cloud Storage バケットに保存されている
- [x] ステージングの API が公開 URL で `/health` に 200 を返す
- [x] ステージングのフロントが公開 URL で表示され、そこから API を呼べる
- [x] API が Cloud SQL に接続し、受注一覧を取得できる
- [x] マイグレーション用の Job が `alembic upgrade head` を完走する
- [x] アップロードしたファイルがステージング専用の Cloud Storage バケットに保存され、
      画面からダウンロードできる
- [x] 機密情報（JWT 署名鍵・DB パスワード・SendGrid APIキー・内部シークレット）が
      Secret Manager から注入され、鍵 JSON をリポジトリにも環境変数にも置いていない
- [x] GitHub Actions が鍵 JSON なしで GCP に認証し、`main` へのマージでステージングへ
      自動デプロイされる
- [ ] ログイン・受注一覧・発注・配送・請求書PDF・外部連携API(v1/v2)・チャットが

## スコープ外

- 本番環境の構築とデータ移行（REQ-0054）
- 外部 VM（illustrator-vm）の移送（REQ-0055）
- 監視・アラートの本格整備
- 独自ドメインの割り当て（当面は発行される URL をそのまま使う）
- 予算アラートの設定（請求先アカウントの権限が必要なため、プロジェクト所有者の作業）

## 実装メモ

**2 本の PR に分ける。**設計書のフェーズ 2／3 の境界で切る。
そこが「動作確認が取れた」の判定ゲートであり、レビューの単位として意味を持つため。

| # | 内容 | 満たす受入基準 |
|---|---|---|
| 1 | `infra/` の Terraform 一式。ステージングを構築し、手動デプロイで疎通を確認する | 1〜9 |
| 2 | Workload Identity 連携とデプロイ用ワークフロー。自動デプロイと業務シナリオの確認 | 10, 11 |

**受入基準 11 は PR 2 では埋まらない。** 請求書PDFの発行が
管理画面・ポータルの双方で 500 になる不具合が見つかったためである（**BUG-0002**）。
環境に依存しない既存の不具合なので、この要件では直さず別の PR で修正する
（`AGENTS.md`「1 不具合 = 1 修正 PR」）。**BUG-0002 の修正が REQ-0053 を閉じる。**

起票時の想定（基盤／データ層／実行層／CI/CD の 4 本）より粗くした。
Terraform のモジュールは互いを参照するため、3 本に切ると
**どの中間状態でも `terraform apply` が完走しない**（=レビューできる形にならない）。
実装の都合による分割なので、要件そのものは分けない。

いずれの中間状態でも `main` は壊れない（既存の Railway / Vercel 運用に影響しないため）。
受入基準はすべて埋まった最後の PR で `done` にする。

### 設計上の決定

- 実行中のコンテナイメージは Terraform の管理対象にしない（**ADR-0030**）。
  Terraform はサンプルイメージで作り、実物はデプロイが入れる

### PR 2 で見つけて直したこと — Cloud Run は 1 サービスに URL を 2 つ割り当てる

**新形式の URL で開くと、ログインすら通らなかった。**

```
https://pod-admin-web-644320531544.asia-northeast1.run.app/login
→ OPTIONS .../api/v1/auth/login が 400 "Disallowed CORS origin"
→ POST は送られない。画面には何も出ない
```

Cloud Run は 1 つのサービスに 2 つの URL を割り当てる。

| 形式 | 例 |
|---|---|
| 旧 | `https://pod-admin-web-kkwi54ngsq-an.a.run.app` |
| 新 | `https://pod-admin-web-644320531544.asia-northeast1.run.app` |

**どちらも公開されていて等しく届く。** ところが Terraform の
`google_cloud_run_v2_service.uri` は**そのうち 1 つしか返さない**ため、
`CORS_ORIGINS` に旧形式だけが入っていた。

`urls`（すべての URL のリスト）を使うように直した。

**受入基準 5 の確認方法が不十分だったのが原因である。**
PR 1 では HTTP クライアントで API を叩き、フロントは HTML を取得しただけだった。
**CORS はブラウザだけが強制する仕組みなので、その確認では原理的に検出できない。**
PR 2 では実際のブラウザでログイン → 受注一覧 → 発注 → 配送まで確認した。

### 起票時の想定から変えたこと

- **Terraform の差分確認は GitHub Actions に置かない**（**ADR-0031**）。
  ADR-0028 はワークフローを 3 つとしていたが、差分確認は state と
  Secret Manager の読み取りを要求し、それは ADR-0027 が
  「DB パスワードを見られる権限と等しい」と定めたものだった。
  CI で行うのは `fmt` と `validate` のまま（資格情報が要らない）
- **`deploy-prod.yml` は作らない。** 本番のリソースも連携設定もまだ存在せず、
  実行すれば必ず失敗するワークフローになる。反映手順の本体は
  `deploy.yml` に切り出してあるので、REQ-0054 では呼び出し側を 1 つ足すだけでよい

- **GCS のライフサイクルは、ステージングでのみ現行オブジェクトを消す。**
  設計書は本番 180 日 / ステージング 30 日としていたが、本番で現行オブジェクトを
  消すと DB に残った `file_path` が参照切れになる。本番の保持方針は REQ-0054 で決める
- **Cloud SQL の `max_connections` を明示的に固定する。**
  ティアごとの既定値はメモリ量から算出されるため、値を仮定して接続プールを設計できない

### 実測値（PR 1 時点、ステージング）

| 項目 | 値 | 備考 |
|---|---|---|
| Cloud SQL `max_connections` | **25** | `db-f1-micro` の既定。`SHOW max_connections` で実測 |
| API のコールドスタート | **約 15 秒** | うち約 9 秒が `uv run` の依存再取得（REQ-0057 で起票） |
| API URL | `https://pod-admin-api-kkwi54ngsq-an.a.run.app` | |
| 管理画面 URL | `https://pod-admin-web-kkwi54ngsq-an.a.run.app` | |

**設計書 7.1 の `DATABASE_URL`（Unix ソケット）は実地で検証済み。**
`?host=/cloudsql/PROJECT:REGION:INSTANCE` はコロンを含むが、SQLAlchemy に
multihost 構文として誤解釈されず、`host='/cloudsql/...'` として asyncpg に渡る。
migrate Job が `alembic upgrade head` を完走し、15 テーブルが作られた。

### 実測値（PR 2 時点、ステージング）

自動デプロイの実地確認は GitHub Actions の
[run #33133642742](https://github.com/Raiku-Setoyama/pod-admin/actions/runs/33133642742) で行った。
`push` 契機で全ステップが成功し、4 つのワークロードすべてが対象コミットの
イメージ（`...:f628b460...`）で動いていることを確認した。

| 項目 | 結果 |
|---|---|
| Workload Identity 連携での認証 | 成功（鍵 JSON なし） |
| イメージの build → push → migrate → api → web → worker | 全ステップ成功 |
| デプロイ後の `terraform plan -detailed-exitcode` | 差分なし（ADR-0030 の `ignore_changes` が効いている） |

**`main` 以外からは借りられないことも実地で確かめた。** 同じブランチから push した
[run #33144118596](https://github.com/Raiku-Setoyama/pod-admin/actions/runs/33144118596) は
最初の認証ステップで止まる。

```
google-github-actions/auth failed with:
  {"error":"unauthorized_client",
   "error_description":"The given credential is rejected by the attribute condition."}
```

GCP 側の IAM 条件で落ちているので、**ワークフローの定義を書き換えても回避できない**（ADR-0031）。

所要時間はレイヤーキャッシュ（`docker/build-push-action` の `type=gha`）を
入れる前後で次のとおり。**2 回目以降は 2 分台で反映される。**

| | キャッシュ無し | キャッシュ有効（2 回目以降） |
|---|---|---|
| API のイメージ | 47 秒 | **11 秒** |
| 管理画面のイメージ | 70 秒 | **9 秒** |
| ジョブ全体 | 4 分 14 秒 | **2 分 15 秒** |

業務シナリオの疎通確認は 16 項目中 15 項目が通った。

| シナリオ | 結果 |
|---|---|
| ログイン（管理者 / 製造委託先ポータル） | OK |
| 外部連携 API v1（受注登録） | OK |
| 外部連携 API v2（受注登録・製造データが `pending` で待ち行列に入る） | OK |
| 外部連携 API の API キー認証（誤った鍵を 401 で拒否） | OK |
| 受注一覧 | OK |
| 発注（ステータス更新・発注サマリー） | OK |
| 配送（納品完了で出荷が自動作成される・配送一覧） | OK |
| **請求書PDF** | **NG（BUG-0002）** |
| チャット（送信・履歴） | OK |
| 管理画面の表示 | OK |

**上の表は HTTP クライアント（`httpx`）での確認である。**
これに加えて、**実際のブラウザで**新旧どちらの URL からもログインでき、
受注一覧・発注一覧・配送一覧が表示されることを確認した
（CORS はブラウザだけが強制するので、この確認は別に要る）。

設計の詳細は `docs/superpowers/specs/2026-08-27-gcp-migration-design.md`。
