## 内容

本格運用に向けて、インフラを**コードで管理できる状態**にしたい。手作業でコンソールを触って
作った環境は、何がどう設定されているか誰にも分からなくなり、同じものをもう一度作れない。

そのうえで、**本番と同じ形のステージング環境**を先に作る。本番を触る前に、そこで動作確認を取る。

ステージングには移行するデータが無いので、まっさらな状態から立ち上げる。

## 背景・理由

現在、API は Railway、フロントは Vercel でホスティングされており、設定はそれぞれの管理画面に
散らばっている。ステージング環境は存在しない。**本番でしか動作確認ができない状態**である。

GCP プロジェクトは会社組織 `tosyoworkspace.tokyo` の下に 2 つ用意されている
（本番 `tosyo-api-504104` / ステージング `tosyo-api-stg`）が、いずれもリソースは未構築である。

## 詳細

### 構成

Terraform のコードを `infra/` に置き、共通モジュールと環境ごとの薄い定義に分ける。
state は環境ごとに別の Cloud Storage バケットへ保存する（ADR-0027）。

デプロイは GitHub Actions から行う。認証には Workload Identity 連携を使い、
**サービスアカウントの鍵 JSON をリポジトリに置かない**（ADR-0028）。

構築するもの（ADR-0026）:

- Cloud Run（API / フロント）
- Cloud Run Job（マイグレーション / 製造データ生成ワーカー）
- Cloud SQL（PostgreSQL 16）
- Cloud Storage（ファイル保管）
- Secret Manager（機密情報）
- Artifact Registry（コンテナイメージ）
- Cloud Scheduler（ワーカーの定期起動）

### 前提

**着手前に、両 GCP プロジェクトへの IAM 権限の付与が必要である。**
現在の作業者は `roles/editor` であり、`resourcemanager.projects.setIamPolicy` /
`iam.workloadIdentityPools.create` / `run.services.setIamPolicy` /
`iam.serviceAccounts.setIamPolicy` を持たない。これが無いと `terraform apply` は必ず失敗する。

### 例外・エッジケース

- ステージングの製造データ生成は、外部 VM を本番と共有すると本番のジョブ待ち行列に混ざるため、
  当面は無効にしておく（外部 VM の移送後に繋ぎ直す。REQ-0055）
- ステージングの DB は最小構成のため同時接続数の上限が小さい。API の最大インスタンス数と
  接続プールのサイズを、その上限に収まるよう設定する

## 受入基準

- [ ] `infra/` に Terraform のコードがあり、ステージング環境の `terraform apply` が完走する
- [ ] 同じ状態で `terraform plan` を再実行したとき、差分が出ない
- [ ] Terraform の state がバージョニング有効の Cloud Storage バケットに保存されている
- [ ] ステージングの API が公開 URL で `/health` に 200 を返す
- [ ] ステージングのフロントが公開 URL で表示され、そこから API を呼べる
- [ ] API が Cloud SQL に接続し、受注一覧を取得できる
- [ ] マイグレーション用の Job が `alembic upgrade head` を完走する
- [ ] アップロードしたファイルがステージング専用の Cloud Storage バケットに保存され、
      画面からダウンロードできる
- [ ] 機密情報（JWT 署名鍵・DB パスワード・SendGrid APIキー・内部シークレット）が
      Secret Manager から注入され、鍵 JSON をリポジトリにも環境変数にも置いていない
- [ ] GitHub Actions が鍵 JSON なしで GCP に認証し、`main` へのマージでステージングへ
      自動デプロイされる
- [ ] ログイン・受注一覧・発注・配送・請求書PDF・外部連携API(v1/v2)・チャットが
      ステージング上で動作する

## スコープ外

- 本番環境の構築とデータ移行（REQ-0054）
- 外部 VM（illustrator-vm）の移送（REQ-0055）
- 監視・アラートの本格整備
- 独自ドメインの割り当て（当面は発行される URL をそのまま使う）
- 予算アラートの設定（請求先アカウントの権限が必要なため、プロジェクト所有者の作業）

## 実装メモ

実装の都合で PR を分ける場合の想定:

1. Terraform の基盤（state バケット・API 有効化・サービスアカウント・Artifact Registry）
2. データ層（Cloud SQL・Cloud Storage・Secret Manager）
3. 実行層（Cloud Run・Cloud Run Job・Cloud Scheduler）
4. CI/CD（Workload Identity 連携・デプロイ用ワークフロー）

いずれの中間状態でも `main` は壊れない（既存の Railway / Vercel 運用に影響しないため）。
受入基準はすべて埋まった最後の PR で `done` にする。

設計の詳細は `docs/superpowers/specs/2026-08-27-gcp-migration-design.md`。
