## 内容

製造データを生成している Windows の仮想マシン（illustrator-vm）を、**会社組織の GCP プロジェクトへ移す。**
いまは個人の Google アカウント配下にあり、費用も会社とは別の請求先に乗っている。

あわせて、**この VM の API がインターネットから誰でも叩ける状態を解消する。**

## 背景・理由

### 会社組織の外にある

`docs/00-charter/constraints.md` は illustrator-vm を「既存システムとの連携」先として記録しているが、
実体は**プロジェクトオーナー個人の Google アカウント配下**（プロジェクト `lively-transit-334610`、
請求先 `01AB65-…`、会社の請求先とは別）にある。

本番の製造データ生成という業務の根幹が個人アカウントに依存しており、
アカウントの状態しだいで業務が止まる。費用も会社の会計に乗っていない。

### 認証なしで公開されている（2026-08-27 に実測で確認）

同プロジェクトのファイアウォールに、送信元 `0.0.0.0/0` から tcp:8000 を許可する規則があり、
**適用先のタグが指定されていない**（＝ネットワーク内の全インスタンスに効く）。

外部から実際に到達することを確認した。

```
http://34.84.121.166:8000/      → HTTP 200
http://34.84.121.166:8000/docs  → HTTP 200
```

`api/app/services/illustrator_vm_client.py` の冒頭にも「認証なし / CORS * /
既定 127.0.0.1:8000（**プライベートVM前提**）」と書かれている。**前提が満たされていない。**

結果として、第三者が次のことをできる状態にある。

- 製造ジョブを自由に投入する（VM は 1 件ずつ直列処理のため、本番の生成を待たせられる）
- 他者の生成結果をダウンロードする（デザインデータが読める）

なお VM に送信しているのは商品種別・サイズ・注文ID・デザイン画像であり、
**顧客の氏名・住所・電話番号・メールアドレスは含まれない**（`app/utils/mfg_product_mapping.py`
および `illustrator_vm_client.submit` で確認）。個人情報の漏えいには当たらない。

加えて、リモートデスクトップ（3389）と SSH（22）も送信元 `0.0.0.0/0` で開いている。

### なぜ不具合ではなく要件か

**違反していると引用できる受入基準が無い。** `nfr.md` のセキュリティ節が定めているのは
pod-admin 自身の認証方式であり、`constraints.md` はむしろ illustrator-vm の認証を
「任意ヘッダ」と現状のまま記録している。同じ形の指摘（本番で認証なしに公開されている
デバッグ用エンドポイント）も REQ-0040 という要件として起票されている。
`AGENTS.md`「不具合か、仕様変更か」の判定に従い、**新しい約束＝要件**として扱う。

## 詳細

### 業務フロー

1. 現行 VM のマシンイメージを作成する
2. そのイメージを会社組織のプロジェクトから読めるよう権限を渡す
3. 会社組織側にネットワークを用意する
4. イメージから**外部IPを付けずに** VM を起動する
5. Adobe Illustrator のライセンス認証が引き継がれているかを確認する
6. API とワーカーの接続先を、新しい VM の内部アドレスに切り替える
7. 動作を確認したうえで、旧 VM を停止し、削除する

### 例外・エッジケース

- **Adobe のライセンス認証がハードウェアに紐づいている場合、移送先で通らない可能性がある。**
  通らなければ、新しい VM に Illustrator を再インストールする
- **旧 VM は、移送先での生成成功を確認するまで削除しない**
- ステージングからこの VM を使えるようにするかは、移送後に別途判断する

## 受入基準

- [ ] 製造データ生成 VM が会社組織の GCP プロジェクト配下で稼働している
- [ ] 移送後の VM に外部 IP が付いていない
- [ ] `http://34.84.121.166:8000/` に外部から到達できない
- [ ] インターネットから、認証なしで製造データ生成 API を呼び出せない
- [ ] リモートデスクトップと SSH が、送信元を限定せずに開いている状態ではない
- [ ] 本番の API とワーカーから新しい VM を呼び出し、製造データの生成が成功する
- [ ] 個人アカウントのプロジェクトに、POD Admin が稼働のために依存する資産が残っていない
- [ ] VM とネットワークが Terraform で管理されており、`terraform plan` の差分が出ない
- [ ] `docs/00-charter/constraints.md` の記述が実態と一致している

## スコープ外

- 製造データ生成そのものの機能変更（REQ-0020 の範囲）
- ステージングから製造データ生成を利用できるようにすること（移送後に別途判断）

## 実装メモ

手順の骨格は `docs/superpowers/specs/2026-08-27-gcp-migration-design.md` の「フェーズ 5」。
**ただし設計書に無い必須要素が 2 つある**（下記「設計書に足りていなかったもの」）。

### PR の分け方

| # | 内容 | 満たす受入基準 | 状態 |
|---|---|---|---|
| 1 | ネットワークの先行構築（`modules/network/`・VPC・サブネット 2 つ・FW 2 本・API 有効化） | — | 着手中 |
| 2 | Cloud NAT・イメージ移送・新 VM の作成・接続先の切替・旧 VM の停止 | 1〜6, 8, 9 | 未着手 |
| 3 | 旧 VM とディスク・静的 IP・旧 FW 規則の削除 | 7 | 未着手 |

**PR 1 は追加しかしない。** VM も Cloud Run も触らないので、**切り戻す対象が無い**
（REQ-0054 の PR 1 と同じ性質である）。

**PR 3 を分けるのは依頼者の判断による**（2026-09-02）。移送後すぐには削除せず、
数日運用してから消す。受入基準 7 だけが PR 3 まで残るので、PR 2 の時点では
`in-progress` のままにする。

### メンテナンス枠は要らない

起票時は「本番の製造データ生成を止めるため、メンテナンス枠を取る」と書いたが、
**止める必要は無い。** ワーカーの Cloud Scheduler を止めておけば、
`manufacturing_data` の行は `pending` のまま待つだけで、**失敗にはならない**。
受注そのものは Cloud Run が受け続ける。

止まるのは「生成が終わるまでの時間」だけであり、それも 2 回に分かれる。

| | 生成が待つ時間 | 何をしているか |
|---|---|---|
| 段階 2 | 20〜30 分 | 旧 VM を停止してイメージを作り、**すぐ起動し直す** |
| 段階 4 | 10〜15 分 | Cloud Run の接続先を内部 IP へ張り替え、実データで 1 件通す |

**段階 3（新 VM の起動・Adobe の認証確認）は無停止である。**
旧 VM が本番を捌き続けている横で新 VM を検証するので、
Adobe の再サインインや再インストールに時間がかかっても本番は動く。
ADR-0035 でカットオーバーに使ったのと同じ形である。

### 設計書に足りていなかったもの

設計書のフェーズ 5 は **Cloud NAT**（外部 IP を外した VM の下り）と
**IAP TCP forwarding**（外部 IP が無い VM に入る唯一の経路）に触れていない。
どちらも外部 IP を外す以上は必須である。
**理由の正本は `infra/modules/network/main.tf` のコメントと `infra/README.md`。**

**Cloud NAT は PR 1 に入れず、PR 2 に回した。**
外部 IP を持たない VM の下りには必須だが、**NAT ゲートウェイは VM が 1 台も無くても課金される。**
PR 1 の狙い（当日その場で組み立てる作業を減らす）は VPC・サブネット・FW・API 有効化で果たせており、
NAT は 20 行・1 分で作れる。**使う相手が居ない期間だけ賃料を払う理由が無い。**

### プロジェクトごと組織へ移す案は使えない

ディスクを作り直さずに済めば Adobe の認証を触らなくてよいが、
**`lively-transit-334610` は POD Admin 専用のプロジェクトではない**（2026-09-02 に実測）。
`bambition` バケット、Cloud Functions、PromePress / RAKUDAA / RKSYO の
Gemini サービスアカウント、BigQuery、Datastore が同居している。
プロジェクトごと移すと、**他事業の資産まで会社組織と会社請求に載る。**

設計書どおり、イメージから VM を作り直す。

### PR 1 の実測（2026-09-02）

| 項目 | 結果 |
|---|---|
| `terraform apply`（本番・初回） | 9 added, 0 changed, 0 destroyed |
| `terraform apply`（本番・レビュー反映後） | **4 added, 0 changed, 6 destroyed**（NAT とルータを PR 2 へ移し、名前を `pod-admin-<役割>` に揃えた） |
| `terraform plan -detailed-exitcode`（本番） | **0**（差分なし） |
| `terraform plan -detailed-exitcode`（ステージング） | **0**（`modules/network` を呼ばないので影響なし） |
| 組織ポリシー | `compute.trustedImageProjects` / `vmExternalIpAccess` / `requireShieldedVm` / `requireOsLogin` / `disableSerialPortAccess` はいずれも**未適用**（2026-09-02 時点）。イメージの持ち込みを止めるものは無い |
| 残ったネットワーク | `pod-admin-vpc` 1 つ。サブネットは `pod-admin-illustrator`（10.20.0.0/24）と `pod-admin-run`（10.20.1.0/24） |
| 残った FW | 2 本のみ。**どちらもタグ `illustrator-vm` で適用先を絞ってある**。`0.0.0.0/0` の規則はプロジェクトに 1 本も無い |

#### compute API を有効にしたら `default` VPC が生えた

**apply の副作用である。** `compute.googleapis.com` を有効にした瞬間に GCP が
`default` VPC を自動生成し、`default-allow-rdp` / `default-allow-ssh`
（ともに `0.0.0.0/0`・適用先の指定なし）が付いてきた。
**この要件が個人プロジェクトで消そうとしているものと、同じ形のものが本番に生まれた。**

VM は `pod-admin-vpc` に置くので実害は無かったが、
**放置すると「このプロジェクトで VM を 1 台作った瞬間に全世界へ RDP が開く」状態が残る。**
空であること（インスタンス 0 / アドレス 0 / 転送ルール 0）を確認したうえで、
FW 4 本と網ごと削除した（依頼者の判断・2026-09-02）。

削除後に残っているのは `pod-admin-vpc` だけで、FW も上記 2 本だけである。
**Terraform では表せない**（自動生成されたものの不在を書けない）ので、
`infra/README.md`「Terraform が管理しないもの」に手順ごと記録した。

### 移送元の実測（2026-09-02）

| 項目 | 値 |
|---|---|
| VM | `illustrator-vm-preview` / `asia-northeast1-a` / `e2-standard-2` |
| OS | Windows Server 2025 Datacenter |
| ディスク | 100GB `pd-ssd`（ブート 1 本のみ） |
| ネットワーク | `default` VPC / 内部 `10.146.0.3` / 外部 `34.84.121.166`（`illustrator-vm-ip` として予約済み） |
| ネットワークタグ | **無し** |
| 生成 API | `GET / → 200`（外部から到達可能）。`/api/process` `/api/status/{job_id}` `/api/download/{job_id}` `/api/products` `/health` |
| イメージ | **まだ 1 つも無い**（machine image / custom image ともに 0 件） |

**ネットワークタグが無いことが、FW を絞れていない直接の原因である。**
`allow-tshirt-api`（0.0.0.0/0 → tcp:8000）も `default-allow-rdp` も `default-allow-ssh` も
適用先が指定されておらず、VPC 内の全インスタンスに効いている。

### PR 2 への申し送り

- **タグを直書きしない。** VM の `tags` は `module.network` の
  `illustrator_target_tag` 出力から渡す。**付け忘れても apply は通り、
  「到達できない」という静かな形でしか表に出ない**（切替の 10〜15 分の枠で見つかるのが最悪）
- **VM の SA ができたら、FW を `target_service_accounts` に切り替えることを検討する。**
  タグは `compute.instances.setTags` があれば誰でも足せるので、
  **無関係な VM に `illustrator-vm` を付ければ tcp:8000 と 3389 が開く。**
  SA なら添付に `iam.serviceAccountUser` が要り、VM は SA 無しでは起動しない
- **Cloud NAT とルータを作る**（PR 1 から移した。上記）
- `modules/stack` は `run_subnet_id`（既定 `null`）を受け取る形にする。ステージングは渡さない
- ネットワーク系のリソースは `labels` を取らないが、**`google_compute_instance` は取る。**
  `local.labels`（`app` / `env` / `managed-by`）を付ける

### イメージは prod にコピーしてから使う

個人プロジェクトのイメージを直接参照して VM を作ると、**そのイメージを消した瞬間に
作り直せなくなる**（`terraform plan` は通るのに `apply` で失敗する状態になる）。
`gcloud compute images create --source-image-project=lively-transit-334610` で
`tosyo-api-504104` 側にコピーし、Terraform はそちらを指す。

コピーは**旧 VM を起動し直したあと**に行う。本番を止めずに済む。
