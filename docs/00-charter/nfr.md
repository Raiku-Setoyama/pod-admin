## 可用性

- 本番は GCP（Cloud Run + Cloud SQL + GCS）。API・管理画面とも Cloud Run のマネージド構成で、
  インスタンス数は 0〜5（REQ-0054）。DB は ZONAL（単一ゾーン。リージョン冗長ではない）。
- DB のバックアップは日次 14 世代 + PITR（本番のみ）。GCS はバージョニング有効で現行オブジェクトを消さない。
- 製造データ生成は、ワーカー（Cloud Run Job）の起動時に取り残しジョブを復旧する（REQ-0052 / ADR-0029。期限切れのリースを `pending` に戻す）。
- **製造データ生成 VM への到達不能は失敗として確定させず、待ち行列へ戻して再試行する**（REQ-0064）。
  再試行の間隔は試行ごとに倍にし、上限（既定 20 回）に達した分だけ `failed` にする。
  `failed` は管理画面「製造データ」から一括で戻せる。
- 製造データ生成 VM のブートディスクは日次スナップショット（14 日保持）で保護する（REQ-0062）。
- メール送信・外部連携の失敗は業務処理（受注登録・DB 更新）を止めない設計（ADR-0014）。

**残っている弱点:**
- メーカー日次ダイジェストの起動が GitHub Actions の定期実行に依存している。
  リポジトリが 60 日間更新されないと自動的に無効化される（ADR-0015）。
- Cloud SQL は ZONAL 構成。ゾーン障害では復旧にバックアップからの復元が要る。

## セキュリティ

- 認証は JWT（HS256）+ bcrypt、ステートレス（ADR-0001）。管理者とメーカーでロール・トークン形状を分離（ADR-0002）。
- 外部連携は `order_sources` 駆動の API キー、内部トリガは共有シークレット（定数時間比較）（ADR-0003）。
- 外部データ取得は SSRF・サイズ超過ガードを通す（ADR-0017）。
- 入力上限: チャット/梱包写真の添付は 10MB、製造データ元画像取得はサイズ上限、受注明細は最大 100 件。
- トークン失効リスト・監査ログは持たない（ステートレス設計。ログアウトはクライアント側のトークン削除）。

**要改善（段階2の発見事項。ADR/要件化して対応方針を決めるべき）:**
- API キーが平文保存（ハッシュ化・ローテーション機構なし）。
- **レート制限を持たない。** 認証は通っている相手（外部販売サイト・管理者）からの
  過大な呼び出しをアプリ側で絞る仕組みが無く、Cloud Run の max_instances が上限になる。

**是正済み:**
- ~~`GET /manufacturer-portal/debug-token` が本番で認証なしに公開されている~~（削除済み。REQ-0040）
- ~~メーカートークン断片が本番ログに出力される~~（削除済み。REQ-0040）

## 保守性

- テスト: pytest（api）/ vitest（web）/ Playwright（E2E）。
  **まだ CI の必須チェックに入っていない**（着手時点で赤いため。REQ-0042）。
- 静的解析: ruff + mypy（api）/ ESLint + tsc（web）。4 つとも CI でブロッキング（REQ-0041）。
- ログは Cloud Logging。Cloud Run では 1 行 1 JSON の構造化ログで出す
  （`api/app/logging_config.py`）。
- 監視は Cloud Monitoring（`infra/modules/monitoring/`）。
  外形監視 1 本と、アラート 5 本（VM に届いていない / 生成が失敗している /
  ワーカーが異常終了 / API が 5xx / API が応答しない）。宛先はメール。
  **通知先が未設定ならアラートは作られない**（`terraform output alerting_active` で確認できる）。
