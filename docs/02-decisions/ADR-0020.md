## 背景

外部販売サイト連携の API キーは `order_sources.api_key` に**平文で保存**されており、ハッシュ化・ローテーションの機構がない（段階2のコード精査で判明）。DB やバックアップの流出時にキーがそのまま漏れる。REQ-0036（受注元の管理画面・APIキー発行）を実装する際、キーの保存方式を先に決める必要がある。

## 検討した選択肢

### 選択肢 A: ハッシュ化して保存し、再発行（ローテーション）機構を整える

- 利点: 流出時もキー原本が漏れない。発行・失効・再発行を運用手段として持てる。
- 欠点: 実装コストが増える（照合方式の変更、既存キーの移行が必要）。

### 選択肢 B: 平文保存を継続する（リスクを受容）

- 利点: 追加実装が不要。
- 欠点: 流出時にキーがそのまま使われる。ローテーション手段がない。

**弊社推奨**: A（受注元管理を実装するなら、発行・失効まで含めて設計する価値が高い）。

## 判断が出ないと止まるもの

## 影響

- コードベース: `api/app/models/order_source.py`（api_key 列）、`api/app/dependencies.py`（`verify_api_key` の照合）、受注元管理の新規実装（REQ-0036）。

## 見直しの条件
