## 背景
利用者ログイン（JWT）とは別に、外部販売サイトなどからのAPI連携リクエストと、システム内部の処理をトリガーするリクエストを、それぞれどう認証するかを決める必要があった。決定時期は不明（既存実装から逆算し 2026-08-06 に記録）。

## 検討した選択肢
### 選択肢 A: 外部連携は DB 駆動（order_sources）の API キー、内部トリガは共有シークレット（定数時間比較）で認証する
- 利点:
  - 外部連携先ごとに API キーを DB（order_sources）で管理でき、連携元の識別・追加・失効を運用で扱える
  - 内部トリガは単一の共有シークレット（X-Internal-Secret）で単純に保護でき、定数時間比較でタイミング攻撃に配慮できる
  - 利用者ログイン（JWT）とは独立した経路として役割が明確になる
- 欠点:
  - API キーと内部シークレットという2種類の資格情報を運用・管理する必要がある
  - 内部シークレットは共有秘密のため、漏えい時の影響範囲が広い
### 選択肢 B: 外部連携・内部トリガも含めてすべて JWT（利用者トークン）で認証する
- 利点:
  - 認証方式を JWT に一本化でき、仕組みが統一される
- 欠点:
  - 外部連携先や内部処理に人間の利用者アカウントを割り当てる必要が生じ、実態に合わない
  - 連携元ごとの識別（order_sources 相当）や内部トリガの単純な保護を、利用者トークンで表現するのは不自然

**弊社推奨**: A

## 判断が出ないと止まるもの
なし

## 決定
選択肢 A を採用する（現行実装）。外部連携リクエストは HTTP ヘッダ `X-API-Key` に付与された API キーを DB（order_sources）駆動で検証し（verify_api_key）、内部処理トリガは HTTP ヘッダ `X-Internal-Secret` に付与された共有シークレットを定数時間比較で検証する（verify_internal_secret）。

## 理由
外部連携先ごとに API キーを DB（order_sources）で管理すれば、連携元の識別と鍵の追加・失効を運用で扱える。内部トリガは共有シークレットによる単純な保護で足り、定数時間比較によりタイミング攻撃に配慮できる。いずれも利用者ログイン（JWT）とは目的が異なる経路であり、独立した認証手段とすることで役割が明確になる。将来この決定を見直す人は、外部連携と内部トリガが利用者認証とは別経路で保護されている前提を理解しておく必要がある。

## 影響
- コードベース: 外部連携API は `X-API-Key` を verify_api_key で検証し、内部トリガは `X-Internal-Secret` を verify_internal_secret（定数時間比較）で検証する経路を備える
- 運用: API キー（order_sources 上で管理）と内部共有シークレットの2種類の資格情報を管理・ローテーションする必要がある
- この決定によって不可能になること: 外部連携先・内部トリガを利用者アカウント（JWT）の権限体系だけで一元管理することはできない

## 見直しの条件
共有シークレット方式では内部トリガの保護・監査が不十分になった場合、外部連携の鍵管理を order_sources とは別の仕組みに移す必要が生じた場合、または認証手段の統一が運用上必要になった場合に再検討する。
