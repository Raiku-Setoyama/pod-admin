## 背景
請求書などの帳票PDFの生成手段、顧客・製造委託先へのメール送信手段、およびCSVの出力・取り込みの文字コード方針を決める必要があった。日本語を含む帳票の整形、外部メールサービス障害時の業務継続、Excelでの文字化け回避、取引先から届くファイルの文字コードのばらつきへの対応が論点となった。決定時期は不明（既存実装から逆算し 2026-08-06 に記録）。

## 検討した選択肢
### 選択肢 A: WeasyPrint+SendGrid+BOM付CSV（現行）
- 利点:
  - 帳票はWeasyPrint＋Jinja2でHTML/CSSベースに整形でき、日本語・レイアウト調整がしやすい
  - メールはSendGridで送信でき、同期SDKを別スレッド（asyncio.to_thread）に逃がしつつ、送信失敗は例外を握りつぶしてbool返却するため業務処理（DB確定など）が止まらない
  - CSV出力はUTF-8のBOM付きでExcelでの文字化けを防ぎ、取り込みはShift-JISも自動判定（chardet）するため取引先由来のファイルにも対応できる
- 欠点:
  - WeasyPrint はフォントなどの外部依存があり、メール送信は SendGrid のAPIキー・サービス稼働に依存する
  - メール失敗を握りつぶすため、送信漏れは呼び出し側で失敗件数を表示するなど別途可視化が必要になる
### 選択肢 B: 代替（別PDF/メール手段）
- 利点:
  - 別のPDF生成（例: ヘッドレスブラウザ）やメール手段（例: SMTP直送）に置き換える余地がある
  - 送信失敗時に即時エラーとして扱う設計も選べる
- 欠点:
  - 日本語帳票の整形やExcel互換のCSV出力を同水準で満たすには追加の作り込みが必要
  - メール失敗を即時エラーにすると、外部サービス障害時に発送確定などの業務処理まで巻き込んで止まる

**弊社推奨**: A

## 判断が出ないと止まるもの
なし

## 決定
選択肢 A を採用する（現行実装）。帳票PDFは WeasyPrint＋Jinja2 で生成し、メールは SendGrid（同期SDKを asyncio.to_thread、送信失敗は例外を握りつぶして bool 返却）で送信し、CSV は Excel 互換の BOM 付きで出力し、取り込みは Shift-JIS も自動判定する。

## 理由
日本語を含む請求書などの帳票を HTML/CSS ベースで柔軟に整形でき、CSV は Excel での文字化けを避けつつ取引先由来の Shift-JIS ファイルも取り込める。メール送信は外部サービス障害があっても業務処理（伝票インポートによる発送確定など）を止めないことを優先し、失敗を握りつぶして bool を返す方針とした。送信漏れは呼び出し側で失敗件数を表示するなどして可視化する前提とする。

## 影響
- コードベース: 帳票生成は WeasyPrint＋Jinja2 テンプレートに集約する。メール送信は非同期化（asyncio.to_thread）した SendGrid 呼び出しで、失敗時は例外を投げず bool を返す。CSV 出力は UTF-8 BOM 付き、取り込みは chardet による文字コード自動判定を通す。
- 運用: WeasyPrint のフォント、SendGrid の API キー、jpholiday などの外部依存の可用性を前提とする。メール送信失敗はエラーとして即時に露出しないため、送信結果は呼び出し側の集計・表示で確認する。
- この決定によって不可能になること: メール送信の失敗を業務処理のエラーとして即座に止めることはできない（発送確定などは維持される）。

## 見直しの条件
メール送信失敗を確実にエラーとして扱い業務処理を止めたくなった場合、WeasyPrint／SendGrid の外部依存が運用上のボトルネックになった場合、または CSV の文字コード方針（BOM付き出力・Shift-JIS自動判定）が要件に合わなくなった場合に再検討する。
