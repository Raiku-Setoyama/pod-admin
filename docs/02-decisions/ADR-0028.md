## 背景

GCP へコンテナイメージを配置し、実行基盤へ反映する経路を決める。

このリポジトリでは既に GitHub Actions で静的解析を実行している
（`.github/workflows/ci.yml`、REQ-0041）。デプロイをどこで動かすかによって、
「Pull Request との紐づけ」と「認証情報の持ち方」が変わる。

とくに認証情報は重要である。**サービスアカウントの鍵ファイルは、一度漏れると
失効させるまで有効な資格情報になる。**

## 検討した選択肢

### 選択肢 A: GitHub Actions ＋ Workload Identity 連携

- 利点: 静的解析と同じ場所で動くため、Pull Request との対応が 1 か所で追える
- 利点: **鍵ファイルを持たない。**GitHub が発行する短命なトークンを GCP 側で検証して
  権限を渡す方式のため、リポジトリに長期有効な資格情報を置かずに済む
- 利点: 本番への反映に人間の承認を挟む仕組みを、既存の機能で足せる
- 欠点: 連携の設定に、プロジェクトの権限管理の操作が必要になる

### 選択肢 B: GCP 側のビルドサービスを使う

- 利点: GCP 内で完結する
- 欠点: **静的解析（GitHub Actions）とビルドが 2 系統に分かれる。**
  どの Pull Request がどのビルドに対応するかが追いにくくなる

### 選択肢 C: 当面は手元からコマンドで反映する

- 利点: 最短で始められる
- 欠点: 誰がいつ何を反映したかが残らない。本格運用の前提に合わない

**弊社推奨**: A

## 決定

**選択肢 A を採用する。**

- Workload Identity 連携で認証する。**サービスアカウントの鍵ファイルは作らない**
- 連携の設定には、**このリポジトリからの要求だけを受け付ける条件を必ず付ける**
- ワークフローは 3 つに分ける

| ワークフロー | 契機 |
|---|---|
| Terraform の差分確認 | Pull Request |
| ステージングへの反映 | `main` へのマージ |
| 本番への反映 | **手動実行（人間の承認を挟む）** |

反映の順序は「マイグレーション用ジョブの実行 → API とフロントの反映」とする。

## 理由

静的解析が既に GitHub Actions にある以上、ビルドと反映を別の場所へ置く理由がない。
1 つの Pull Request に対して、検査・ビルド・反映が同じ画面で追える。

鍵ファイルを作らない点が決定的である。鍵ファイルは GitHub のシークレットに保存しても、
**漏えいしたときに「いつ・どこから使われたか」を追えない。**
Workload Identity 連携は要求のたびに短命なトークンを発行するため、この問題が構造的に起きない。

**連携にリポジトリの条件を付けないと、任意の GitHub リポジトリから同じサービスアカウントを
使えてしまう。**設定漏れが致命的になるため、決定として明記する。

本番への反映を手動実行にするのは、`AGENTS.md` の「人間が判断を行う」という原則に合わせるためである。

## 影響

### コードベースへの影響

- `.github/workflows/` にワークフローが 3 つ増える
- 連携の設定は Terraform の管理対象に含める（ADR-0027 の構成に置く）

### 運用への影響

- 本番への反映には手動の操作が要る。自動では反映されない
- 連携の設定には、プロジェクトの権限管理の操作権限が必要になる。
  現在の作業者の権限では設定できないため、**権限の付与が着手の前提になる**（REQ-0053）

### この決定によって不可能になること

- 手元から直接デプロイする運用は、緊急時を除いて行わない

## 見直しの条件

- GitHub Actions の実行時間が費用として無視できなくなったとき
- ビルドに GCP 内部のリソースへの接続が必要になったとき
