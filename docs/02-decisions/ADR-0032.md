## 背景

設計書（`docs/superpowers/specs/2026-08-27-gcp-migration-design.md` の 5.3）は、
本番の Cloud Storage バケットに **180 日のライフサイクル**を設定すると書いている。
コストの見積もり（同 10.1、GCS 〜¥3,717/月）もその前提で作られている。

一方、その後 REQ-0053 で実装した `infra/modules/gcs` は、現行オブジェクトを消す
`retention_days` について次のように書いている。

> **使い捨て環境専用。** 本番で設定すると業務ファイルの実体が消え、
> DB に残った file_path が参照切れになる。

**設計書とコードが食い違っている。** 本番環境を作るにあたって、どちらかに決める必要がある。

## 決定

**本番では現行オブジェクトのライフサイクル削除を設定しない**（`gcs_retention_days = null`）。
旧バージョンの掃除（`noncurrent_retention_days = 7`）だけを残す。

設計書 5.3 の「180 日ライフサイクル」は、この ADR で置き換える。

## 理由

このバケットに入るのは、製造データ・請求書 PDF・チャットの添付ファイルである。
**いずれも参照期限が読めない。**

- 請求書は会計の証憑であり、**法定の保存期間は 7 年**である。180 日で消える
- 製造データは同じ商品の再発注で作り直しになる。キャッシュの意味が消える
- チャットの添付は、過去のやり取りを遡ったときに参照される

そして消えたときの壊れ方が悪い。**アプリはファイルが消えたことを知らない。**
`file_path` は DB に残り続けるので、一覧には項目が並び、開いた瞬間に落ちる。
**利用者から見ると「昔のデータが壊れている」であって、「保存期間を過ぎた」ではない。**

見積もりへの影響は無視できる。**実測 30MB** であり、1TB を前提にした
¥3,717/月 という見積もりは上限として置いたものである。**削除しても浮く額が無い。**

保存期間を定める必要が出たときは、日数ではなく**業務の状態**（受注が完了して N 年、など）
で決めるべきものである。バケットのライフサイクルはその条件を表現できない。

## 影響

- 本番の GCS 費用は保存量に比例して増え続ける。**現状 30MB なので当面は問題にならない**が、
  製造データの生成が本格稼働すると増える。実測を見て、必要になった時点で
  アーカイブクラスへの移行ルール（削除ではなく）を検討する
- ステージングは従来どおり 30 日で消す。使い捨て環境であり、参照切れが起きても業務に影響しない
