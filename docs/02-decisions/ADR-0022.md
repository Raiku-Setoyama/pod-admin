## 背景

REQ-0046 は「RKSYO が決済時に判定した配送区分（メール便／宅急便）を TOSYO の管理画面に表示する」という要望である。表示そのものは難しくないが、**その値が TOSYO にどうやって届くのか**が決まっていない。

現状を確認した結果は次のとおりである。

- `Order` / `OrderItem`（`api/app/models/order.py`）に配送区分に相当するカラムは無い。
- `Shipment.carrier`（`api/app/models/shipment.py:36`）は配送 CSV 取り込み時に入る運送会社名であり、決済時の配送区分とは別物である。
- 受注は外部連携 API（`POST /api/v1/orders` = REQ-0010、`POST /api/v2/orders` = REQ-0011）経由で RKSYO から入ってくる。現在の受注取込のリクエストに配送区分は含まれていない。

つまり **TOSYO 側だけでは完結せず、RKSYO 側の改修を伴う可能性がある**。誰がいつ何を直すかに関わるため、弊社では決められない。

## 検討した選択肢

### 論点 1: 値の入手経路

#### 選択肢 A: 受注取込 API に配送区分の項目を追加し、RKSYO が決済時の判定結果を送る

- 利点: RKSYO の判定結果がそのまま TOSYO に入るので、定義上、差異が発生しない。REQ-0046 の目的（請求金額・案内の齟齬をなくす）を直接満たす。
- 利点: 受注 1 件ごとに値が確定するタイミング（決済時）と、値が届くタイミング（受注取込）が一致する。
- 欠点: RKSYO 側の送信処理の改修が必要で、TOSYO 単独では完結しない。
- 欠点: この対応より前の受注には値が入らない（空欄になる）。

#### 選択肢 B: TOSYO 側で同じ判定ロジックを実装して算出する

- 利点: TOSYO 単独で完結する。過去の受注にも遡って値を出せる。
- 欠点: **判定が 2 か所に存在することになり、REQ-0046 が解こうとしている「差異が起きる」問題をそのまま作り込む。** RKSYO 側でロジックが変わるたびに追随が必要になる。
- 欠点: 判定に必要な情報（送料設定・購入者の選択など）が TOSYO 側に揃っている保証がない。

#### 選択肢 C: 配送区分を別経路（CSV 取り込み・管理画面からの手入力）で入れる

- 利点: API を変えずに始められる。
- 欠点: 手作業が増え、入力漏れ・誤りという新しい齟齬の原因になる。要望の趣旨に反する。

**弊社推奨**: A（判定を 1 か所に保つことが要望そのものであり、B・C は差異の発生源を残す）

### 論点 2: 値の語彙と保存形式

#### 選択肢 A: 決められた値のみを受け付ける（例: `mail` / `courier` の 2 値）

- 利点: 表記ゆれが入らない。絞り込みや集計に使える。表示名（「メール便」「宅急便」）は TOSYO 側で持てる。
- 欠点: RKSYO 側で区分が増えたとき、TOSYO 側の改修とリリース調整が必要になる。

#### 選択肢 B: 文字列をそのまま受け取って表示する

- 利点: RKSYO 側で区分が増えても TOSYO の改修が要らない。
- 欠点: 表記ゆれ（「宅急便」「宅配便」など）が管理画面にそのまま出る。将来この値で絞り込みたくなったときに使えない。

**弊社推奨**: A（今回の目的が「両者の認識を一致させること」なので、値が一致していることを機械的に保証できる形にしたい）

論点 1 で B・C を採る場合も、語彙の決定は同じく必要である。

## 判断が出ないと止まるもの

- REQ-0046 の着手そのもの。入手経路が決まらないと、何を表示するのかが定まらない。
- 選択肢 A を採る場合、RKSYO 側の改修の可否と時期。TOSYO 側の実装だけ先に入れても値は入ってこない。
- この対応より前の受注（配送区分を持たない受注）の扱い。空欄でよいか、遡って埋めるかたを用意するか。

## 影響

- 論点 1 で A を採る場合、外部連携 API のリクエスト仕様（`openapi/schema.yaml`）と受注テーブルにフィールドが増える。RKSYO 側との同時リリース調整が必要になる。
- 論点 1 で B を採る場合、配送区分の判定ロジックが TOSYO の保守対象になり、RKSYO 側の変更に追随し続ける義務が発生する。
- 論点 2 で A を採る場合、区分が増えるたびに TOSYO 側の改修が必要になる。B を採る場合、この値による絞り込み・集計は将来にわたって諦めることになる。

## 見直しの条件

- RKSYO 側で配送区分の種類が増えた、または判定のタイミングが決済時から変わったとき。
- 配送区分を表示だけでなく、請求金額の突合や配送業者向け CSV に使いたくなったとき（正確さの要求が上がるため、論点 2 の判断が変わりうる）。
