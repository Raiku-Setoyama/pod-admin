## 背景
管理画面・メーカーポータルの画面遷移（ルート）を、未認証・種別違いの利用者から保護する方式を決める必要があった。あわせて、実効的なアクセス制御をどの層に置くかを決める必要があった。決定時期は不明（既存実装から逆算し 2026-08-06 に記録）。

## 検討した選択肢
### 選択肢 A: クライアント側の認証ガードで画面を保護し、実効的なアクセス制御はバックエンドAPIの依存に集約する
- 利点:
  - 管理画面・メーカーポータルそれぞれに認証ガード（AuthGuard / ManufacturerAuthGuard）を置くだけで画面遷移を制御でき、実装が単純
  - 実効的な認可はバックエンドAPIの依存（get_current_admin など）に集約されるため、UIをすり抜けても保護される
  - フロント・バックで保護ロジックを二重に厳密実装しなくてよい
- 欠点:
  - クライアント側ガードのみでは、画面レンダリング自体をサーバー到達前に止められない
  - 保護の正しさがバックエンドAPI側の依存の網羅性に依存する
### 選択肢 B: Next.js middleware でルート保護を行う
- 利点:
  - サーバー到達前（エッジ）でルート単位の保護をかけられる
  - 保護対象ルートを middleware に一元的に宣言できる
- 欠点:
  - middleware とバックエンドAPIの双方で保護ロジックを持つと二重管理になりうる
  - 実効的な認可は結局バックエンドAPIが担うため、middleware は入口制御にとどまる

**弊社推奨**: A

## 判断が出ないと止まるもの
なし

## 決定
選択肢 A を採用する（現行実装）。ルート保護はクライアント側の認証ガード（AuthGuard / ManufacturerAuthGuard）で行い、Next.js middleware は用いない。実効的なアクセス制御はバックエンドAPIの依存（get_current_admin / get_current_manufacturer など）に集約する。

## 理由
画面遷移の制御はクライアント側ガードで十分に実現でき、実装も単純になる。一方で「本当に守るべき」データ・操作の保護はバックエンドAPIの依存に集約したため、UIをすり抜けてもAPI側で拒否される。middleware を導入すると入口制御が重複し二重管理になりうるため採用しなかった。将来この決定を見直す人は、実効的な認可がバックエンドAPIに集約されている前提を理解しておく必要がある。

## 影響
- コードベース: フロントはルートごとにクライアント側ガードを配置する。バックエンドAPIの各エンドポイントは認証・権限依存を必ず備える必要がある（保護の実効はここに集約）
- 運用: Next.js middleware による入口制御は存在しないため、保護漏れの点検はバックエンドAPIの依存付与の網羅性に対して行う
- この決定によって不可能になること: サーバー到達前（middleware/エッジ）でのルート遮断はできない。保護をフロント側だけで完結させることはできない（API側の依存が必須）

## 見直しの条件
サーバー到達前のルート遮断が必要になった場合、クライアント側ガードだけでは保護要件を満たせなくなった場合、または保護対象ルートの一元宣言が運用上必要になった場合に再検討する。
