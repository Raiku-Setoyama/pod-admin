## 背景

REQ-0055 で、製造データ生成 VM を置くための VPC・サブネット・ファイアウォールを
**本番にだけ**作る必要が生じた。ステージングは `illustrator_vm_base_url = ""` で
生成機能ごと止めており、繋ぐ先が無い。

ADR-0027 が決めた構成は「`modules/stack/` が構成の本体を持ち、`envs/<env>/` は値だけを持つ」
である。`infra/README.md` はさらに「`modules/stack/` がアプリを知っている唯一の層であり、
その下の `modules/*` は POD Admin のことを何も知らない汎用ラッパーである」と書いている。

新しい `modules/network/` は**汎用ラッパーではない。** タグ `illustrator-vm` と
生成 API のポート 8000 を知っている。置き場を決めないと、この原則が崩れたまま残る。

**もう 1 つ、ステージング固有の事情がある。** このモジュールは
`compute.googleapis.com` を有効化する。**GCP は compute API を有効にした瞬間に
`default` VPC を自動生成し、`0.0.0.0/0` からの RDP と SSH を許可する規則を付けてくる**
（本番で実際に起きた。REQ-0055 の PR 1 で削除した）。
ステージングでこの API を有効にする理由は無く、有効にすれば同じ後始末が要る。

## 検討した選択肢

### 選択肢 A: `envs/prod/main.tf` から `modules/network` を直接呼ぶ

- 利点: ステージングに `compute.googleapis.com` が有効化されない
- 利点: 「本番には VPC があり、ステージングには無い」が env のファイルを見れば分かる
- 利点: `modules/stack` が VPC を持たずに済む。Cloud Run への配線は
  PR 2 で `run_subnet_id`（null 可）という 1 つの入力で表せる
- 欠点: `envs/<env>/` が値だけを持つ、という原則の例外になる
- 欠点: `diff envs/staging/main.tf envs/prod/main.tf` の末尾に、値ではなく構造が出る

### 選択肢 B: `modules/stack` の中に入れ、真偽値のトグルで切り替える

- 利点: 原則を崩さない。呼び出しが 1 か所に集まる
- 欠点: **「この環境に生成 VM は無い」を表す設定が 2 つになる。**
  stack は既に `paused = worker_schedule_paused || illustrator_vm_base_url == ""` を持ち、
  その直上のコメントが「2 つの設定が並んでいるだけでは、片方だけ変えた事故を防げない」と
  書いている。同じ形の事故をもう 1 つ作る
- 欠点: 7 リソースに `count` が付き、出力すべてに `[0]` / `one()` が要る

### 選択肢 C: B と同じだが、トグルを持たず `illustrator_vm_base_url != ""` から導出する

- 利点: 「この環境に生成 VM は無い」の表現が 1 つに保たれる
- 欠点: **`illustrator_vm_base_url` を空にする操作が、VPC ごと（PR 2 以降は VM ごと）
  destroy する操作に化ける。** `infra/README.md` はこの変数を空にすることを
  「生成を止める手段」として案内しており、`envs/prod/main.tf` のコメントも
  「戻すのを忘れても何もエラーにならない」と書いている。**止めるつもりの操作で
  VM が消えるのは、取り返しのつかない事故である**

## 決定

**選択肢 A を採用する。**

`modules/network/` は `envs/prod/main.tf` から直接呼ぶ。ステージングは呼ばない。

あわせて、原則を次のように言い直す。

> **`modules/stack/` は「アプリ 1 環境ぶんの構成」を持つ層である。**
> 環境の一部ではあるが**アプリの構成ではないもの**（ネットワークのような
> プロジェクト単位の土台）は、`envs/<env>/` から直接呼んでよい。
> **ただし、それは stack と並ぶ第 2 の app-aware 層になる。**
> 増やすたびに「値だけを持つ」という env の性質が薄まるので、
> **同じ形のものが 3 つ目になったら、この決定を見直す。**

## 理由

**選択肢 C を落としたことが、この決定の中心である。**
単一の情報源にまとめる利点より、「止めるつもりの操作が消す操作になる」危険のほうが大きい。
Terraform は destroy を静かに plan に混ぜるので、**間違いが操作の直前まで見えない。**

B と A の差は原則の見た目だけで、機械的な安全性はほぼ変わらない。
そこでステージングに `compute.googleapis.com` を持ち込まない A を採った。
**`default` VPC の自動生成は Terraform では表せず、消し忘れを plan が検出できない**
（`infra/README.md`「Terraform が管理しないもの」）。
検出できない後始末を、必要のない環境にまで増やさない。

## 影響

- `infra/envs/prod/main.tf` が `module "stack"` と `module "network"` の 2 つを呼ぶ
- `diff infra/envs/staging/main.tf infra/envs/prod/main.tf` の末尾に構造が現れる。
  **「環境の差分の一覧」という性質自体は保たれる**（本番にだけ VPC がある、という差分である）
- ステージングから生成 VM を使う判断が出た場合（REQ-0055 のスコープ外・ADR-0034）、
  `envs/staging/main.tf` から同じモジュールをそのまま呼べる。**コピーは要らない**
- PR 2 で Cloud Run に Direct VPC egress を付けるとき、`modules/stack` は
  `run_subnet_id`（既定 null）を受け取る。ステージングは渡さない

## 見直しの条件

- `envs/<env>/` から直接呼ぶモジュールが **3 つ目**になったとき。
  そのときは「envs は値だけを持つ」が実態と合っていないので、原則のほうを書き換える
- ステージングにも生成 VM が要るという判断が出たとき。
  両環境が呼ぶなら、`modules/stack` に入れる利点が戻ってくる
