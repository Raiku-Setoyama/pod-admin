## 背景

段階2のコード精査（/adopt-repo）で、本番稼働中に次のデバッグ資産が残っていることが判明した。

- `GET /manufacturer-portal/debug-token` が認証なしで公開され、渡した JWT の payload（`manufacturer_id` の有無など）を返す。`DEBUG` フラグでもガードされていない。
- `get_current_manufacturer` がメーカートークンの先頭断片とデコード済み payload を `logger.info` で常時出力しており、トークン断片が本番ログに残る。

いずれも情報漏えい面につながりうるため、扱いを決める必要がある。

## 検討した選択肢

### 選択肢 A: 両方とも即時に除去する

- 利点: 情報漏えい面を最短で塞げる。デバッグ用途は開発環境で代替できる。
- 欠点: 本番でのトークン調査手段が一時的に失われる（実運用ではほぼ不要）。

### 選択肢 B: `DEBUG` フラグでガードして保持する

- 利点: 開発時のみ有効化でき、調査手段を残せる。
- 欠点: フラグ誤設定のリスクが残る。ログ出力は運用上ほぼ不要で、保持の利点が薄い。

**弊社推奨**: A（本番に情報漏えい面を残す積極的な理由がない）。

## 判断が出ないと止まるもの

- REQ-0040（本番のデバッグ資産の除去）の着手。

## 影響

- コードベース: `api/app/routers/manufacturer_portal.py` の debug-token エンドポイント、`api/app/dependencies.py` のトークンログ出力。

## 見直しの条件

本番でのトークン調査が恒常的に必要になった場合、認証付きの調査手段を別途設計する。
