## 背景

**ADR-0036 が自分で置いた引き金を、REQ-0055 の PR 2 が踏んだ。**

ADR-0036 の「見直しの条件」はこう書いてある。

> `envs/<env>/` から直接呼ぶモジュールが **3 つ目**になったとき。
> そのときは「envs は値だけを持つ」が実態と合っていないので、原則のほうを書き換える。

PR 2 で `modules/illustrator-vm/` を足したことにより、`infra/envs/prod/main.tf` は
`stack` / `network` / `illustrator_vm` の 3 つを呼ぶようになった。**条件は満たされている。**

## 検討した選択肢

### 選択肢 A: 原則のほうを書き換える（ADR-0036 が想定していた対応）

「envs は値だけを持つ」をやめ、複数のモジュールを呼ぶことを正式に認める。

- 利点: 今あるコードを 1 行も動かさずに済む
- 欠点: **数が増えた理由が「増えたから」になる。** 歯止めが無くなる
- 欠点: `diff envs/staging/main.tf envs/prod/main.tf` が環境差分の一覧である、
  という性質がさらに薄まる

### 選択肢 B: `network` と `illustrator-vm` を 1 つのモジュールに統合する

- 利点: **2 つは実際には 1 つの単位である。** 根拠が 3 つある。
  - `illustrator-vm` の必須入力（`subnetwork_id` / `network_tag`）は**両方とも
    `module.network` から来る。** ネットワーク無しでは呼べない
  - Cloud NAT を PR 1 から PR 2 へ送ったのは、**VM が居て初めて意味を持つ**からである。
    ライフサイクルが同じであることを、こちらが既に認めている
  - `internal_ip = "10.20.0.10"` が妥当なのは、それが**他方のモジュールの
    `local` にある CIDR** の中に入っているからである。
    いま env のファイルは、片割れを見られない契約の半分を持っている
- 利点: **ファイアウォールを `target_service_accounts` に切り替えられるようになる。**
  いまは循環になるので選べない（下記）
- 欠点: 適用済みの 9 リソースに `moved` ブロックが要る

### 選択肢 C: いま統合する（PR 2 に含める）

- 欠点: **統合の対象に、40 分前に本番の唯一の生成経路になったばかりの VM が含まれる。**
  得られるのは構造の整合であり、危険が乗るのは**システムで唯一の再現不能資産**である

## 決定

**選択肢 B を採る。ただし実行は REQ-0055 の PR 3 に置く。**

PR 3 は旧プロジェクトの資産（VM・ディスク・静的 IP・ファイアウォール規則）を削除する
PR であり、**そこで扱うものと、この統合が触る境界は同じである。**
`target_service_accounts` への切り替えも同じ PR に入れる。

`state` の移動は `moved` ブロックで宣言的に行う。**この手法はこのリポジトリで
実績がある**（`infra/envs/staging/moved.tf`）。`plan` に `destroy` が 1 件でも出たら
やり直す。

## 理由

**ADR-0036 が指示していたのは「見直せ」であって「原則を書き換えろ」ではない。**
書き換えは、見直した結果として A を選んだときの帰結にすぎない。
実際に見直すと、**増えた 3 つ目は「例外がもう 1 つ要る」ではなく
「2 つ目と 3 つ目が同じものだった」**という話だった。原則は正しく、分け方が誤っていた。

**`target_service_accounts` が選べないことが、境界が誤っている何よりの証拠である。**
ネットワークタグは `compute.instanceAdmin` を持つ者が自分で付けられるので、
VPC 内に紛れ込んだ VM は**自分にタグを付けるだけで IAP → RDP の規則を得られる。**
サービスアカウントなら `iam.serviceAccounts.actAs` が要る。
そちらへ移りたいのに移れないのは、SA を作る `illustrator-vm` が
`network` の出力を消費しており、**逆向きの参照が循環になる**ためである。
統合すれば循環自体が消える。

**いまやらない理由は、価値ではなく順序である。** 本番の生成経路になったばかりの VM を
含む state 移動を、移送を終えたその日に重ねない。

## 影響

- PR 3 で `modules/network/` と `modules/illustrator-vm/` が 1 つになり、
  `infra/envs/prod/main.tf` が呼ぶモジュールは `stack` とそれの 2 つに戻る
- **ADR-0036 は書き換えない。** 引き金は正しく働き、正しく回収された
- 統合後はファイアウォールの適用先をネットワークタグから
  サービスアカウントへ移せる。**タグの付け忘れという静かな失敗は残る**が、
  「他人が自分にタグを付けて入ってくる」経路は塞がる

## 見直しの条件

- PR 3 の `plan` に `destroy` が出て `moved` で消せないとき。
  そのときは統合を諦め、選択肢 A に倒して ADR-0036 を書き換える
- ステージングにも生成 VM が要るという判断が出たとき（ADR-0034）。
  統合したモジュールを両環境が呼ぶだけなので、この決定は影響を受けない
