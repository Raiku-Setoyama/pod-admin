## 背景
決定時期は不明（既存実装から逆算し 2026-08-06 に記録）。製造委託先への日次発注ダイジェストメールを、メーカーごとに設定された送信時刻に沿って1日1回だけ送る仕組みが必要だった。定時実行のトリガーをどこに置き、送ってよいか・二重に送らないかの判定をどこで担保するかを決める必要があった。

## 検討した選択肢
### 選択肢 A: GitHub Actions が高頻度で内部エンドポイントを叩き、送信可否・冪等（原子的な日次ガード）はAPI側でJST基準に保証する（現行の採用案）
- 利点: スケジューラ（GitHub Actions）は単純に高頻度で叩くだけでよく、時刻判定や重複防止のロジックをアプリに集約できる。送信時刻の判定・その日送ったかの原子的ガード（claim_daily_run）・メーカーごとのウォーターマークをJST基準で一貫して扱える。トリガーが多重・再実行されても1日1通に収まる。
- 欠点: スケジューラが高頻度で呼び出すため、大半は送信対象なしの空振り呼び出しになる。時刻ズレや二重送信防止の責務がすべてAPI側に寄る。

### 選択肢 B: スケジューラ側で正確な時刻に1回だけ起動し、API はそのまま送信する
- 利点: 呼び出し回数が最小で、空振りが無い。
- 欠点: スケジューラの起動保証・時刻精度・再実行時の重複に依存する。メーカーごとに異なる送信時刻をスケジューラ側で管理する必要があり、冪等性の担保がアプリ外に漏れる。

**弊社推奨**: A

## 判断が出ないと止まるもの
なし

## 決定
選択肢 A を採用する（現行実装）。

## 理由
送信時刻の判定と二重送信防止という業務ロジックをAPI側に集約すれば、スケジューラは高頻度に叩くだけの単純な役割に保てるため。JST基準での送信可否判定・原子的な日次ガード・メーカー単位のウォーターマークをアプリ内で一貫して扱うことで、トリガーの多重・再実行があっても1日1通の冪等性を保証できる。内部エンドポイントは内部シークレットで保護する。

## 影響
- コードベース: 内部エンドポイントで、enabled／送信時刻／原子的日次ガード（claim_daily_run）／メーカーごとのウォーターマーク（last_notified_at）をJST基準で判定するロジックを保守する。
- 運用: GitHub Actions が高頻度（例: 15分毎）で内部エンドポイントを叩き、送信対象が無い呼び出しも常時発生する。
- この決定によって不可能になること: 送信可否・重複防止をスケジューラ側だけで担保すること（API側の判定を経ずに送ること）。

## 見直しの条件
空振り呼び出しのコストが無視できなくなった場合、またはメーカーごとの正確な時刻起動を保証できるスケジューラ基盤へ移行する場合に再検討する。
