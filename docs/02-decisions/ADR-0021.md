## 背景

品質ゲート（`scripts/quality-gate.sh`）と CI（`.github/workflows/ci.yml`）に静的解析を必須チェックとして
組み込みたいが、現状のコードベースでは大量に失敗するため、docs-lint 以外は無効化・非ブロッキングにしてある。
REQ-0041 はこの是正を求める要件だが、**どこまで直すか・どの順で必須化するか**が決まらないと
受入基準を書けず、着手できない。

2026-08-06 時点の main（`c394ce2`）で全チェックを実測したところ、**失敗の大半はテストコードに偏っている**
ことが分かった。総件数だけを見て「1758 件」と判断すると実態を見誤る。

### 実測値（2026-08-06 / main `c394ce2`）

| チェック | 全体 | 本番コード | テスト・スクリプト |
|---|---|---|---|
| ruff（api） | 260 errors（174 自動修正可） | `app/` **70**（25 自動修正可） | `tests/` 137 / `scripts/`+`alembic/` 53 |
| mypy（api・strict） | 1758 errors（116 files） | `app/` **143** | `tests/` 1544 / `scripts/` 70 / `alembic/` 1 |
| eslint（web） | 5 errors・34 warnings | `src/` **5 errors** | warnings の大半は `tests/` の未使用変数 |
| tsc（web） | 26 errors | `src/` **0** | `tests/` 26 |

### 内訳から読み取れること

- **tsc は本番コードでは既に緑である。** 26 件はすべてテストのモックが `src/types/api/` の生成型から
  乖離しているもの（`customer_name` 欠落など）。API 型の再生成とモック追従で閉じる。
- **mypy の 1758 件のうち 88%（1544 件）がテストである。** 内訳は `no-untyped-def` 1061 件・`type-arg` 412 件が
  大半で、`strict = true` をテストにも課していることによる機械的な指摘。実バグの検出ではない。
  本番コード `app/` に限れば 143 件。
- **ruff は 260 件中 174 件（67%）が `--fix` で機械的に閉じる。** 手修正が要るのは
  `B904`（21・例外の再送出に `from` がない）、`B007`（16）、`B008`（8）、`F821`（4）など。
  - `B008`（引数デフォルトでの関数呼び出し）は FastAPI の `Depends()` / `Query()` に対する事実上の偽陽性で、
    設定で除外するのが一般的である。
  - `F821`（未定義名）4 件は `app/repositories/order_repository.py:698`、`app/services/shipment_service.py:61,1000,1036`。
    いずれも型注釈中の名前で、`from __future__ import annotations` により実行時評価されないため
    現時点で動作不良は起きていないが、`TYPE_CHECKING` 配下の import が漏れている状態である。
- **eslint の 5 errors はすべて `react-hooks/set-state-in-effect`**（React 19 で追加されたルール）であり、
  `src/` の実コードにある。カスケード再レンダリングの指摘なので、機械的置換ではなく実装の見直しが要る。
- 付随して、`api/pyproject.toml` の ruff 設定が旧形式（トップレベルの `select` / `ignore` / `isort`）で
  非推奨警告が出ている。`[tool.ruff.lint]` への移行が必要。

## 検討した選択肢

### 選択肢 A: 本番コードを先に緑化し、緑になったものから順に必須化する（段階的）

対象を「本番コード（`api/app/`・`web/src/`）」に絞って先に緑化し、テスト・スクリプトは後段に回す。
mypy は当面 `app/` のみを対象とし（`tests/`・`scripts/` は設定で除外）、`strict = true` は維持する。

想定する段階（各段階が 1 実装 PR）:

| 段階 | 内容 | 規模の目安 | 必須化するもの |
|---|---|---|---|
| 1 | ruff 設定を `[tool.ruff.lint]` へ移行、`B008` を FastAPI 向けに除外、`--fix` + 手修正で api 全体を緑化 | 260 件（うち自動 174） | ruff |
| 2 | web の eslint 5 errors を修正、tsc のテスト型ずれ 26 件を修正 | 31 件 | eslint / tsc |
| 3 | mypy の対象を `app/` に限定し、143 件を strict のまま緑化 | 143 件 | mypy（`app/` のみ） |
| 4 | `tests/`・`scripts/` を mypy 対象に広げる | 1614 件 | —（別要件として起票し直す） |

- 利点: 各段階の終わりで必ず「緑のチェックが 1 つ増える」状態になり、途中で止めても成果が残る。
  実バグに近い指摘（`B904`・`F821`・`set-state-in-effect`）が最初の 2 段階で片付く。
  段階 1〜3 の合計は約 430 件で、大半が機械的修正。機能開発と並行できる規模である。
- 欠点: mypy が当面テストを見ないため、テストコードの型崩れは検出されないまま残る。
  段階 4 を別要件に切り出すため、「全部緑」に到達するのは先になる。

### 選択肢 B: テストを含めて全件を一括で緑化してから必須化する

- 利点: 妥協がなく、一度で「全チェックが緑」に到達する。設定に除外を持ち込まないため後の判断が要らない。
- 欠点: mypy strict の 1544 件（テスト）が支配的で、その大半はテスト関数への `-> None` 付与と
  `dict` → `dict[str, Any]` の書き換えという機械的作業。バグ検出への寄与に対して作業量が大きく、
  完了まで必須化が一切進まない。途中で中断すると成果がゼロになる。

### 選択肢 C: 自動修正可能な分だけ直し、残りはルールを緩めて（除外して）必須化する

- 利点: 最短で「緑」を宣言でき、すぐ必須化できる。
- 欠点: `B904`（例外連鎖の欠落）・`F821`（import 漏れ）・`set-state-in-effect`（再レンダリング）といった
  実装上の問題がルール除外という形で恒久的に残る。ゲートを通ることが品質の裏づけにならなくなり、
  REQ-0041 の目的（必須チェック化）が形骸化する。

**弊社推奨**: **A**。実測の内訳が「本番コードは小さく、テストが大きい」という形になっており、
本番コードだけなら約 430 件・大半が機械的修正で片付く。段階ごとに必須チェックが 1 つずつ増えるため、
機能開発を止めずに進められ、途中で優先度が変わっても成果が残る。
`tests/` への mypy 適用は、費用対効果を見てから別途判断するのが妥当と考える。

## 決定

**選択肢 B を採用する。** テストコードを含めて全件を緑化してから、4 つのチェック
（ruff / mypy / eslint / tsc）を一括で品質ゲートと CI の必須チェックに昇格させる。

- mypy の `strict = true` は維持し、対象範囲も絞らない（`app/` / `tests/` / `scripts/` / `alembic/` のすべて）。
- ルールの緩和・除外は、**ツールの仕様上の偽陽性に限る**。具体的には FastAPI の `Depends()` / `Query()` に対する
  `B008` を `extend-immutable-calls` で除外する。指摘を消すためのルール無効化は行わない。
- 是正の過程でテストの振る舞いを変えない。pytest / vitest が緑のままであることを完了条件に含める。

## 理由

段階的に進める案（選択肢 A）と比べ、B は完了まで必須化が一切進まないという欠点があるが、
**除外設定という形の負債を残さない**点を優先した。選択肢 A は `tests/` を mypy の対象外にする設定を
恒久的に抱えることになり、「いつ段階 4 をやるのか」という判断が後に残り続ける。
一度で全件を緑にしておけば、以後は「緑を維持する」だけの運用になり、判断が要らなくなる。

作業量の大半（mypy の 1544 件）はテスト関数への `-> None` 付与と `dict` → `dict[str, Any]` の
書き換えという機械的な修正であり、設計判断を伴わない。**判断の要らない作業量は、
判断を将来に残すことより安い**という評価である。

## 影響

- コードベース: `api/pyproject.toml`（ruff の設定形式・除外、mypy の対象範囲）、`api/app/` 配下（ruff・mypy の是正）、
  `web/src/`（eslint の是正）、`web/tests/`（tsc のモック型追従）、`web/eslint.config.mjs`（必要なら除外設定）。
- 運用: `scripts/quality-gate.sh` の `PROJECT_CHECKS` に緑のチェックを追加していく順序。
  `.github/workflows/ci.yml` の `continue-on-error` を外す順序と、ブランチ保護の必須チェック設定。
- 是正が完了するまで、4 つのチェックはいずれも必須化されない（非ブロッキングのまま）。
- 是正後は、新しいコードが 4 つのチェックすべてを満たさないと push・マージができなくなる。
  テストコードにも `strict` な型注釈が要求される。

## 見直しの条件

- 静的解析ツールのメジャー更新で新ルールが増え、緑だったチェックが赤に戻った場合は、
  除外設定の方針を含めてこの判断を見直す。
- テストコードへの `strict` 適用が新規テストの作成速度を著しく損なっていると判断された場合は、
  `tests/` に限った緩和を別 ADR で検討する。
