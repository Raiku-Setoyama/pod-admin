## 背景

ADR-0028 は GitHub Actions に置くワークフローを 3 つと定め、その 1 つを
**「Terraform の差分確認（Pull Request 契機）」**とした。

実装するにあたって、その差分確認が何を要求するかを洗い出したところ、
次の 3 つが必要になることが分かった。

1. state バケット（`gs://tosyo-api-stg-tfstate`）の読み取り
2. 管理下のリソース全体の閲覧
3. **Secret Manager のシークレット値の読み取り**

3 が必要なのは、Terraform が `google_secret_manager_secret_version` の現在値を
差分計算のために読み直すためである。1 は ADR-0027 が
**「state バケットの閲覧権限は、データベースのパスワードを見られる権限と等しい」**
と明記している。

つまり差分確認を CI に置くと、**CI がこのシステムの機密情報をすべて読める**状態になる。

そのうえで問題になるのが、Pull Request 契機のワークフローは
**その Pull Request 自身が持ち込んだワークフロー定義で動く**という GitHub Actions の仕様である。
ブランチに push できる者は、差分確認のジョブに 1 行足すだけで機密を持ち出せる。
**人間のレビューはワークフローが走り終わったあとにしか入らない。**

## 検討した選択肢

### 選択肢 A: Terraform を CI から外し、`fmt` と `validate` だけを残す

- 利点: **CI が資格情報を一切持たない。**上記の経路が構造的に生じない
- 利点: 書式と構文の誤りは資格情報なしで捕まえられる（`ci.yml` の `infra` ジョブで実施済み）
- 欠点: 設定と実物のずれ（drift）は、人間が `terraform plan` を打つまで見つからない

### 選択肢 B: 閲覧専用のサービスアカウントを別に作って差分確認を回す

- 利点: drift を自動で検知できる
- 欠点: **リポジトリ単位の連携では意味のある分離にならない。**
  Workload Identity 連携の許可はリポジトリ単位に付くため、
  同じリポジトリのどのワークフローからも借りられる。役割を分けても到達可能性は変わらない
- 欠点: 閲覧専用でも、読めるものの中身が機密そのものである

### 選択肢 C: GitHub Environment の承認を挟んで差分確認を回す

- 利点: 上記の経路を塞ぎつつ drift を検知できる
- 欠点: 承認の設定がリポジトリの設定画面にあり、**Terraform の管理下に置けない。**
  設定が外れても誰も気づかない
- 欠点: 差分確認のたびに人間の操作が要る。自動である利点が消える

**弊社推奨**: A

## 決定

**選択肢 A を採用する。ADR-0028 の 3 ワークフローのうち、Terraform の差分確認は作らない。**

- `terraform plan` / `apply` は作業者の手元から実行する
- CI で行うのは `terraform fmt -check` と `terraform validate` だけとする。
  これらは資格情報を必要としない（`ci.yml` の `infra` ジョブ）
- **デプロイ用のワークフローには state もシークレットも渡さない。**
  必要なのは Cloud Run の更新権限、イメージの push 権限、実行 ID のなりすまし権限の 3 つだけである

ADR-0028 の他の決定（Workload Identity 連携を使う・鍵 JSON を作らない・
リポジトリ条件を必ず付ける・本番への反映は手動）は変更しない。

## 理由

CI に権限を渡す判断は、**渡した権限で何ができるかではなく、
その権限を誰が引き出せるかで決めるべきである。**
Pull Request 契機のワークフローは、レビュー前のコードで動く。
そこに機密の読み取り権限を置くと、レビューという唯一の人間のゲートが後ろに来てしまう。

失うものは drift の自動検知だけである。**この環境の drift は、
`terraform apply` が人間の手元でしか走らない以上、人間が打つ以外の経路では発生しない。**
検知が要る場面（例: コンソールでの手作業）は、そのとき `terraform plan` を打てばよい。

## 影響

### コードベースへの影響

- `.github/workflows/terraform.yml` は作らない
- `.github/workflows/deploy.yml`（反映手順の本体）と
  `deploy-staging.yml`（`main` マージ契機の呼び出し側）の 2 つになる

### 運用への影響

- **インフラの変更は、Pull Request を出す前に手元で `terraform apply` まで済ませる。**
  Pull Request は「適用済みの構成をコードとして記録する」ものになる
- 適用結果（`terraform plan -detailed-exitcode` が差分なしを返すこと）は
  Pull Request 本文に記載する

### 残るリスク

デプロイ用のサービスアカウントは `roles/run.admin` を持つ。
これは **Cloud Run のサービスを任意のイメージに差し替えられる**ということであり、
差し替えたイメージは `pod-admin-api@` として動くのでシークレットを読める。
自動デプロイを持つ以上この経路は消せない。

**緩和は GCP 側の IAM 条件で行う。ワークフローの書き方に頼らない。**
`main` 契機に限るという制約をワークフロー側（`on: push: branches: [main]`）に置いても、
**ブランチに push できる者がその定義ごと差し替えられる**ので守りにならない。
本文で退けたのと同じ穴である。

トークンの発行を許す条件を 2 つとも付ける（`infra/modules/github-oidc`）。

```
assertion.repository == 'Raiku-Setoyama/pod-admin' && assertion.ref == 'refs/heads/main'
```

**リポジトリ条件だけでは足りない。** 同じリポジトリの他のワークフローも同じ条件を満たす。
実際 `.github/workflows/claude.yml` は issue のコメントを契機に `id-token: write` で動くため、
リポジトリ条件だけなら**コメント 1 つでデプロイ用 SA を名乗れる。**
`main` に限れば、経路は「人間が Pull Request をマージする」1 本になる。

### この決定によって不可能になること

- Pull Request の画面で Terraform の差分を見ることはできない

## 見直しの条件

- 機密情報を state に置かない仕組みを導入し、state の閲覧が機密の閲覧と等しくなくなったとき
- 環境が増え、手元での `terraform plan` が実務的に回らなくなったとき
