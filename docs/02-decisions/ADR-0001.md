## 背景
利用者（管理者・製造委託先）の認証方式と、パスワードの保管方法、発行したトークンのクライアント側での保管場所を決める必要があった。決定時期は不明（既存実装から逆算し 2026-08-06 に記録）。

## 検討した選択肢
### 選択肢 A: ステートレス JWT（HS256・単一 SECRET_KEY）+ bcrypt、トークンは localStorage 保管
- 利点:
  - サーバー側でセッションを保持せずに済み、スケールしやすい
  - トークンに種別（type）・有効期限（exp）クレームを持たせ、管理者／メーカーを同一基盤で扱える
  - パスワードは bcrypt ハッシュで保管でき、管理者・メーカー共通の方式にできる
  - localStorage はブラウザ内で扱いやすく、フロントエンドの実装が単純になる
- 欠点:
  - ステートレスかつブラックリストを持たないため、発行済みトークンをサーバー側で失効できない（ログアウトはクライアント側削除のみ）
  - トークンを localStorage に置くため XSS による窃取リスクを受容することになる
### 選択肢 B: サーバー側セッション（ステートフル）+ HttpOnly Cookie 保管
- 利点:
  - サーバー側でセッションを破棄でき、確実な失効・ログアウトが可能
  - HttpOnly Cookie により JavaScript からの読み取りを防ぎ XSS リスクを下げられる
- 欠点:
  - セッションストアの運用が必要になり、ステートレスな構成より複雑になる
  - Cookie 運用に伴う CSRF 対策など別の考慮が増える

**弊社推奨**: A

## 判断が出ないと止まるもの
なし

## 決定
選択肢 A を採用する（現行実装）。認証はステートレスな JWT（HS256、単一 SECRET_KEY、type・exp クレーム、ブラックリストなし）で行い、パスワードは passlib + bcrypt でハッシュ化して管理者・メーカー共通で扱い、発行したトークンはブラウザの localStorage に保管する。

## 理由
サーバー側でセッションを保持しないステートレス構成は運用が単純で、トークンに種別・有効期限を持たせることで管理者とメーカーを同一の認証基盤で扱える。パスワードは bcrypt ハッシュにより安全に保管し、両利用者で共通化できる。トークンの localStorage 保管はフロントエンド実装を単純化できるため、XSS リスクを受容したうえで採用した。将来この決定を見直す際は、確実な失効が必要になったか（ブラックリスト／サーバー側セッション）や、XSS リスク低減のための保管方式変更が論点になる。

## 影響
- コードベース: JWT の署名・検証（HS256・単一 SECRET_KEY）、bcrypt によるパスワードハッシュ、トークンの localStorage 読み書きがフロント・バックにわたって前提となる
- 運用: SECRET_KEY の管理が全認証の要になる。発行済みトークンをサーバー側で無効化できないため、失効は有効期限切れに依存する
- この決定によって不可能になること: 発行済みトークンの即時失効（サーバー主導のログアウト・強制ログアウト）ができない。localStorage 保管のため HttpOnly Cookie 相当の XSS 耐性は得られない

## 見直しの条件
発行済みトークンの即時失効が必要になった場合、XSS による localStorage 窃取のリスクを許容できなくなった場合、または単一 SECRET_KEY での鍵運用・ローテーションが要件に合わなくなった場合に再検討する。
