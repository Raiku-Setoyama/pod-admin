## 背景

Railway（API）と Vercel（フロント）から GCP へ移行するにあたり、3 つを決める必要がある。

1. **どの実行基盤に載せるか**
2. **アプリからデータベースへどう繋ぐか**
3. **30〜360 秒かかる製造データ生成を、どこで動かすか**

`docs/gcp-deployment-cost-review.md`（2026-07-29 確定版）は、3 について
「Windows VM 上でワーカーを常駐させる」と結論していた。しかし 2026-08-27 に GCP を実測した結果、
**その前提が変わった。**

- 製造データ生成に使う Windows VM は、会社組織ではなく**個人アカウント配下**にあり、
  請求先も会社とは別だった（プロジェクト `lively-transit-334610`）
- 依頼者の判断で、この VM は**移行の完了後に別途移送する**ことになった（REQ-0055）

つまり移行の期間中、VM は会社組織の外に置かれたままになる。
ワーカーをその VM に置くと、会社組織の外に運用の中核を作ることになる。

## 検討した選択肢

### 選択肢 A: Windows VM 上に常駐ワーカーを置く（コストレビュー確定版の案）

- 利点: 外部 VM の API をローカルホスト経由で呼べるため、ネットワーク的に閉じている
- 欠点: VM のサービスアカウントの権限範囲を広げる必要がある（現状は読み取り専用のため、
  成果物を保存できない）。変更には VM の停止・起動を伴う
- 欠点: 会社組織をまたいだ権限付与が必要になる
- 欠点: Windows 上での Python プロセスの常駐運用（サービス化・自動再起動・実行環境の構築）を
  抱える。VM が個人アカウント配下にある間は、運用が組織をまたいで分断される
- 欠点: VM を移送するとき、ワーカーも一緒に引っ越すことになる

### 選択肢 B: コンテナ実行基盤のジョブとしてワーカーを動かす

- 利点: **VM 側の作業がゼロ。**権限範囲の変更も、組織をまたいだ権限付与も要らない
- 利点: VM を移送しても、変わるのは接続先の URL 1 つだけ
- 利点: ジョブは CPU が常時割り当てられ、実行時間の上限も十分に長いため、
  「リクエスト処理中しか CPU が割り当てられない」という制約を受けない
- 利点: 処理対象が無ければ数秒で終了するため、待機時間に費用がかからない
- 欠点: 定期起動の仕組みが 1 つ増える。多重起動を防ぐ仕掛けが要る
- 欠点: 常時稼働させると割高になる（対象が無ければ即終了する実装が前提になる）

### 選択肢 C: API 本体に常時 CPU を割り当て、いまの実装のまま動かす

- 利点: アプリの改修が最も小さい
- 欠点: 費用が上乗せされるうえ、インスタンスが縮退するときに処理中の生成が失われる。
  数分かかる処理の置き場としては不安定である

**弊社推奨**: B

## 決定

**選択肢 B を採用する。**

あわせて、実行基盤と DB 接続方式を次のとおりとする。

| 対象 | 決定 |
|---|---|
| API・フロント | コンテナ実行基盤（Cloud Run）に載せる |
| マイグレーション | 起動コマンドから分離し、独立したジョブとして実行する |
| 製造データ生成 | **ジョブ（Cloud Run Job）として実行し、定期起動する** |
| DB 接続 | **パブリック IP を持たせるが、許可ネットワークは 0 件にし、IAM 認証の接続経路だけを使う** |
| ネットワーク | **移行の段階では専用ネットワーク（VPC）を作らない。**外部 VM の移送時に追加する |
| ファイル保管 | Cloud Storage。認証は鍵ファイルではなく実行環境の権限を使う |

## 理由

**ワーカーをジョブに置いたことで、VM から DB へ接続する必要が最後まで生じない。**
その結果、データベースに専用ネットワーク上のアドレスを持たせる理由が消え、
ネットワーク一式（VPC・サーバーレス接続・NAT）が不要になった。

もし DB を専用ネットワーク上に置くと、個人アカウント配下の VM から届かせるために
**別の組織・別の請求先をまたぐネットワーク接続**が必要になる。移行期間だけのために
その複雑さを抱えるのは割に合わない。

「コンテナ実行基盤ではリクエスト処理中しか CPU が割り当てられない」という
コストレビュー確定版の前提は、**サービスとして常駐させる場合の話**であり、
**ジョブには当てはまらない**。ジョブは CPU が常時割り当てられる。
確定版はこの区別をしていなかった。

DB 接続にパブリック IP を使うことは、一見すると後退に見える。しかし許可ネットワークを
0 件にすれば直接接続できる経路は無く、IAM 認証を通した接続だけが成立する。
専用ネットワークを用意する場合と比べて、**露出は増えないまま構成が大幅に単純になる。**

## 影響

### コードベースへの影響

- 非同期処理を実行基盤に依存しない形へ改める必要がある（REQ-0052）
- **データベース接続文字列の組み立ては変更不要。**既存の変換処理がそのまま通ることを確認済み
- **ファイルパスの保存形式も変更不要。**保存先に依存しない形式で記録されていることを確認済み

### 運用への影響

- 製造データ生成の実行状況が、実行基盤側のログとして一覧できるようになる
- 定期起動の間隔が、生成の待ち時間の下限になる
- 外部 VM を移送しても、アプリ側は接続先の設定を 1 つ変えるだけで済む

### この決定によって不可能になること

- 外部 VM の API をローカルホスト経由で呼ぶことはできない。移送が済むまでは
  インターネット経由の呼び出しが続く（REQ-0055 で解消する）

## 見直しの条件

- 製造データの生成量が増え、定期起動の間隔では待ち時間が許容できなくなったとき
- 外部 VM の移送が完了し、ネットワークを閉じたあとに、DB も同じネットワーク内へ
  移したほうが単純になると判断したとき
- ジョブの費用が、常時稼働させる場合と変わらない水準まで増えたとき
