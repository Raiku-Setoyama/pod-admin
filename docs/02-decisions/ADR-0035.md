## 背景

REQ-0054 のカットオーバー手順は、**手順 2 で Railway の API を停止し**、そのあとに
ダンプの取得・移送・動作確認を行う形で書かれていた。メンテナンス枠を取り、その間は
サービスを止める前提である。

これに対し依頼者から 2 つの要求が出た（2026-08-31）。

1. **移行が完了して動作検証が取れるまで、旧環境（Vercel + Railway）は停止したくない**
2. **URL の切り替え前に Railway を停止する必要があるのか。停止は全部終わったあとでよいのでは**

2 は手順の前提そのものへの問いである。**旧環境を止める目的は URL 切替の前提ではなく、
「書き込みを凍結して、ダンプを欠けのない断面にすること」**である。ダンプを取ったあとに
旧環境へ書き込みが入ると、その分は旧 DB にしか存在せず、移行先から永久に消える。

さらに、止めたままにすると**別の穴が開く。** 旧 API を止めてから外部販売サイトが新 URL を
向くまでの間、届いた受注はどこにも入らない。**この空白の長さは、こちらの作業時間ではなく
相手方が切り替えるのにかかる時間で決まる。**

着手時点の状況は次のとおりだった。

- 外部販売サイトからの受注は現在ほぼ無い（依頼者の確認）
- 切替は今日中に実施できる（同上）
- 旧環境は**現に使われている**（旧バケットのオブジェクトが 8/30 の複製時 10 件から 11 件に増えていた。
  増えた 1 件は 2026-08-31 09:51 JST 生成）

## 検討した選択肢

### 選択肢 A: 手順どおり、先に Railway を停止する

- 利点: 書き込みの凍結が**機械的に保証される**。操作者の注意に依存しない
- 欠点: 停止から外部販売サイトの切替完了までの受注が落ちる。空白の長さを
  こちらで制御できない。旧環境を再開する操作がロールバックの前提になる

### 選択肢 B: 停止せず、最後に回す

- 利点: **停止時間がゼロになる。** 切り戻しは「向き先を戻すだけ」になり、
  旧環境を再開する操作が要らない。落ちる受注が無い
- 欠点: 「書き込みが起きない」ことを人の合意に頼る。旧管理画面での作業や、
  旧 URL に届いた受注は移行先に来ない

**弊社推奨**: B

## 決定

**選択肢 B を採用する。旧環境は停止せず、切替がすべて終わったあとに止める。**

代わりに、**「書き込みが起きなかったこと」を機械的に確かめる**。

1. **自動の書き込みを先に止める。** メーカー日次発注ダイジェストのワークフローは
   15 分ごとに旧 API を叩き、送信条件を満たすと**旧 DB に「本日送信済み」を書き込んで
   実際にメールを送る**。これは「誰も触らない」では防げないので、移送の前に停止し、
   切替後に新 URL を向けてから再開する
2. 旧管理画面での作業を止めてもらう（人の合意）
3. **戻れなくなる切替に入る前に 2 回目のダンプを取り、1 回目と件数を突き合わせる。**
   一致すれば、その間に書き込みが無かったことが機械的に言える。
   ずれていれば、どのテーブルが動いたかが分かるので移送をやり直す（15〜30 分）。
   **切替のあとでは遅い** — 外部販売サイトが新環境を向いたあとに `reset` すると、
   切替後の受注を壊す。検知はできても直せない位置になり、B を選んだ根拠が消える

## 理由

**停止は目的ではなく、書き込み凍結の一手段にすぎない。** 書き込みが実際に起きないなら、
止めなくても結果は同じであり、止めないほうが停止時間と受注の取りこぼしが消える。

**A と B は「検知できるか」で非対称である。** B が壊れる経路（誰かが旧画面で作業した）は
2 回目のダンプとの突合で必ず検知でき、やり直しは 15〜30 分で済む。
一方 A が壊れる経路（相手方の切替が長引き、その間の受注が落ちた）は、
**検知できても受注そのものが失われており、取り返せない。**

**判断ポイントの意味も強くなる。** A では判断ポイントに立った時点で旧環境が既に止まっており、
「戻す」は再開の操作を含む。B では旧環境が無傷で動いたままなので、
**何もしないことがロールバックになる。**

## 影響

- REQ-0054 の「業務フロー（カットオーバー）」の手順 2 が最後尾へ移る。
  メンテナンス枠は「サービスを止める枠」ではなく「旧画面で作業しない枠」になる
- **受入基準「移行前後で各件数が一致する」は 2 回目のダンプまで閉じない。**
  1 回目の `compare` が示すのは「ダンプ → 移送先」が一致することだけであり、
  移送の間に移送元が動いていないことは、2 回目との突合でしか言えない
- ダイジェストのワークフローを止めている間、その日の送信は行われない。
  ガードは日付単位なので、再開後に同じ日の送信が二重になることはない
- **旧環境が動いたまま残るので、旧 URL を知っている経路は書き込めてしまう。**
  外部販売サイトの切替と、旧管理画面を使わない合意が、この決定の前提になる

## 見直しの条件

- 外部販売サイトからの受注が常時あり、切替に日数がかかる案件では、
  **落ちる受注の量が「取りこぼしゼロ」の前提を崩す。** その場合は A に戻し、
  停止時間を受け入れるか、旧環境から移行先への転送を用意する
- 2 回目のダンプとの突合が一致しないことが常態化するなら、
  人の合意による凍結が機能していない。停止による凍結へ戻す
