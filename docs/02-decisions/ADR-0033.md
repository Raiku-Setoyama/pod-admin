## 背景

ADR-0031 は、GitHub Actions が GCP の資格情報を借りる条件について次のように書いた。

> リポジトリ条件だけでは足りない。`.github/workflows/claude.yml` は issue コメントを
> 契機に `id-token: write` で動くので、そこからデプロイ用 SA を名乗れてしまう。

そのうえで対策として `assertion.ref == 'refs/heads/main'` を足した。

**この対策は、名指しした脅威をふさいでいなかった。**

`issue_comment` と `issues` を契機に動くワークフローでは、**GitHub が `ref` に
既定ブランチを入れる。** マージは起きていないのに `refs/heads/main` になる。
つまり `claude.yml` のトークンは `ref` 条件を素通りする。

REQ-0053 で行った否定確認（ブランチからの実行が認証で落ちること）は、
**push イベントでしか試していなかった。** push なら `ref` はそのブランチなので落ちる。
`issue_comment` は試しておらず、通ることに気づけなかった。

本番環境（REQ-0054）を作ったことで、この経路の先が本番の
`pod-admin-deployer`（`roles/run.admin`）になった。**リポジトリは公開である。**

## 決定

**`job_workflow_ref` で絞る。**

```
assertion.repository == 'Raiku-Setoyama/pod-admin' &&
assertion.job_workflow_ref == 'Raiku-Setoyama/pod-admin/.github/workflows/deploy.yml@refs/heads/main'
```

サービスアカウントを借りられる主体（`principalSet`）も、
`attribute.repository` ではなく `attribute.job_workflow_ref` に張り替える。

## 理由

`job_workflow_ref` は「`owner/repo/パス@ref`」という 1 つのクレームに、
**リポジトリ・ワークフローファイル・ref の 3 つ**が入っている。
`ref` 単独と違い、**どのワークフローの実行か**まで表せる。

再利用ワークフローを `uses:` で呼んだジョブでは、**呼ばれた側**の値になる。
`deploy-staging.yml` も `deploy-prod.yml` も実体は `deploy.yml` なので、
1 つの条件で両方の呼び出しを通しつつ、他のワークフローを落とせる。

`ref` を条件から外しても弱くならない。`job_workflow_ref` の末尾が `@refs/heads/main` である。

## 影響

- `claude.yml` はデプロイ用 SA を名乗れなくなった。両プロジェクトで確認済み
- **`deploy.yml` そのものが信頼の単位になった。** このファイルを変更する PR は、
  資格情報の境界を変更する PR である
- ステージングと本番で条件は同じである。**両者は同じ信頼ドメインにある**（下記）

## 残っている risk

**`deploy.yml` の中で動くコードは、ステージングにも本番にも到達できる。**
`deploy-staging.yml` は `main` へのマージで自動起動するので、
そこに書く 2 つの値（provider と SA）を本番のものへ差し替えれば、
マージだけで本番に反映できてしまう。**`deploy-prod.yml` の手動実行は迂回できる。**

これを機械的に止めるには、GitHub Environment の承認を挟み、
WIF の条件に `attribute.environment` を足して「承認を通った実行だけ」に絞る必要がある。
`github_repository_environment` は Terraform で作れるので、
ADR-0031 が「リポジトリの設定画面が正本になる」として退けた理由は当たらない。

**今回は入れていない。** 迂回には `main` への PR とそのレビューが要り、
`claude.yml` の経路（コメント 1 つ）とは危険度が 2 桁違う。
REQ-0054 のカットオーバー（PR 3）までに判断する。

## この失敗から言えること

**否定確認は、ふさぎたい経路そのもので行う。** 今回は
「ブランチからの push が落ちること」を確認して満足したが、
ふさぎたかったのは `claude.yml`（issue コメント契機）だった。
**別の経路で落ちることを確かめても、目的の経路の証拠にはならない。**
