## 背景

Cloud Run のサービスと Job は、「どんな箱で動かすか」（CPU・メモリ・環境変数・接続先）と
「何を動かすか」（コンテナイメージのタグ）を 1 つのリソースとして持つ。

前者は Terraform が管理する。後者はデプロイのたびに変わる。
**この 2 つが同じリソースに同居しているため、どちらが所有者かを決める必要がある。**

決めずに放置すると、`terraform apply` が最後に Terraform が知っているイメージへ巻き戻し、
デプロイ済みのアプリが古い版に戻る。インフラの設定を 1 行変えただけでアプリが巻き戻る、
という形で事故が起きる。

## 検討した選択肢

### 選択肢 A: Terraform はイメージタグを見ない（`ignore_changes`）

- 利点: **インフラの変更とアプリのデプロイが互いに干渉しない。**
  どちらをいつ実行しても、もう一方を壊さない
- 利点: デプロイが Terraform を経由しないため、反映が速く、権限も小さくて済む
- 欠点: **Terraform の定義を読んでも、いま何が動いているかは分からない。**
  実物は `gcloud run services describe` で見る

### 選択肢 B: Terraform がイメージタグを持ち、デプロイも Terraform で行う

- 利点: 定義と実物が一致する。1 か所を見れば動いている版が分かる
- 欠点: **デプロイのたびに Terraform の state が書き換わる。**
  アプリのデプロイに state バケットへの書き込み権限が要る（ADR-0027 より、
  それは DB のパスワードを読める権限と等しい）
- 欠点: インフラ変更とデプロイが同じロックを奪い合う

### 選択肢 C: イメージタグを変数にして、デプロイのたびに `tfvars` を書き換える

- 利点: 定義と実物が一致する
- 欠点: **デプロイのたびにリポジトリへのコミットが必要になる。**
  ロールバックのような急ぐ操作が、Pull Request の速度に縛られる

**弊社推奨**: A

## 決定

**選択肢 A を採用する。**

`cloud-run-service` / `cloud-run-job` モジュールで、イメージタグを
`lifecycle.ignore_changes` の対象にする。

- Terraform が作るときは **Google 公開のサンプルイメージ**を使う。
  Artifact Registry にまだ何も無い状態でも apply が完走する
- 実物のイメージは、デプロイ（GitHub Actions / `gcloud run deploy`）が入れる
- **Terraform はイメージ以外のすべて**（CPU・メモリ・スケール上限・環境変数・
  シークレット・Cloud SQL 接続・IAM）を持ち続ける

## 理由

決め手は**権限の大きさ**である。

選択肢 B を採ると、アプリをデプロイするだけの経路に state バケットへの書き込み権限が要る。
ADR-0027 のとおり state には DB のパスワードが平文で入るので、
**「アプリを更新できる」と「本番 DB の資格情報を読める」が同じ権限になる。**
デプロイは 1 日に何度も走る操作であり、そこに最も重い権限を載せるのは筋が悪い。

選択肢 A の欠点（定義を読んでも動いている版が分からない）は、
**そもそも Terraform に期待すべきことではない。**動いている版は実行基盤に聞けばよく、
どの版がいつ入ったかはデプロイの履歴が持っている。

apply を初回から完走させられる点も実務上大きい。
イメージが先に無いと apply できない構成にすると、環境の新規作成が
「Terraform → ビルド → Terraform」の 3 段になり、手順が壊れやすくなる。

## 影響

### コードベースへの影響

- `infra/modules/cloud-run-service` と `infra/modules/cloud-run-job` に
  `lifecycle.ignore_changes` を置く
- `image` 変数の既定値は Google 公開のサンプルイメージにする

### 運用への影響

- **環境を新規に作った直後は、サンプルイメージが動いている。**
  続けてデプロイを実行するまでアプリは動かない。手順は `infra/README.md` に置く
- 動いている版を知りたいときは `gcloud run services describe` を見る
- Terraform の `plan` は、デプロイ後も差分ゼロのままになる

### この決定によって不可能になること

- `terraform apply` でアプリを特定の版へ戻すことはできない。
  ロールバックは Cloud Run のリビジョン操作、またはデプロイの再実行で行う

## 見直しの条件

- state に機密情報を置かない仕組みへ移行し、デプロイ経路の権限が小さくできるようになったとき
- インフラとアプリを 1 つの操作でまとめて切り替えたい要求が出たとき
