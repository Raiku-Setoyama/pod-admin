## 背景

本番とステージングの 2 環境を Terraform で管理する。GCP プロジェクトは環境ごとに分かれている
（`tosyo-api-504104` / `tosyo-api-stg`）。

Terraform で複数環境を扱う方法は複数あり、選び方によって「ステージングで直した設定が
本番に伝わるか」「本番を誤って触る事故が起きうるか」が変わる。

state（Terraform が管理下のリソースを記録するファイル）の置き場も決める必要がある。
**state にはデータベースのパスワードが平文で入る。**

## 検討した選択肢

### 選択肢 A: 共通モジュール ＋ 環境ごとの薄い定義

```
infra/modules/      共通の部品
infra/envs/staging/ ステージングの定義と設定値
infra/envs/prod/    本番の定義と設定値
```

- 利点: 環境差分が設定値ファイルに露出し、読めば分かる
- 利点: ステージングで直したモジュールが、そのまま本番に適用できる
- 利点: 作業ディレクトリが環境ごとに分かれるため、本番を誤って触りにくい
- 欠点: ファイル数が増える

### 選択肢 B: Terraform の workspace で環境を切り替える

- 利点: ファイル構成が 1 つで済む
- 欠点: **いまどちらの環境を触っているかがコマンドの実行状態に依存する。**
  切り替え忘れで本番に適用する事故が起きうる
- 欠点: 環境差分が条件分岐としてコードに埋まり、読み取りづらくなる

### 選択肢 C: 環境ごとにコードを丸ごと複製する

- 利点: 差分が完全に読める
- 欠点: **ステージングで直した修正が本番に自動では伝わらない。**移行の目的に反する

**弊社推奨**: A

## 決定

**選択肢 A を採用する。**

state は**環境ごとに別の Cloud Storage バケット**へ保存する。
バケットはそれぞれの GCP プロジェクト内に置き、バージョニングを有効にする。

```
gs://tosyo-api-stg-tfstate       ← ステージング
gs://tosyo-api-504104-tfstate    ← 本番
```

state バケットは Terraform 自身では作れない（自分の置き場を自分で作れない）ため、
**`gcloud` で先に作る。**この手順は設計書に残す。

## 理由

移行の目的の 1 つは「ステージングで確認してから本番に適用する」ことである。
選択肢 C はこの流れを壊す。選択肢 B は流れは保てるが、**取り違えの事故が本番に直撃する。**

state を環境ごとに分けるのは、影響範囲を環境の境界で切るためである。
1 つのバケットにまとめると、ステージングの操作ミスが本番の記録に届きうる。

**state にはデータベースのパスワードが平文で入る。**
これは Terraform の仕組み上避けられないため、バケットへのアクセスを絞ることで守る。
バージョニングを有効にするのは、誤った上書きから復旧できるようにするためである。

## 影響

### コードベースへの影響

- `infra/` ディレクトリを新設する
- 環境の追加は、`infra/envs/` にディレクトリを 1 つ増やす作業になる

### 運用への影響

- `terraform apply` は環境のディレクトリに移動してから実行する
- state バケットは Terraform の管理対象外になる。削除すると管理情報を失う
- **state バケットの閲覧権限は、データベースのパスワードを見られる権限と等しい**

### この決定によって不可能になること

- 1 コマンドで全環境をまとめて適用することはできない（意図的な制約である）

## 見直しの条件

- 環境が 3 つ以上に増え、環境ごとのディレクトリの重複が問題になったとき
- 機密情報を state に置かない仕組み（外部の機密管理との連携）を導入するとき
