## 不具合と要件の違い

**判定は 1 つの問いで決まります。**

> **既存の受入基準に違反しているか。**
>
> - **違反している → 不具合（`BUG-XXXX`）。** ここに入ります
> - **違反していない → 要件（`REQ-XXXX`、`priority: undecided`）。** 新しい約束の話です

「既存の受入基準」には憲章も含みます。`../00-charter/nfr.md`（`NFR`）と
`constraints.md`（`CONSTRAINTS`）も**マージ済みの約束**です。
性能要件を割っているなら、特定の要件に紐づかなくても不具合です。

**この線は瑕疵と仕様変更の境界そのものです。** 「書いてある約束を満たしていない」＝瑕疵、
「書いていないことを求められた」＝仕様変更。判定の正本は `AGENTS.md` にあります。

**迷ったら要件に倒してください。** 不具合と判定すると採否の判断を経ずに修正まで進むので、
誤判定のコストが非対称です。要件に倒せば人間の判断ゲートを必ず通ります。

## priority — いつ直すか

要件と同じフィールドですが、**意味が違います。**

| | 意味 |
|---|---|
| 要件の `priority` | **やると約束するか** |
| 不具合の `priority` | **すでにした約束を、いつ果たすか** |

約束は元の受入基準として既に存在するので、**採否を問う段階がありません。
`undecided` は使いません**（書くと `scripts/docs-lint.py` が落ちます）。

| priority | 意味 | 顧客向け表記 |
|---|---|---|
| `must` | 直す（**起票時の既定**） | 修正対応 |
| `future` | 既知の不具合として今回は出す。次期に直す | 次期修正 |
| `wont` | 直さない（現状仕様として受容 / 再現せず / 重複） | 現状仕様 |

**起票時の既定値が要件と逆です。**

| | 起票時 | 人間の判断が要るのは |
|---|---|---|
| 要件 | `undecided` | **上げる**とき |
| 不具合 | **`must`** | **下げる**とき（`future` / `wont`） |

`future` / `wont` にするときは `decision` に理由を、`decided_at` に判断日を必ず書きます。
**「不具合として報告を受けたが、仕様の範囲内と判断した」記録は、受託開発で資産になります。**

## status — 修正の進み具合

要件と同じです。`not-started` / `in-progress` / `done` / `on-hold`。

`done` は修正 PR 自身が書き込みます。未達の受入基準を残したまま `done` にすると
`scripts/docs-lint.py` が落ちます。

## 元の要件は `done` のまま戻しません

**`done` は「その時点で全受入基準を満たして PR がマージされた」という履歴の記録**であり、
「今この瞬間も満たしている」という保証ではありません。

- 検収済みの要件が「未完了」に戻ると、報告と契約上の意味がぶれます
- 1 つの要件が同時に複数の不具合を抱えられます（`status` は 1 つしか持てません）
- WBS と進捗レポートが不具合のたびに巻き戻ります

**今の健全性は「未修正の不具合があるか」で表します。** これは `defect_of` の逆引きで
導出できるので保存しません。要件タブ（`/client-export`）と `/status-report` が出します。

**例外が 1 つあります。** 受入基準が**最初から満たされていなかった**と判明した場合は、
不具合ではなく要件を `in-progress` に戻します。これは**完了申告の訂正**です。

## `defect_of` — どの約束に違反しているか

要件側には逆参照を書きません。**リンクは片方向です。**

逆参照を持たせると、不具合が出るたびに要件ファイルが書き換わり、`updated` が動き、
要件の差分に不具合の話が混ざります。**要件を汚さないことが目的なので、片方向でなければなりません。**

## 作業 ID

**`BUG-XXXX` がそのまま作業 ID です。** GitHub Issue は作りません。

| | |
|---|---|
| 起票 | `/defect-intake` |
| 修正 | `/implement BUG-XXXX` |
| ブランチ | `fix/BUG-XXXX-slug` |
| PR | `[BUG-XXXX] 概要` / 本文に `Refs: BUG-XXXX` |

**1 つの PR が実装してよい作業項目は 1 件までです**（要件 1 件、または不具合 1 件）。
