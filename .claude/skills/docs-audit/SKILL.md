# ドキュメント監査

**時間が経つと溜まるものを回収する。**

起票（`/meeting-intake`・`/requirements-intake`）は今回の入力に出たものしか見ない。
採否・受入基準・依存関係はそこで確定するので、このスキルはそれを追いかけない。
**入力と無関係に溜まるものを人間の前に運ぶのが、ここの仕事である。**

| 回収するもの | なぜ起票では拾えないか |
|---|---|
| 決まっていない論点（`proposed` の ADR） | 起票の入力に出てこない。時間だけが経つ |
| 実装状態のズレ | マージ済み PR との照合は全件を見ないと分からない |
| 30 日以上動いていない要件 | 引き金が経過時間であり、入力がない |
| 参照切れ・矛盾・陳腐化・領域の劣化 | 同上 |

**定例を持たないチームでは、`proposed` の ADR を人間の前に運ぶ経路はここしかない**
（定例がある場合は `/meeting-agenda` も同じ役割を果たす）。**週 1 回を空けない。**

機械的に検出できるものはスクリプトに任せ、判断が要るものだけを人間に上げる。

## 1. 現状を集める

```!
echo "--- 機械チェック ---"
python3 scripts/docs-lint.py 2>&1 || true
echo "--- 論点（proposed の ADR）---"
grep -l "^status: proposed" docs/02-decisions/ADR-*.md 2>/dev/null | while read f; do
  echo "$f: $(grep -m1 '^title:' "$f")"
done || echo "なし"
echo "--- 未決参照 ---"
grep -rn "NEEDS-DECISION" docs/ || echo "なし"
echo "--- 要件の状態 ---"
grep -H "^priority:\|^status:\|^area:\|^title:\|^updated:" docs/01-requirements/REQ-*.md 2>/dev/null | sed 's|docs/01-requirements/||' || echo "なし"
echo "--- 不具合の状態 ---"
grep -H "^priority:\|^status:\|^area:\|^title:\|^defect_of:\|^updated:" docs/05-defects/BUG-*.md 2>/dev/null | sed 's|docs/05-defects/||' || echo "なし"
```

```bash
gh pr list --state all --limit 60 --json number,title,body,mergedAt,isDraft
```

**作業 ID は REQ-XXXX（要件）または BUG-XXXX（不具合）である。** PR との対応は、
PR 本文の `Refs:` とブランチ名（`feat/REQ-XXXX-*` / `fix/BUG-XXXX-*`）で辿る。
GitHub Issue は使わない。

## 2. 論点（`proposed` の ADR）をすべて回収する

`docs/02-decisions/` に残っている `proposed` の ADR を**全件**、
PR 本文の「判断していただきたいこと（論点）」に並べる。**古いものほど上に置く。**

各論点には「この論点が決まらないと何が止まるか」を添える。書けないなら、
その論点は本当に判断が必要なのかを疑う。

**選択肢のない論点は判断できない。**「どうしましょうか」のまま出さない。
選択肢と推奨が書かれていない `proposed` があれば、ここで補う。

## 3. 実装の状態を実態に合わせる

実装 PR が `done` を書き込むので、通常このズレは出ない。出ているのは取りこぼしなので、
次を突き合わせて直す。

| 実態 | あるべき status |
|---|---|
| `Refs: REQ-XXXX` を持つ PR がマージ済みで、受入基準がすべて `[x]` | `done` |
| `Refs: REQ-XXXX` を持つ open な PR がある | `in-progress` |
| 受入基準の一部だけ満たしてマージ済み（複数 PR に分けている） | `in-progress` |
| 着手したが止まっている | `on-hold`（理由を本文に書く） |
| それ以外 | `not-started` |

`done` にする際は、受入基準がすべて満たされているかを PR の内容で確認する。
満たされていない項目があれば `in-progress` のままにし、残作業を本文に書く。

長期間 `in-progress` のまま動いていない要件は、**放置された作業ブランチ**である可能性が高い。
対応する PR の有無を確認し、なければ `not-started` に戻して報告する。

## 4. 30 日以上動いていないものを洗う

`priority: undecided` のまま長期間放置されている要件は、次のいずれかである。

- 実は不要だった → `wont` を提案（`decision`: 「起票後◯日議論されず、優先度が低いと判断」）
- 忘れられている → PR 本文の先頭に置き、次回議題にする

**放置されたまま黙って残さない。** どちらかに倒す提案を必ず出す。

**ここで `undecided` を `must` に上げない。** 採否を上げるには根拠が要り、根拠は入力から来る
（`AGENTS.md`「採否の提案」）。**時間の経過は根拠ではない。**
新しい根拠が出たなら、それは新しい入力なので `/requirements-intake` の仕事である。

### 不具合の放置は要件より重い

`priority: must` かつ `status: not-started` の不具合は、**「直すと決めたのに手を付けていない」**
状態である。要件の `undecided` は判断待ちという正当な状態だが、**こちらに正当な状態は無い。**

30 日を目安に一覧へ出し、次のどちらかに倒す提案を必ず出す。

| 提案 | 併せて必要なもの |
|---|---|
| 着手する | なし（`/implement BUG-XXXX` に送る） |
| `future` / `wont` に下げる | `decision`、`decided_at` |

**下げる提案は「判断していただきたいこと（採否）」に出す。**
不具合を下げるのは「直さない」という新しい判断であり、顧客に説明が必要である。
**要件と向きが逆**（要件は上げるときに判断が要り、不具合は下げるときに要る）。

## 5. 機械では見つからない問題を探す

スクリプトが検出できないのは次の種類の劣化である。手で確認する。

**矛盾**
2 つの要件が互いに矛盾する内容を書いていないか。特に、**別々の機会に追加された要件どうし**を疑う。`source` の議事録 ID が異なる要件のペアを重点的に見る。

**`source` が空の要件（打ち合わせ由来でないもの）では、この手がかりが使えない。** その場合は `## 経緯` の出典と `updated` の日付で「別々の機会」を判定する。定例を持たないチームでは全要件の `source` が空になるので、**そちらが主な手がかりになる。**

**陳腐化**
`docs/00-charter/` の制約が、実際の技術選定と食い違っていないか。ADR で覆された制約が憲章に残っていないか。

**用語のゆれ**
同じ概念が複数の呼び方をされていないか。`docs/90-glossary.md` に登録されていない業務用語が本文に出ていないか。

**不具合の整合**
次の 3 つを見る。

- `defect_of` が空の不具合 → 何をもって「直った」とするかが決まらない。
  違反している受入基準を特定できないなら、それは不具合ではなく要件かもしれない
- `defect_of` が指す要件が `wont` になっている → その約束はもう無い。
  不具合として残す意味があるかを確認する
- **`status: done` の不具合で `## 原因` が空** → 同じ原因が次に出たときに辿れない。
  不具合を文書として残す理由の半分が失われている

**領域の劣化**
`docs/00-charter/areas.md` の語彙が実態に合っているか。次の 3 つを疑う。

- 半分以上の文書が 1 つの領域に集まっている → 粒度が粗い。分割を提案する
- `common` が多い → 本来は個別領域に割り当てられるものが逃げている可能性がある
- `unassigned` が滞留している → 起票の時点で領域を決められていない。語彙が実態に合っているかを疑う

スクリプトが出す `領域 'xxx' はどの文書からも使われていません` は、語彙が実態から
浮いている合図である。`retired` にするか、そこに入るべき文書がないかを確認する。

**語彙そのものが未定義（`common` と `unassigned` しかない）なら、この PR で作る。**
本来は初回の `/meeting-intake` または `/requirements-intake` が作るが、そこで材料が足りずに
見送られている場合がある。**溜まった要件の内容が最良の材料になる。**
顧客・チームが使っている言葉から 5〜15 個を提案する。**語彙がないと 1 件も `must` に上げられない。**

```bash
git log -1 --format="%ad %s" --date=short -- docs/01-requirements/
```

## 6. 依存関係と分割を見直す

起票は、入力に順序が明示されたものと、その回に作った要件どうしの依存しか書かない。
**全件を横断して依存を見るのはここである。**

- 先に `done` でなければ着手できない要件があるか（データモデル、認証基盤、外部連携の口）
- 循環していないか。**循環は必ず解く。** 解けないなら 1 要件に統合するか、切り直す
- 依存先が `wont` になっていないか。なっていれば依存を外すか、その要件自体を見直す

**分割するのは、実体が複数の要件だったときだけである。** 行数は理由にならない
（`AGENTS.md`「作業の単位」）。兆候は次の 3 つ。

- 顧客が別々に採否を判断したがっている（片方だけ `must`、片方は `future` にしたい）
- 受入基準が明らかに別々の関心事に分かれている
- 領域（`area`）が異なるものが 1 つの要件に混ざっている

分割するときは、元の要件を残さず**新しい ID に採番し直す**。写しを作らない。
受入基準は元の要件からそのまま引き継ぎ、**分割のついでに追加・変更しない。**
**迷ったら分割せず、1 つのままユーザーに相談する。**

## 7. WBS を確認する

```bash
python3 scripts/export-wbs.py
```

**WBS は `dist/wbs.md` に生成される投影である。** リポジトリにコミットしない。
生成された内容を読み、次を報告に使う。

- 着手可能な要件と、並行して着手できる組み合わせ
- 着手条件を満たさない要件と、何が足りないか
- 見積もり（`estimate`）が未入力の要件。**エージェントは工数を見積もらない**

依存の循環や、着手可能が 0 件という結果は、3〜6 節の見落としの合図である。**戻って直す。**

## 8. 整合性を再確認する

```bash
python3 scripts/docs-lint.py
```

次を潰す。

- `priority が must ですが受入基準がありません` → 受入基準を書くか、`undecided` に戻す
- `priority が {future|wont} ですが decision（理由）が空です` → 理由と判断日を書く
- `status が {in-progress|done} ですが priority が {undecided|wont} です` → 採否か実装状態のどちらかが誤り
- `判断済みですが area が unassigned です` → 領域を決めるか、`undecided` に戻す
- `[NEEDS-DECISION: ADR-XXXX] の参照先が存在しません` → ADR を `proposed` で起票する

## 9. PR を出す

**直してよいものと、提案に留めるものを分ける。**

| 種別 | 扱い |
|---|---|
| 誤字、リンク形式、`updated` の欠落、明らかなタイプミスの参照切れ | 直す |
| 実装状態（`status`）のズレ | 直す。**根拠を PR 本文に書く** |
| 採否（`priority`）の変更 | **提案として書き、PR 本文に必ず出す。** マージが承認になる |
| 内容の矛盾・陳腐化 | 直し方が一意でないので、**報告に留める。** 判断が要るなら ADR を `proposed` で起票する |

```bash
git switch -c docs/audit-YYYY-MM-DD
git add docs/
git commit -m "docs(audit): ドキュメント監査"
git push -u origin docs/audit-YYYY-MM-DD
```

PR 本文:

```markdown
## ドキュメント監査 YYYY-MM-DD

### 判断していただきたいこと（論点）
<!-- proposed の ADR を全件。古いものほど上 -->
- ADR-0012「承認は2段階か3段階か」— 選択肢を用意しました。REQ-0005 の着手が止まっています

### 判断していただきたいこと（採否）
| ID | 内容 | 提案 | 理由 |
|---|---|---|---|
| REQ-0004 | 帳票のPDF出力 | undecided → wont | 起票後 45 日議論されていないため。異論があればお知らせください |

### 自動で実態に合わせた項目
| ID | 変更 | 根拠 |
|---|---|---|
| REQ-0002 | status: in-progress → done | PR #34 マージ済み、受入基準 3 件すべて充足 |

### 依存関係の更新
| ID | depends_on | 根拠 |
|---|---|---|
| REQ-0007 | REQ-0005 | 取込先のスキーマ確定が前提のため |

### 報告のみ（直していません）
| 場所 | 問題 | 推奨対応 |
|---|---|---|
| REQ-0004 / REQ-0011 | 承認フローの段数が矛盾（2段 vs 3段） | ADR-0015 を proposed で起票しました |
| 00-charter/constraints.md | 「RDBは MySQL」とあるが ADR-0003 で PostgreSQL に変更済み | 憲章を ADR に合わせて更新してよいか |

### 着手できる要件（`python3 scripts/export-wbs.py` の結果より）
- REQ-0007, REQ-0008（並行可。領域が異なる）

### 着手条件を満たさない要件
| ID | 不足しているもの |
|---|---|
| REQ-0013 | depends_on の REQ-0009 が未完了 |

### 見積もりが必要な要件
- REQ-0008, REQ-0011

Refs: なし（ドキュメント監査）
```

`Refs:` に採否を変更した要件がある場合は、その ID を列挙する。
**ドキュメントのみの PR なので「要件 ID は 1 つだけ」の制約は適用されない。**

## 10. 報告して終わる

マージしない。ユーザーに PR の URL と、次を伝える。

- 判断していただきたいこと（論点・採否）の件数
- 報告のみに留めた項目
- マージ後に着手できる要件と、推奨する着手順序
