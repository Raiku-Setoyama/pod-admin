# ドキュメント監査

機械的に検出できるものはスクリプトに任せ、判断が要るものだけを人間に上げる。

## 1. 機械チェック

```!
python3 scripts/docs-lint.py 2>&1 || true
```

## 2. 機械では見つからない問題を探す

スクリプトが検出できないのは次の種類の劣化である。手で確認する。

**矛盾**
2 つの要件が互いに矛盾する内容を書いていないか。特に、別々の打ち合わせで追加された要件どうしを疑う。`source` の議事録 ID が異なる要件のペアを重点的に見る。

**陳腐化**
`docs/00-charter/` の制約が、実際の技術選定と食い違っていないか。ADR で覆された制約が憲章に残っていないか。

**用語のゆれ**
同じ概念が複数の呼び方をされていないか。`docs/90-glossary.md` に登録されていない業務用語が本文に出ていないか。

**放置**
`updated` が 60 日以上前で、かつ `priority: undecided`（判断待ち）または `status: in-progress` / `on-hold`
のまま止まっている文書。動いていないのか、更新を忘れているのかを判別する。

**領域の劣化**
`docs/00-charter/areas.md` の語彙が実態に合っているか。次の 3 つを疑う。

- 半分以上の文書が 1 つの領域に集まっている → 粒度が粗い。分割を提案する
- `common` が多い → 本来は個別領域に割り当てられるものが逃げている可能性がある
- `unassigned` が滞留している → 仕分けが回っていない。`/requirements-refine` に送る

スクリプトが出す `領域 'xxx' はどの文書からも使われていません` は、語彙が実態から
浮いている合図である。`retired` にするか、そこに入るべき文書がないかを確認する。

```bash
git log -1 --format="%ad %s" --date=short -- docs/01-requirements/
```

## 3. 報告する

**修正 PR を出す前に、まず所見を報告する。** 監査で機械的に直してよいのは次だけ。

- 誤字、リンク形式の統一、`updated` の欠落
- スクリプトが指摘した参照切れのうち、明らかにタイプミスであるもの

矛盾・陳腐化・放置は **内容の判断を伴う** ので、勝手に直さずに報告する。

```markdown
## ドキュメント監査 YYYY-MM-DD

### 自動修正した項目（PR にします）
- <件数>件の軽微な不整合

### 判断が必要な項目
| 場所 | 問題 | 推奨対応 |
|---|---|---|
| REQ-0004 / REQ-0011 | 承認フローの段数が矛盾（2段 vs 3段） | 次回打ち合わせで確認。アジェンダに追加しますか |
| 00-charter/constraints.md | 「RDBは MySQL」とあるが ADR-0003 で PostgreSQL に変更済み | 憲章を ADR に合わせて更新 |

### 放置されている文書
| ID | 状態 | 最終更新 | 状況 |
|---|---|---|---|
| REQ-0009 | undecided | 78日前 | 採否が決まっていない。次回議題にすべき |
```

判断が必要な項目のうち打ち合わせで決めるべきものは、ADR を `proposed` で起票し、
該当文書に `[NEEDS-DECISION: ADR-XXXX]` を追記してよいか確認する。追記すれば `/meeting-agenda` が自動で拾う。
