# 実装・修正

`$ARGUMENTS` で指定された **REQ-XXXX（要件）または BUG-XXXX（不具合）** に着手する。
**作業 ID はこの ID であり、GitHub Issue は使わない。**

## 0. 対象と種別を決める

**ID のプレフィックスが種別を決める。** 以降の手順はこれで分岐する。

| プレフィックス | 種別 | 正本 | やること |
|---|---|---|---|
| `REQ-` | 要件 | `docs/01-requirements/REQ-XXXX.md` | **決めた完了条件に向かって作る** |
| `BUG-` | 不具合 | `docs/05-defects/BUG-XXXX.md` | **壊れていることを先に固定してから直す** |

ID が渡されていない場合は、着手可能なものを両方列挙してユーザーに選んでもらう。

```!
echo "--- 着手可能な要件・不具合 ---"
python3 scripts/export-wbs.py --actionable
```

判定は `scripts/export-wbs.py` の `blockers()` が正本である
（`AGENTS.md`「着手可能かどうかは保存しない」）。**要件と不具合に同じ条件が効く。**
ここに出てこないものの理由は `python3 scripts/export-wbs.py --stdout` で確認できる。

```bash
# 着手中（その ID を参照する open な PR がある）ものを除外するために確認する
gh pr list --state open --json number,title,body,headRefName
```

**不具合を優先するかどうかは自動で決めない。** 要件と不具合は同じ実装キャパシティを
奪い合うので、順序はユーザーの判断である。列挙して選んでもらう。

## 1. 文脈を読み込む

対象の文書を読み、そこから次を **必ず** 読む。

### 要件（REQ）の場合

- `docs/00-charter/` の非機能要件と制約
- `depends_on` が指す要件（完了しているか、前提が変わっていないか）
- 関連する `docs/02-decisions/ADR-XXXX.md`
- **同じ `area` の既存文書**（下記）

**受入基準は `REQ-XXXX.md` の `## 受入基準` が正本である。** 他のどこにも写しを作らない。

### 不具合（BUG）の場合

- **`defect_of` が指す文書**（`REQ-XXXX` / `NFR` / `CONSTRAINTS`）。
  **あるべき姿の正本はこちらである。** 不具合の文書に写しは無い（`## 違反している受入基準` は引用）
- `docs/00-charter/` の非機能要件と制約
- **同じ `area` の既存の不具合**（同じ原因で他にも壊れていないか）
- 関連する `docs/02-decisions/ADR-XXXX.md`

**不具合の `## 受入基準` は「修正作業の完了条件」であって「あるべき姿」ではない。**
2 つを混同しない。あるべき姿は `defect_of` の先にある。

### 共通 — 同じ領域を読む

対象の `area` の値をそのまま埋めて実行する。

```bash
grep -rlE "^area:[[:space:]]*[\"']?(<対象の area>|common)\b" docs/01-requirements/ docs/02-decisions/ docs/05-defects/
```

同じ領域の文書には、対象に書かれていない前提が入っていることが多い。
命名・エラーの扱い・画面遷移などがそこで既に決まっている。**読まずに実装すると領域内で流儀がぶれる。**

## 2. 着手前に確認する

次のいずれかに当てはまるなら、**実装せずに止まる**。

### 共通

- `priority` が `must` / `future` ではない（不具合なら「直さない」と決まっているもの）
- `status` が `not-started` でも `in-progress` でもない
- `depends_on` が `done` になっていない
- `[NEEDS-DECISION]` が残っている
- 憲章の制約（技術・非機能）と矛盾する
- 文書に書かれていない設計判断が必要になる

### 要件（REQ）だけ

- 受入基準が曖昧で、複数の解釈が成り立つ

### 不具合（BUG）だけ

- **`## 再現手順` のとおりにやっても再現しない。**
  **推測で直さない。** 再現しないものを「直した」と宣言する PR は検証できない。
  出口は次の 2 つ。
  - 手順が不足している → 報告者に確認する。分かったことを `## 再現手順` に追記する PR を先に出す
  - 手順は正しいが再現しない → `priority: wont` と `decision: "再現せず（<試した条件>）"` を
    **提案**する PR を出して止まる。**勝手に確定させない**
- **`defect_of` が空で、本文にも違反している約束が書かれていない。**
  何が「直った」状態なのかが決まらない。`/defect-intake` に差し戻す

止まったときの出口は 2 つ。**どちらもリポジトリの中に残す。** チャットだけで完結させない。

**(a) その場でユーザーに聞けば済む場合** — 次の形式で提示し、回答を得てから着手する。

```markdown
**論点**: <一行>
**選択肢 A**: <案と、それを選んだ場合の帰結>
**選択肢 B**: <案と、それを選んだ場合の帰結>
**推奨**: <どちらか。理由を一行で>
```

回答を得たら、その内容を対象の文書に反映する PR を先に出す。

**(b) 顧客・PM の判断が要る場合** — `_templates/adr.md` から `docs/02-decisions/ADR-XXXX.md` を
`status: proposed` で起票し、**選択肢と弊社推奨を用意する**。`area` は対象から引き継ぐ。
対象の文書に `[NEEDS-DECISION: ADR-XXXX]` を置く。
これを `docs/` の PR として出して止まる。

起票した論点は、**次のどちらかの経路で必ず回収される。**

- 定例の打ち合わせがある → `/meeting-agenda` が自動で次回議題に載せる
- **定例を持たない** → **`/docs-audit` が `proposed` の ADR を
  PR の「判断していただきたいこと（論点）」に出す。** 打ち合わせは要らない

**止まったことをユーザーに報告するときは、どちらの経路で回収されるかを併せて伝える。**
「止まりました」だけで終えると、判断待ちが誰にも拾われないまま放置される。

推測で埋めて進めない。判断は人間の仕事である。

## 3. PR の分け方を決める（要件のみ）

**不具合はこの節を飛ばす。1 不具合 = 1 PR である。**
修正が大きくなるなら、それは複数の不具合が 1 件に混ざっている合図なので、
分けた不具合を起票してから着手する。

**要件は 1 要件 = 1 実装 PR が原則である。行数の上限はない。**

実装の都合で分けたほうがよいときだけ分ける。例:

- スキーマ変更・マイグレーションを先に入れ、確認してからロジックを載せたい
- 依存パッケージの追加や大量の機械的置換を、レビュー対象から切り離したい
- 中間状態がそれ自体で動作し、レビュー可能な形になっている

**「行数が多いから」は分割の理由にならない。**
意味のある単位で切られた 1 本の PR は、要件を半分ずつ実装した 2 本より読みやすい。
**中間状態が壊れる分割はしない。** main が動かない状態を経由するくらいなら 1 本で出す。

分けると決めたら、`REQ-XXXX.md` の `## 実装メモ` に計画を書く。

```markdown
## 実装メモ

スキーマ変更を先に確認したいので 2 PR に分ける。
1. テーブル追加とマイグレーション（受入基準 1）
2. API・画面・E2E（受入基準 2, 3, 4）
```

**この判断に人間の承認は要らない。** 実装の都合はエージェントが決めてよい。
ただし**要件そのものを分割するのは別の話**であり、実体が複数の要件だったときだけ行う。
分割は起票の時点で済んでいるのが原則で、後から気づいたものは `/docs-audit` が提案する。

**1 つの PR が 2 つ以上の作業項目を実装してはならない。** CI が機械的に拒否する。

## 4. ブランチを切る

| 種別 | 形式 |
|---|---|
| 要件 | `feat/REQ-XXXX-short-slug` |
| 不具合 | `fix/BUG-XXXX-short-slug` |

```bash
git switch -c <上記の形式>
```

要件を複数 PR に分ける場合も、ID は同じままにする（`feat/REQ-XXXX-schema`, `feat/REQ-XXXX-api` など）。

## 5. 実装する

**ここが要件と不具合でいちばん違う。順序が逆である。**

### 要件（REQ）— 決めた完了条件に向かって作る

1. 受入基準を読み、各項目に対応するテストを書く
2. 実装する
3. テストが通ることを確認する

テストが書けない受入基準は、基準の書き方が悪い。`REQ-XXXX.md` 側を直す PR を先に出す。

### 不具合（BUG）— 壊れていることを先に固定してから直す

1. **`## 再現手順` をテストにする。** まだ直していないので、このテストは**失敗する**
2. **失敗することを実際に確認する。** ここを飛ばさない。
   失敗しないテストは何も検知していない。「回帰テストを追加した」が嘘になる
3. **原因を特定する。** 症状を隠すのではなく原因を直す。
   特定できないまま「たぶんここ」で直さない
4. 直す
5. **1 のテストが通ることを確認する**
6. **同じ原因で他に壊れている箇所がないかを探す。**
   見つかったら**この PR では直さず**、別の不具合として起票する（下記）

**この順序には理由がある。** 先に直してからテストを書くと、
そのテストが本当に元の不具合を検知できるのかを確かめる機会が永久に失われる。

### 共通

- 既存のコード規約に従う。`AGENTS.md` のプロジェクト固有セクションを確認する。
- 実装中に発見した別の問題は、**直さずに起票する。スコープを広げない。**
  **PR 本文のメモだけで済ませない。** マージ後に誰も読み返さない。
  行き先は `AGENTS.md`「不具合か、仕様変更か」で決める。

  | 見つけたもの | 行き先 |
  |---|---|
  | 既存の受入基準に違反している | `docs/05-defects/` に `BUG-XXXX` を `priority: must` で起票 |
  | 違反していない（新しい要求） | `docs/01-requirements/` に `REQ-XXXX` を `priority: undecided` で起票 |
  | 判定がつかない | **要件に倒す**（`priority: undecided`）。PR 本文でその旨を書く |

  `area` は問題が見つかった場所の領域にする（対象の領域とは限らない）。

  **要件の採否をここで提案しない。** 起票時に採否を提案してよいのは根拠を入力から
  引用できるときだが（`AGENTS.md`「採否の提案」）、**エージェント自身の気づきは誰の依頼でもない。**
  **不具合は別である。** 根拠は違反している受入基準であり、それは既にマージ済みなので
  `priority: must` で起票してよい。エージェントの意見ではなく、文書に書かれた約束が根拠になる。

## 6. 品質検証（必須）

`/quality-gate` を実行する。静的チェック → `/simplify max` → 静的チェック再実行 → `--seal` の 4 ステップである。

**この手順を飛ばして push しようとすると、PreToolUse フックが拒否する。**

## 7. コミットとプッシュ

| 種別 | type | Refs |
|---|---|---|
| 要件 | `feat` | `Refs: REQ-XXXX` |
| 不具合 | `fix` | `Refs: BUG-XXXX` |

```bash
git add -A

Refs: <ID>"
git push -u origin <ブランチ名>
```

## 8. ドキュメントの状態を更新

同じ PR に含める。

### 共通

- 満たした受入基準を `[x]` にする
- **すべての受入基準を満たしたなら** 対象の文書の `status` を **`done`** にし、
  `updated` を今日にする。一部しか満たしていない場合（要件を複数 PR に分けている途中を含む）は
  `in-progress` にし、残作業を本文に書く。
  **未チェックの受入基準を残したまま `done` にすると docs-lint が落ちる。**
- 設計上の判断をした場合は ADR を起こす（`status: accepted`。論点ではなく決定なので `proposed` にしない）

### 要件（REQ）だけ

- 実装により要件の解釈が確定した場合は、本文を明確化する
  （合意内容を変えるのではなく、曖昧さを解消するだけ）

### 不具合（BUG）だけ

- **`## 原因` を埋める。** 空のまま `done` にしない。
  同じ原因が次に出たときに辿れることが、不具合を文書として残す理由の半分である
- 同じ原因で他に見つけたものがあれば `## スコープ外` に ID を書く
- **`defect_of` が指す要件は触らない。`done` のまま戻さない。**
  `done` はマージ時点の履歴であり、今も満たしている保証ではない。
  今の健全性は「未修正の不具合があるか」で表され、それは導出される

  **例外**: 受入基準が**最初から満たされていなかった**（実装 PR の `done` 宣言が誤りだった）
  と判明した場合は、不具合ではなく**完了申告の訂正**である。この場合だけ要件を
  `in-progress` に戻し、該当の受入基準を `[ ]` に戻す。**判断は PR 本文に明記する**

ドキュメントを変更したら `/quality-gate` を **やり直す**（ファイル内容が変わったため封が無効になる）。

## 9. PR を作成する

`.github/pull_request_template.md` の項目をすべて埋める。特に:

- `Refs: <ID>` — **これが唯一のトレーサビリティ記載である。** CI が必須で検証する。
  **ID は 1 つだけ書く。** 2 つ以上書くと CI が落ちる
- 品質検証セクション（`/quality-gate` が指示する形式）
- レビュアーに判断してほしい点を「レビュー観点」に具体的に書く
- 要件を複数 PR に分けている場合は、何本目でありこの PR がどの受入基準を満たすかを書く
- **不具合の場合は「原因」と「同じ原因で他に壊れていないかを確認した結果」を書く。**
  レビュアーが見るのは修正の正しさより、**原因の特定が正しいか**である

```bash
gh pr create --draft --title "[<ID>] 概要" --body-file /tmp/pr-body.md
```

Draft で作成する。CI が通ってから Ready にする。

## 10. 報告して終わる

**PR をマージしない。** `gh pr merge` は権限設定で拒否される。

ユーザーには次を伝えて終了する。

- PR の URL
- レビューで判断してほしい点（あれば）
- 要件を複数 PR に分けた場合は、残りの本数と次に出す内容
- 実装中に起票した要件・不具合・ADR（あれば）
- **不具合の場合**: 原因と、同じ原因で他に影響がないかを確認した結果
