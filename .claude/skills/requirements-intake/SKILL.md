# 要件の起票（打ち合わせによらない）

**このスキルは `/meeting-intake` から議事録の作成を取り除いたものである。**
起票のルールは同じで、入力が打ち合わせではないという一点だけが違う。

打ち合わせを持たないチームでは、**要件が生まれる入口はここしかない。**
Slack で流れた「これ欲しいね」を起票しなければ、その話は存在しなかったことになる。

| 使い分け | 入口 |
|---|---|
| 文字起こしのある打ち合わせ | `/meeting-intake`（議事録も作る） |
| **それ以外のすべて** | **このスキル** |

## 1. 入力を受け取る

`$ARGUMENTS` に内容そのものかファイルパスが渡される。渡されていなければユーザーに聞く。

入力になるもの: Slack のスレッド、チャットのログ、口頭で受けた依頼のメモ、箇条書き、メール、
他システムのチケットの断片。**形式は問わない。**

**原文をリポジトリに取り込まない。** `docs/03-meetings/raw/` は打ち合わせの文字起こしの置き場であり、
Slack のスレッドを置く場所ではない。**出典は要件の `## 経緯` に一行で書く**（次節）。

不明な点は**推測で埋めない。** 起票に足りない情報があれば、その要件の本文に「未確認」と書く。

## 2. 領域の語彙を確認する

```!
sed -n '/^## 領域一覧/,/^## /p' docs/00-charter/areas.md 2>/dev/null | grep '^|' || echo "areas.md なし"
```

### `common` と `unassigned` しかない場合（初回のみ）

**この回の入力から領域のたたき台を作り、同じ PR に含める。** 後回しにしない。

領域が `unassigned` のままだと `priority` を `must` に上げる時点で docs-lint が落ちる。
つまり**語彙を作らないと 1 件も実装に進めない。** 打ち合わせを持たないチームでは、
`/meeting-intake` が語彙を作る機会が来ないので、**ここが唯一の初期化の入口になる。**

- 顧客・チームが業務を区切るときに使った言葉をそのまま採る。開発側の用語に翻訳しない
- 5〜15 個に収める。**今見えている範囲だけ**を書く。全体を先回りして埋めない
- 迷ったものは領域にせず、その要件を `unassigned` にして PR 本文で確認する
- `docs/00-charter/areas.md` の「領域一覧」表に追記し、PR 本文の「領域の追加提案」節で
  **なぜその区切りにしたか**を説明する。確定するのはマージの瞬間である

入力が少なくて語彙を作る材料が足りないなら、**作らずに `unassigned` で起票してよい。**
材料が溜まってから `/docs-audit` が提案する。**根拠のない語彙を先に作るほうが害が大きい。**

## 3. 起票する

**入力に出てきた話は、決定・未決を問わず、すべて残す。** 行き先は 3 つしかない。

| 出た話 | 行き先 |
|---|---|
| 「〜したい」「〜できると嬉しい」 | 要件 `docs/01-requirements/` |
| 誰も要求していないが検討価値のある案 | 要件 |
| このままだと困ること（作業になるもの） | 要件 |
| **決める必要がある論点** | **ADR** `docs/02-decisions/`（`status: proposed`） |
| **すでに作ったものが壊れている** | **不具合** `docs/05-defects/`（`priority: must`） |

### 不具合か、仕様変更か

「これだと困る」の中には、**すでにした約束が果たされていない**ものが混じる。それは要件ではない。

> **既存の受入基準（憲章の `NFR` / `CONSTRAINTS` を含む）に違反しているか。**
>
> - **違反している → 不具合。** `/defect-intake` に渡すか、このスキルで `BUG-XXXX` を起票する
> - **違反していない → 要件**
> - **判定がつかない → 要件に倒す。** PR 本文に「不具合の可能性がある」と書く

**判定の正本は `AGENTS.md`「不具合か、仕様変更か」である。**
不具合として起票するときは違反している受入基準を引用し、`defect_of` にその ID を入れる。
**引用できないなら不具合ではない。**

**不具合の `priority` は `must` から始まる。** 次節の「根拠を引用できるときだけ提案する」は
不具合にも同じく効くが、**引用するものが違う。** 要件は依頼者の発言を引用し、
不具合は**違反している受入基準**を引用する。約束は既にマージ済みなので、根拠は常に存在する。
`future` / `wont`（＝直さない）に下げるときだけ、新しい判断として `decision` / `decided_at` が要る。

不具合が主題の入力（「バグが出た」「動かない」）は **`/defect-intake` のほうが適している。**
再現確認の工程があり、必要なフィールドを取りこぼさない。

`status` は `not-started` から動かさない。実装はまだ始まっていない。

### 採否（`priority`）を提案する

**根拠を入力から一行で引用できるものは、その値で起票する。** 棚卸しを待たない。
確定するのはマージの瞬間であり、**エージェントが書くのは提案である。**

| 提案する値 | 入力にこれがあるとき | 併せて必ず書くもの |
|---|---|---|
| `must` | 依頼者が「やる」と言っている | **受入基準**、確定した `area` |
| `future` | 「やるが今回ではない」と読める | `decision`、`decided_at`、確定した `area` |
| `wont` | 「やらない」と読める | `decision`、`decided_at`、確定した `area` |
| `undecided` | 上のどれも言えない | なし |

**引用できないものを推測で埋めない。迷ったら `undecided`。**
チャットの流れで「いいね」と返された程度のものは合意ではない。
**根拠は PR 本文に入力からそのまま引用する。**要約すると、後から検証できなくなる。

**受入基準が書けないなら `must` にしない。**
「やると決めるなら、何をもって完了とするかも決める」が統合モデルの前提である。
合意はあるが完了条件が定まらないときは `undecided` に留め、何を確認したいかを PR 本文に書く。
**合意した事実は本文の `## 経緯` に残るので失われない。**

**`undecided` 以外を提案するなら `area` を確定させる。** `unassigned` のままだと docs-lint が
落ちる。決められないなら採否も決められる段階ではないので、`undecided` に留める。

### 依存関係（`depends_on`）を書く

**`must` / `future` を提案する要件には、着手の前提になる要件を書く。**
順序の制約だけを書き、親子関係は作らない。見る範囲は 3 つ。

- 入力に順序が明示されているもの
- この起票で作った要件どうしの依存
- **既存要件のうち、先に `done` でなければ着手できないもの**
  （データモデル、認証基盤、外部連携の口など）。`docs/01-requirements/` を検索して確認する

依存先が `wont` になっていないかも見る。なっていれば依存を外すか、その要件自体を見直す。

**見るのは、今回起票・変更した要件から既存要件への向きだけでよい。**
全件を横断した洗い直しは `/docs-audit` の担当である。

### 1 つの話が複数の要件なら分けて起票する

顧客が別々に採否を判断したがっている、受入基準が明らかに別々の関心事に分かれている、
領域（`area`）が違うものが混ざっている — このいずれかなら、**最初から別の ID で起票する。**

**「実装が大きいから」で分けない。** 要件の粒度は合意の単位で決まる。
実装の都合による分割は実装時に PR を分ければよい（`AGENTS.md`「作業の単位」）。
**迷ったら分けず、1 件のまま PR 本文で相談する。**

### `source` は空でよい

議事録が存在しないので `source: []` のままにする。**架空の MTG-ID を作らない。**
docs-lint は `source` が空であることを問題にしない（`scripts/docs-lint.py` は参照切れだけを見る）。

**出典は本文の `## 経緯` の「出典」列に一行で書く。** 例:

```markdown
| 日付 | 出典 | できごと |
|---|---|---|
| 2026-08-06 | Slack #dev のスレッド | 起票 |
```

リンクがあれば貼る。**「どこから来た話か」が辿れれば形式は問わない。**

### 論点は要件にしない

「承認は 2 段階か 3 段階か」は要件ではなく**決める必要がある論点**である。
`_templates/adr.md` から `docs/02-decisions/ADR-XXXX.md` を `status: proposed` で起票し、
**選択肢と推奨を書く。** 関係する要件の本文に `[NEEDS-DECISION: ADR-XXXX]` を置く。

決まったら同じファイルが `accepted` になる。**論点と決定を別々の文書に書き分けない。**

### 領域（area）を必ず入れる

**空欄は CI エラーになる。** 判断できないものは `unassigned` にする。**推測で埋めない。**
`unassigned` にしたものは PR 本文に列挙する。

**`common` を逃げ道に使わない。** `common` に入れてよいのは、複数の領域に**実際にまたがる**ものだけである。
どの領域か分からないだけなら `unassigned` にする。両者を混ぜると、後から区別できなくなる。

既存の語彙に当てはまらない話が出たときは、**`areas.md` への追加提案を同じ PR に含める。**
勝手に新しいキーを frontmatter に書かない（docs-lint が落ちる）。

## 4. 既存の要件への影響を見る

`docs/01-requirements/` を検索し、今回の話がどう当たるかを分類する。

| 種別 | 対応 |
|---|---|
| 新規 | 新しい `REQ-XXXX.md` を作成し、前節の基準で `priority` を決める |
| 変更 | 該当ファイルを編集し、`## 経緯` に行を追記して `updated` を今日にする |
| 取りやめ | `priority: wont` と `decision` / `decided_at` を書く。**ファイルは消さない** |
| 影響なし | 何もしない |

**既存要件の `priority` を変えるときも、根拠の引用が要る。** 基準は新規と同じである。
入力に書かれていない採否の変更を差分に混ぜない。

**採否を提案・変更したものは 1 件残らず PR 本文の「判断していただきたいこと」に出す。**
差分の中に埋もれさせない。

**「これは要件にするほどでもない」と判断して起票を省略しない。** 省略した話は存在しなかったことになる。

## 5. 整合性を確認する

```bash
python3 scripts/docs-lint.py
```

参照切れとステータス不正はここで潰す。警告として出る `[NEEDS-DECISION]` は残ってよい。

採否を提案したことで次が出たときは、**提案を取り下げて `undecided` に戻すのが正しい対処**である。
基準を満たせないものを無理に通さない。

- `priority が must ですが受入基準がありません`
- `priority が {future|wont} ですが decision（理由）が空です`
- `判断済みですが area が unassigned です`

マージ後に着手できるものを確認する。

```bash
python3 scripts/export-wbs.py --actionable
```

**`must` を提案したのにここに出てこない要件は、何かが足りていない。**
`python3 scripts/export-wbs.py --stdout` の「着手条件を満たさない要件」で理由を確認し、
埋められるなら埋め、埋められないなら PR 本文に書く。

## 6. PR を出す

```bash
git switch -c docs/intake-YYYY-MM-DD
git add docs/
git commit -m "docs(req): 要件の起票"
git push -u origin docs/intake-YYYY-MM-DD
```

同じ日に複数回動かす場合はブランチ名に `-2`, `-3` を付ける。

PR 本文:

```markdown
## 要件の起票

出典: <Slack #dev のスレッド / 2026-08-06 の口頭依頼 など。リンクがあれば貼る>

### 判断していただきたいこと（採否）
<!-- undecided 以外を提案したものをすべて並べる。根拠は入力からの引用にする -->
| ID | 内容 | 提案 | 根拠（入力からの引用） |
|---|---|---|---|
| REQ-0021 | 一括CSV取込をしたい | **must**（受入基準 3 件を書きました） | 「今期中に入れたいので進めてください」 |
| REQ-0022 | 多言語対応 | **future** | 「あると嬉しいけど今回じゃない」 |
| REQ-0009（既存） | 帳票のPDF出力 | **wont** | 「あれは既存システムを使い続けます」 |

**同意できないものがあればコメントしてください。`undecided` に戻して出し直します。**

### 記録が合っているかの確認（判断は不要）
| ID | 領域 | 内容 | priority |
|---|---|---|---|
| REQ-0023 | 未分類 | ここは自動化できそう | undecided（領域の確認だけお願いします） |

### 採否を提案しなかったもの
| ID | 理由 |
|---|---|
| REQ-0024 | 「やる」と伺っていますが完了条件が定まらないため `undecided` に留めました。<確認したいこと> |

### 未決のまま残した論点
- ADR-0012 <論点> — 選択肢を用意しました。<誰の判断待ちか>

### 領域の追加提案（areas.md）
<!-- 初回の語彙定義、または既存の語彙に当てはまらない話が出た場合に書く。なければ節ごと省く -->
| キー | 表示名 | 追加したい理由 |
|---|---|---|
| `notify` | 通知 | REQ-0023, REQ-0024 が既存のどの領域にも入らないため |

Refs: REQ-0021, REQ-0022, ADR-0012
```

**空の節は書かない。** 採否を 1 件も提案していないなら「判断していただきたいこと（採否）」ごと省く。
**レビューが軽くて済む PR は軽いままにする。**

`Refs:` には**起票・変更したすべての ID を列挙する。** これはドキュメントのみの PR なので、
実装 PR の「要件 ID は 1 つだけ」の制約は適用されない（CI もドキュメントのみの PR では数えない）。

## 7. 報告して終わる

マージしない。ユーザーに PR の URL と「判断していただきたいこと」の要約を伝える。

次を必ず伝える。

- 起票した要件・ADR の件数と、そのうち採否を提案したものの内訳
- **マージすれば着手可能になる要件**（`python3 scripts/export-wbs.py --actionable` の結果）。
  **この PR がマージされれば、そのまま `/implement REQ-XXXX` に進める。**
  別の PR を挟む必要はない
- `undecided` に留めたものと `proposed` の ADR は `/docs-audit` が回収すること

**WBS はコミットしていない。** `python3 scripts/export-wbs.py` でいつでも
最新の `dist/wbs.md` を生成できる（`AGENTS.md`「WBS は生成物である」）。
古くなることがないので、この PR で更新する必要もない。
