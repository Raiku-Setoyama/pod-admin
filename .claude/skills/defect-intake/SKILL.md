# 不具合の起票

**このスキルは `/requirements-intake` の不具合版ではない。**
起票の前に「そもそも不具合か」と「再現するか」を確かめる工程がある。

**不具合は完了した約束が満たされていない状態であり、新しい要求ではない。**
だから採否（やるかどうか）の判断は要らず、起票時から `priority: must` で始まる。
**この既定値が要件と逆であることが、種別を分ける理由の本体である。**

## 1. 報告を受け取る

`$ARGUMENTS` に内容そのものかファイルパスが渡される。渡されていなければユーザーに聞く。

入力になるもの: 顧客からの連絡、Slack の報告、監視のアラート、実装中の発見、テストの失敗。
**形式は問わない。**

次が揃っていなければ、**推測で埋めずに確認する。**

| 要るもの | 揃っていない場合 |
|---|---|
| 何が起きたか（**現象**。原因ではない） | 必須。無ければ起票できない |
| 再現手順 | ユーザーに聞く。分からなければ「未確認」と書く |
| 発生環境（本番 / ステージング / ローカル） | ユーザーに聞く |
| 発生頻度（毎回 / 断続的） | 分からなければ「未確認」と書く |

**原因を書かない。** 報告の時点で「〜が原因です」と書かれていても、それは仮説である。
`## 現象` には観測された事実だけを書き、原因は調査後に `/implement BUG-XXXX` が埋める。

## 2. 不具合かどうかを判定する

**これがこのスキルの中心である。**

```!
echo "--- 要件（違反していないか照合する対象）---"
grep -H "^id:\|^title:\|^area:\|^status:" docs/01-requirements/REQ-*.md 2>/dev/null | sed 's|docs/01-requirements/||' || echo "なし"
echo "--- 憲章（非機能要件・制約も約束である）---"
ls docs/00-charter/ 2>/dev/null || echo "なし"
echo "--- 既存の不具合（重複していないか）---"
grep -H "^id:\|^title:\|^status:" docs/05-defects/BUG-*.md 2>/dev/null | sed 's|docs/05-defects/||' || echo "なし"
```

判定は 1 つの問いで決まる。**正本は `AGENTS.md`「不具合か、仕様変更か」である。**

> **既存の受入基準に違反しているか。**

| 判定 | 行き先 | 起票時の値 |
|---|---|---|
| 違反している | **不具合** `docs/05-defects/BUG-XXXX.md` | `priority: must` |
| 違反していない（新しい要求） | **要件** `docs/01-requirements/REQ-XXXX.md` | `priority: undecided` |
| **判定がつかない** | **要件**（倒す先は要件） | `priority: undecided` |

「既存の受入基準」には憲章も含む。`docs/00-charter/nfr.md`（`NFR`）と
`constraints.md`（`CONSTRAINTS`）も**マージ済みの約束**である。
性能要件を割っているなら、特定の要件に紐づかなくても不具合である。

### 違反している基準を引用する

**引用できないなら、それは不具合ではない。** 該当の受入基準を `## 違反している受入基準` に
そのまま引用し、その文書の ID を `defect_of` に入れる。

```markdown
## 違反している受入基準

> REQ-0009 の受入基準 2「検索結果が 3 秒以内に表示されること」
```

**写しを作らない。** 引用は根拠を示すためのもので、正本は元の文書のまま動かさない。

### 迷ったら要件に倒す

**誤判定のコストは非対称である。** 不具合と判定すると採否の判断を経ずに修正まで進むが、
要件に倒せば人間の判断ゲートを必ず通る。

判定に幅があるとき（「そこまで速いとは書いていないが遅すぎる」など）は、
**要件として `priority: undecided` で起票し、PR 本文に「不具合の可能性がある」と明記する。**
人間が起票 PR で種別ごと差し戻せる。

**「これは仕様です」と勝手に結論づけて起票を省略しない。** 省略した報告は存在しなかったことになる。

## 3. 再現を確認する

**起票の前に再現を試す。** 再現しない不具合は直せず、直ったことも検証できない。

再現できた場合は、`## 再現手順` を**他人がなぞれる形**に整えて書く。
報告の言葉のままにしない（「検索が遅い」→「1. 顧客一覧を開く 2. 空文字で検索する 3. 10 秒以上かかる」）。

再現できなかった場合も**起票する。** ただし本文に明記する。

```markdown
## 再現手順

<!-- 起票時点では再現していない -->

報告された手順: 1. ... 2. ...
試した条件: <ブラウザ / 環境 / 回数>
→ 再現せず。再現条件の確認待ち
```

**再現しないことを理由に起票を見送らない。** 報告が消えるほうが害が大きい。
`/implement BUG-XXXX` が着手時にもう一度再現を試し、それでも再現しなければ
`priority: wont` + `decision: "再現せず"` を提案して止まる。

## 4. 起票する

`_templates/defect.md` からコピーして `docs/05-defects/BUG-XXXX.md` を作る。
ID は既存ファイルの最大値 + 1。

| フィールド | 値 |
|---|---|
| `priority` | **`must`**（既定。エージェントはここから動かさない） |
| `status` | `not-started` |
| `area` | **`defect_of` が指す要件から引き継ぐ。`unassigned` は使えない**（docs-lint が落ちる） |
| `defect_of` | 違反している文書の ID。`[REQ-0009]` / `[NFR]` / `[CONSTRAINTS]` |
| `requester` | 報告者 |
| `source` | 打ち合わせで報告されたなら議事録 ID。それ以外は空 |
| `milestone` | 分かっていれば。分からなければ空 |

### `priority: must` から動かさない

**要件と逆である。** 要件は `undecided` で起票して人間が上げるが、不具合は `must` で起票して
**人間が下げる**（`future` = 次期修正 / `wont` = 直さない）。

約束は元の受入基準として既に存在するので、エージェントは新しい約束をしていない。
**「直さない」ほうが新しい判断であり、そちらに `decision` と `decided_at` が要る。**

下げるべきだと考える場合も、**エージェントは確定させない。**
`must` のまま起票し、PR 本文の「判断していただきたいこと」に提案として書く。

### 受入基準は既定の 2 項目を入れる

```markdown
- [ ] 「再現手順」を実行しても再現しないこと
- [ ] 再発を検知する回帰テストが追加されていること
```

**これは省力化ではなく規律である。** `must` には受入基準が必須なので、
この 2 項目が入っていることで**回帰テストの追加が機械的に強制される。**
環境起因などで不要なら消してよいが、消したことが差分に残る。

### 重複を確認する

既存の不具合と同じものなら、新しく起票せず既存の `## 経緯` に報告を追記する。
別件だが同じ原因が疑われるなら、`related` で結ぶ。

## 5. 整合性を確認する

```bash
python3 scripts/docs-lint.py
```

不具合で落ちやすいのは次の 3 つ。

| エラー | 直し方 |
|---|---|
| `priority 'undecided' は不正です` | 不具合に `undecided` は無い。`must` にする |
| `判断済みですが area が unassigned です` | 起票時から領域が必須。`defect_of` の要件から引き継ぐ |
| `参照先 REQ-XXXX が存在しません` | `defect_of` の ID を確認する |

警告として出る `defect_of が空です` は、憲章由来などで特定できない場合のみ許容する。
その場合は `## 違反している受入基準` に根拠を書く。

## 6. PR を出す

```bash
git switch -c docs/defect-YYYY-MM-DD
git add docs/
git commit -m "docs(bug): 不具合の起票"
git push -u origin docs/defect-YYYY-MM-DD
```

同じ日に複数回動かす場合はブランチ名に `-2`, `-3` を付ける。

PR 本文:

```markdown
## 不具合の起票

出典: <顧客からの連絡 / 監視アラート / 実装中の発見 など>

### 不具合と判定した根拠
| ID | 違反している受入基準 | 再現 |
|---|---|---|
| BUG-0003 | REQ-0009 の受入基準 2「検索結果が 3 秒以内に表示されること」 | 確認済み |

### 起票した不具合（すべて priority: must。直す前提です）
| ID | 領域 | 現象 | 対象 | 影響 |
|---|---|---|---|---|
| BUG-0003 | 検索 | 検索結果の表示に 10 秒以上かかる | REQ-0009 | 全ユーザー。回避策なし |

### 判断していただきたいこと
<!-- 無ければ「なし」と書く。must のまま進めます -->
1. BUG-0004 — 影響が軽微なため `future`（次期修正）を提案します。ご判断ください

### 要件として起票したもの（不具合ではないと判定）
<!-- 該当が無ければ節ごと省く -->
| ID | 内容 | 判定の理由 |
|---|---|---|
| REQ-0056 | 検索結果を CSV で出したい | どの受入基準にも書かれていないため仕様変更 |

Refs: BUG-0003
```

`Refs:` には**起票したすべての ID を列挙する。** これはドキュメントのみの PR なので、
実装 PR の「ID は 1 つだけ」の制約は適用されない。

## 7. 報告して終わる

マージしない。ユーザーに PR の URL と次を伝える。

- 起票した不具合の件数と、そのうち再現を確認できたもの
- **要件として起票したものがあれば、その判定理由**（種別の判定は人間が覆せる）
- 判断していただきたいこと（`future` / `wont` を提案した場合）

**この PR がマージされれば、そのまま `/implement BUG-XXXX` に進める。**
起票時から `priority: must` なので、要件と違って採否が決まるのを待つ段階が無い。
