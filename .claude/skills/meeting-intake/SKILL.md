# 議事録の取り込み

打ち合わせを **イベント** として記録し、そこから要件という **状態** を更新する。この向きを逆にしない。

**文字起こしがない場合はこのスキルを使わない。** Slack のスレッド・口頭のメモ・箇条書きから
起票するなら `/requirements-intake` である（議事録を作らないだけで、起票のルールは同じ）。
**架空の議事録を作って辻褄を合わせない。**

## 1. 入力を特定する

`docs/03-meetings/raw/` から対象の文字起こしを探す。`$ARGUMENTS` に日付があればそれを使い、なければ最新のものを対象にして、対象ファイル名をユーザーに確認する。

**`raw/` のファイルは絶対に編集しない。** 原文である。

領域の語彙も先に確認する。**まだ定義されていなければ、この回で作る**（次節）。

```!
sed -n '/^## 領域一覧/,/^## /p' docs/00-charter/areas.md 2>/dev/null | grep '^|' || echo "areas.md なし"
```

### 領域が `common` と `unassigned` しかない場合（初回のみ）

**この回の文字起こしから領域のたたき台を作り、同じ PR に含める。** 後回しにしない。

領域を決めるのに条件が最も良いのはこの瞬間である。顧客が使った言葉が文字起こしに残っており、
まだ 1 件も文書がないので後から振り直すコストがゼロである。ここを飛ばすと、
**すべての要件が `common` に入る。** `common` は常に有効なキーなので、
「語彙に当てはまらない」という理由で後から追加提案が立ち上がることはない。

- 顧客が業務を区切るときに使った言葉をそのまま採る。開発側の用語に翻訳しない
- 5〜15 個に収める。1 回の打ち合わせで全体は見えないので、**話に出た範囲だけ**を書く
- 迷ったものは領域にせず、その要件を `unassigned` にして次回の議題にする
- `docs/00-charter/areas.md` の「領域一覧」表に追記し、PR 本文の「領域の追加提案」節で
  **なぜその区切りにしたか**を説明する。確定するのはマージの瞬間である

## 2. 構造化議事録を書く

`_templates/meeting-minutes.md` をひな形として `docs/03-meetings/MTG-YYYY-MM-DD.md` を新規作成する。同日に複数ある場合は `-a`, `-b` を付ける。

抽出のルール:

- **決定事項** — 明確に合意された内容だけ。「〜という方向で」「たぶん〜」は決定事項ではなく論点に入れる。
- **論点（未決）** — 議論されたが結論が出なかったもの。誰の判断待ちかを書く。
- **宿題** — 誰が・何を・いつまでに。担当が曖昧なものは「担当未定」と明記する。
- **要件への影響** — 後続の作業に直結する最重要セクション。次節参照。

**文字起こしに書かれていないことを補わない。** 前後関係から推測したことは `（推測）` を付ける。

## 3. 出た話をすべて起票する（最重要）

**打ち合わせで出た話は、決定・未決を問わず、すべて `docs/01-requirements/` に残す。**
行き先は 2 つしかない。

| 出た話 | 行き先 |
|---|---|
| 顧客の「〜したい」 | 要件 |
| 誰も要求していないが検討価値のある案 | 要件 |
| このままだと困ること（作業になるもの） | 要件 |
| **決める必要がある論点** | **ADR**（`status: proposed`） |

`status` は `not-started` から動かさない。実装はまだ始まっていない。

### 採否（`priority`）を提案する

**根拠を文字起こしから一行で引用できるものは、その値で起票する。** 棚卸しを待たない。
確定するのはマージの瞬間であり、**エージェントが書くのは提案である。**

| 提案する値 | 文字起こしにこれがあるとき | 併せて必ず書くもの |
|---|---|---|
| `must` | 顧客が「やる」と明確に言っている | **受入基準**、確定した `area` |
| `future` | 「やるが今回ではない」と読める | `decision`、`decided_at`、確定した `area` |
| `wont` | 「やらない」と読める | `decision`、`decided_at`、確定した `area` |
| `undecided` | 上のどれも言えない | なし |

**議事録の「決定事項」の判定基準をそのまま使う。**「〜という方向で」「たぶん〜」は
決定事項ではないので、採否の根拠にもならない。**その 2 つは常に一致する。**

**引用できないものを推測で埋めない。迷ったら `undecided`。**
**根拠は PR 本文に文字起こしからそのまま引用する。**要約すると、後から検証できなくなる。

**受入基準が書けないなら `must` にしない。**
「やると決めるなら、何をもって完了とするかも決める」が統合モデルの前提である。
合意はあるが完了条件が定まらないときは `undecided` に留め、何を確認したいかを PR 本文に書く。
**合意した事実は議事録の「決定事項」に残るので失われない。**

**`undecided` 以外を提案するなら `area` を確定させる。** `unassigned` のままだと docs-lint が
落ちる。決められないなら採否も決められる段階ではないので、`undecided` に留めて次回の議題にする。

### 依存関係（`depends_on`）を書く

**`must` / `future` を提案する要件には、着手の前提になる要件を書く。**
順序の制約だけを書き、親子関係は作らない。見る範囲は 3 つ。

- 打ち合わせで順序が明示されたもの
- この回に作った要件どうしの依存
- **既存要件のうち、先に `done` でなければ着手できないもの**
  （データモデル、認証基盤、外部連携の口など）。`docs/01-requirements/` を検索して確認する

依存先が `wont` になっていないかも見る。なっていれば依存を外すか、その要件自体を見直す。

**見るのは、今回起票・変更した要件から既存要件への向きだけでよい。**
全件を横断した洗い直しは `/docs-audit` の担当である。

### 1 つの話が複数の要件なら分けて起票する

顧客が別々に採否を判断したがっている、受入基準が明らかに別々の関心事に分かれている、
領域（`area`）が違うものが混ざっている — このいずれかなら、**最初から別の ID で起票する。**

**「実装が大きいから」で分けない。** 要件の粒度は顧客との合意の単位で決まる。
実装の都合による分割は実装時に PR を分ければよい（`AGENTS.md`「作業の単位」）。
**迷ったら分けず、1 件のまま PR 本文で相談する。**

### 論点は要件にしない

「承認は 2 段階か 3 段階か」は要件ではなく**決める必要がある論点**である。
`_templates/adr.md` から `docs/02-decisions/ADR-XXXX.md` を `status: proposed` で起票し、
**選択肢と弊社推奨を書く。** 関係する要件の本文に `[NEEDS-DECISION: ADR-XXXX]` を置く。

決まったら同じファイルが `accepted` になる。**論点と決定を別々の文書に書き分けない。**

### 領域（area）を必ず入れる

語彙は `docs/00-charter/areas.md` にある。**空欄は CI エラーになる。**

判断できないものは `unassigned` にする。**推測で埋めない。**
`unassigned` にしたものは PR 本文に列挙し、どの領域か打ち合わせで確認する旨を書く。

既存の語彙に当てはまらない話が出たときは、**`areas.md` に領域を追加する提案を同じ PR に含める。**
勝手に新しいキーを frontmatter に書かない（docs-lint が落ちる）。追加を提案した理由を PR 本文に書く。

**`common` を逃げ道に使わない。** `common` は常に有効なキーなので、判断を省いても機械的には通ってしまう。
`common` に入れてよいのは、複数の領域に**実際にまたがる**ものだけである。
どの領域か分からないだけなら `unassigned` にする。両者を混ぜると、後から区別できなくなる。

既存の要件に該当するものがあれば、新規作成せず既存を更新して `source` に今回の議事録 ID を追記する。

**「これは要件にするほどでもない」と判断して起票を省略しない。** 省略した話は存在しなかったことになる。

## 4. 既存の要件への影響を洗い出す

既存の `docs/01-requirements/` を検索し、今回の話がどう当たるかを次の 5 種に分類する。

| 種別 | 意味 | 対応 |
|---|---|---|
| 新規 | 既存要件に該当なし | 新しい `REQ-XXXX.md` を作成し、前節の基準で `priority` を決める |
| 変更 | 既存要件の内容が変わる | 該当ファイルを編集。変更前の内容は失われるが Git 履歴に残る |
| 取りやめ | 既存要件が不要になった | `priority: wont` と `decision` / `decided_at` を書く。**ファイルは消さない** |
| **不具合** | **すでに作ったものが約束どおり動いていない** | `docs/05-defects/BUG-XXXX.md` を `priority: must` で作成（下記） |
| 影響なし | 実装や運用の話のみ | 議事録に残すだけ |

### 不具合か、仕様変更か

**打ち合わせでは「先週入れたあれ、使えない」という形で不具合が出る。** それは要件ではない。

> **既存の受入基準（憲章の `NFR` / `CONSTRAINTS` を含む）に違反しているか。**
>
> - **違反している → 不具合**（`docs/05-defects/`、`priority: must`）
> - **違反していない → 要件**（`priority: undecided`）。新しい約束の話である
> - **判定がつかない → 要件に倒す。** PR 本文に「不具合の可能性がある」と書く

**判定の正本は `AGENTS.md`「不具合か、仕様変更か」である。**
不具合として起票するときは違反している受入基準を引用し、`defect_of` にその ID を入れる。
**引用できないなら不具合ではない。** `area` は `defect_of` の要件から引き継ぐ。

**この判定は打ち合わせの場で結論づけない。** 瑕疵か仕様変更かは金額に直結するので、
議事録には**顧客が何と言ったか**を書き、判定はこちらの見解として PR 本文に出す。
確定するのはマージの瞬間である。

議事録の「要件への影響」セクションに、この分類を表で書く。

**既存要件の `priority` を変えるときも、根拠の引用が要る。** 基準は新規と同じである。
打ち合わせで出ていない採否の変更を差分に混ぜない。

**採否を提案・変更したものは 1 件残らず PR 本文の「判断していただきたいこと」に出す。**
差分の中に埋もれさせない。マージがその承認になる。

## 5. 差分を適用する

- **新規作成する要件の `status` は必ず `not-started`。** `priority` は前節の基準で決める。
  値を書くのは提案であり、**確定するのは PR がマージされた瞬間である。**
- 新しく作る要件・ADR の `area` は、話の出どころの領域にする。
  複数領域にまたがるものは `common`、分からないものは `unassigned`。
  **`undecided` 以外を提案するなら `unassigned` は残せない。**
- 変更した要件の `source` に今回の議事録 ID を **追記** する（上書きしない）。
- 本文の `## 経緯` に今回の行を追記する。
- `updated` を今日の日付にする。
- 決定できなかった論点は ADR を `proposed` で起票し、関係する要件の本文に
  `[NEEDS-DECISION: ADR-XXXX]` を書く。ID のない `[NEEDS-DECISION]` は CI エラーになる。
- 設計方針が**決まった**場合は ADR を `status: accepted` で起こす（論点ではないので `proposed` にしない）。
- **受入基準を書くのは `must` を提案するときだけ。** `undecided` の間は空でよい。
  「やると決めるなら、何をもって完了とするかも決める」の裏返しで、
  **書けないなら `must` を提案しない。**

## 6. 整合性を確認する

```bash
python3 scripts/docs-lint.py
```

参照切れとステータス不正はここで潰す。警告として出る `[NEEDS-DECISION]` は残ってよい。

採否を提案したことで次が出たときは、**提案を取り下げて `undecided` に戻すのが正しい対処**である。
基準を満たせないものを無理に通さない。

- `priority が must ですが受入基準がありません`
- `priority が {future|wont} ですが decision（理由）が空です`
- `判断済みですが area が unassigned です`

マージ後に着手できるものを確認する。

```bash
python3 scripts/export-wbs.py --actionable
```

**`must` を提案したのにここに出てこない要件は、何かが足りていない。**
`python3 scripts/export-wbs.py --stdout` の「着手条件を満たさない要件」で理由を確認し、
埋められるなら埋め、埋められないなら PR 本文に書く。

## 7. PR を出す

```bash
git switch -c docs/mtg-YYYY-MM-DD
git add docs/
git commit -m "docs(meeting): MTG-YYYY-MM-DD の議事録と要件反映

Refs: MTG-YYYY-MM-DD"
git push -u origin docs/mtg-YYYY-MM-DD
```

PR 本文は次の形式にする。**レビュアーが差分を見る前に、何を判断すればよいかが分かること**が目的である。

```markdown
## MTG-YYYY-MM-DD の反映

### 判断していただきたいこと（採否）
<!-- undecided 以外を提案したものをすべて並べる。根拠は文字起こしからの引用にする -->
| ID | 内容 | 提案 | 根拠（打ち合わせでの発言） |
|---|---|---|---|
| REQ-0021 | 一括CSV取込をしたい | **must**（受入基準 3 件を書きました） | 「これは今期中にお願いします」 |
| REQ-0022 | 多言語対応 | **future** | 「必要になるけど今回じゃないですね」 |
| REQ-0009（既存） | 帳票のPDF出力 | **wont** | 「あれは既存システムを使い続けます」 |

**同意できないものがあればコメントしてください。`undecided` に戻して出し直します。**

### 記録が合っているかの確認（判断は不要）
| ID | 領域 | 内容 | priority |
|---|---|---|---|
| REQ-0003（変更） | 見積管理 | <何がどう変わったか> | must（変更なし） |
| REQ-0023 | 未分類 | ここは自動化できそう | undecided（領域の確認だけお願いします） |

### 採否を提案しなかったもの
| ID | 理由 |
|---|---|
| REQ-0024 | 合意はいただきましたが完了条件が定まらないため `undecided` に留めました。<確認したいこと> |

### 未決のまま残した論点
- ADR-0012 <論点> — <誰の判断待ちか>。選択肢を用意しました。次回アジェンダに載せます

### 領域の追加提案（areas.md）
<!-- 初回の語彙定義、または既存の語彙に当てはまらない話が出た場合に書く。なければ節ごと省く -->
<!-- 初回はこの表が実質的に「領域の定義そのもの」になるので、区切りの理由を丁寧に書く -->
| キー | 表示名 | 追加したい理由 |
|---|---|---|
| `notify` | 通知 | REQ-0023, REQ-0024 が既存のどの領域にも入らないため |

### 変更サマリー
| ID | 種別 | 内容 |
|---|---|---|
| REQ-0021 | 新規(must を提案) | ... |
| REQ-0023 | 新規(undecided) | ... |
| ADR-0012 | 新規(proposed) | ... |

### 影響なしと判断した決定事項
- <決定事項> — 運用手順の話であり要件に影響しないため
```

**空の節は書かない。** 採否を 1 件も提案していないなら「判断していただきたいこと（採否）」ごと省く。
**レビューが軽くて済む PR は軽いままにする。**

## 8. 報告して終わる

マージしない。ユーザーに PR の URL と「判断していただきたいこと」の要約を伝える。

次を必ず伝える。

- 起票した要件・ADR の件数と、そのうち採否を提案したものの内訳
- **マージすれば着手可能になる要件**（`python3 scripts/export-wbs.py --actionable` の結果）。
  **この PR がマージされれば、そのまま `/implement REQ-XXXX` に進める。**
  別の PR を挟む必要はない
- `undecided` に留めたものと `proposed` の ADR は `/meeting-agenda` が次回議題に自動で載せること
  （定例がない期間は `/docs-audit` が回収する）

**WBS はコミットしていない。** `python3 scripts/export-wbs.py` でいつでも
最新の `dist/wbs.md` を生成できる（`AGENTS.md`「WBS は生成物である」）。
古くなることがないので、この PR で更新する必要もない。
