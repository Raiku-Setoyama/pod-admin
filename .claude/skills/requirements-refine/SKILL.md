# 要件の棚卸し

`docs/01-requirements/` は**要求・要件・バックログを兼ねる 1 つの層**である。
区別は 2 つのフィールドだけ。

| 軸 | フィールド | 値 | 誰が決めるか |
|---|---|---|---|
| 採否 | `priority` | `undecided` / `must` / `future` / `wont` | **人間（PR マージ）** |
| 実装 | `status` | `not-started` / `in-progress` / `done` / `on-hold` | エージェント |

このスキルの目的は 2 つ。**判断待ちを人間が承認できる形に整えること**と、
**エージェントが次に着手できる要件を並べること**である。

## 1. 現状を集める

```!
echo "--- 要件の状態 ---"
grep -H "^priority:\|^status:\|^area:\|^title:\|^milestone:\|^decided_at:" docs/01-requirements/REQ-*.md 2>/dev/null | sed 's|docs/01-requirements/||' || echo "なし"
echo "--- 論点（proposed の ADR）---"
grep -H "^status: proposed" docs/02-decisions/ADR-*.md 2>/dev/null || echo "なし"
echo "--- 未決参照 ---"
grep -rn "NEEDS-DECISION" docs/ || echo "なし"
echo "--- 定義済みの領域 ---"
sed -n '/^## 領域一覧/,/^## /p' docs/00-charter/areas.md 2>/dev/null | grep '^|' || echo "なし"
```

```bash
gh pr list --state all --limit 60 --json number,title,body,mergedAt,isDraft
```

**作業 ID は REQ-XXXX である。** PR と要件の対応は、PR 本文の `Refs: REQ-XXXX` と
ブランチ名 `feat/REQ-XXXX-*` で辿る。GitHub Issue は使わない。

## 2. 採否を仕分ける

`priority: undecided` の要件を一件ずつ判定する。**判定はエージェントが提案し、確定は人間が行う。**

| 提案する値 | 条件 | 併せてやること |
|---|---|---|
| `must` | 今回のスコープでやることに顧客が同意済み | **受入基準を書く**（必須）。`area` を確定させる |
| `future` | やる価値はあるが今回のフェーズの範囲外 | `decision` に「なぜ今回やらないか」、`decided_at` を書く |
| `wont` | やらない | `decision` に「なぜやらないか」、`decided_at` を書く |
| `undecided` のまま | 判断材料が足りない | 不足している情報を本文に書き、次回議題にする |

### 判定の原則

- **`must` / `future` / `wont` を勝手に確定させない。** 提案として PR に出し、マージが顧客・PM の判断になる。
- **`decision` が書けない判定はしない。** 理由のない判断は必ず蒸し返される。
- **`must` を提案するなら受入基準を書く。** 空だと docs-lint が落ちる。
  「やると決めるなら、何をもって完了とするかも決める」が統合モデルの前提である。
- **`must` / `future` / `wont` を提案するなら `area` を確定させる。** `unassigned` のままだと docs-lint が落ちる。
  仕分けは領域を決める最後の機会である。決められないなら `undecided` に留め、議題にする。
  既存の語彙に入らないなら `areas.md` への追加を同じ PR で提案する。
- **語彙そのものが未定義（`common` と `unassigned` しかない）なら、この PR で作る。**
  本来は初回の `/meeting-intake` または `/requirements-intake` が作るが、そこで材料が足りずに
  見送られている場合がある。**溜まった要件の内容が最良の材料になる。**
  顧客・チームが使っている言葉から 5〜15 個を提案し、PR 本文の「領域の追加提案」節で
  区切りの理由を説明する。**語彙がないと 1 件も `must` に上げられない。**
- 重複していたら、片方を `wont` + `decision: "REQ-XXXX と重複"` にし、`related` で本体を指す。**内容は消さない。**
- **見積もりを書かない。** 規模感が必要なら「小/中/大」の粗い感覚を本文に書き、`estimate` は人間に委ねる。

### 論点は要件にしない

「承認は 2 段階か 3 段階か」のような**決める必要がある論点**は要件ではない。
`docs/02-decisions/` に ADR を `status: proposed` で起こし、**選択肢と弊社推奨を用意する。**
関係する要件の本文に `[NEEDS-DECISION: ADR-XXXX]` を置く。

「どうしましょうか」のまま議題に載せない。選択肢のない論点は判断できない。

### `proposed` の ADR をすべて回収する

**このスキルで新しく起こした論点だけでなく、`docs/02-decisions/` に残っている
`proposed` の ADR をすべて**、PR 本文の「判断していただきたいこと（論点）」に並べる。

**これが、定例を持たないチームにおける論点の回収経路である。**
打ち合わせがある案件では `/meeting-agenda` が同じ役割を果たすが、定例がなければ
**このスキルを回さない限り `proposed` は誰にも拾われない。** 古いものほど上に置く。

各論点には「この論点が決まらないと何が止まるか」を添える。書けないなら、
その論点は本当に判断が必要なのかを疑う。

## 3. 実装の状態を実態に合わせる

実装 PR が `done` を書き込むので、通常このズレは出ない。出ているのは取りこぼしなので、次を突き合わせて直す。

| 実態 | あるべき status |
|---|---|
| `Refs: REQ-XXXX` を持つ PR がマージ済みで、受入基準がすべて `[x]` | `done` |
| `Refs: REQ-XXXX` を持つ open な PR がある | `in-progress` |
| 受入基準の一部だけ満たしてマージ済み（複数 PR に分けている） | `in-progress` |
| 着手したが止まっている | `on-hold`（理由を本文に書く） |
| それ以外 | `not-started` |

`done` にする際は、受入基準がすべて満たされているかを PR の内容で確認する。
満たされていない項目があれば `in-progress` のままにし、残作業を本文に書く。

長期間 `in-progress` のまま動いていない要件は、**放置された作業ブランチ**である可能性が高い。
対応する PR の有無を確認し、なければ `not-started` に戻して報告する。

## 4. 着手可能なものを並べる

**着手可能フラグは保存しない。** 次の条件をその場で判定し、満たすものを一覧にする。

- `priority` が `must` または `future`
- `status` が `not-started`
- 受入基準が検証可能な形で書かれている（「使いやすいこと」は不可、「3 秒以内に応答すること」は可）
- `[NEEDS-DECISION]` が残っていない
- `area` が確定している
- `depends_on` がすべて `done`

条件を落とした要件は、何が足りないかを PR 本文に明記する。

## 5. 分割が必要かを判定する

**行数は分割の理由にならない。** 実装が大きいだけなら、実装時に PR を分ければよい
（`AGENTS.md`「作業の単位」）。ここで分割するのは、**実体が複数の要件だったとき**だけである。

分割すべき兆候:

- 顧客が別々に採否を判断したがっている（片方だけ `must`、片方は `future` にしたい）
- 受入基準が明らかに別々の関心事に分かれている
- 領域（`area`）が異なるものが 1 つの要件に混ざっている

分割するときは、元の要件を残さず**新しい ID に採番し直す**。写しを作らない。
順序の制約は `depends_on` に書く。親子関係は作らない。

受入基準は元の要件からそのまま引き継ぐ。**分割のついでに受入基準を追加・変更しない。**
変更が必要だと気づいたら、その旨を PR 本文の「判断していただきたいこと」に書く。

**迷ったら分割せず、1 つのままユーザーに相談する。** 過剰な分割はレビュー負荷を増やすだけになる。

## 6. 30 日以上動いていないものを洗う

`undecided` のまま長期間放置されている要件は、次のいずれかである。

- 実は不要だった → `wont` を提案（`decision`: 「起票後◯日議論されず、優先度が低いと判断」）
- 忘れられている → 次回アジェンダの先頭に載せる

**放置されたまま黙って残さない。** どちらかに倒す提案を必ず出す。

## 7. 整合性を確認する

```bash
python3 scripts/docs-lint.py
```

次を潰す。

- `priority が must ですが受入基準がありません` → 受入基準を書くか、`undecided` に戻す
- `priority が {future|wont} ですが decision（理由）が空です` → 理由と判断日を書く
- `status が {in-progress|done} ですが priority が {undecided|wont} です` → 採否か実装状態のどちらかが誤り
- `判断済みですが area が unassigned です` → 領域を決めるか、`undecided` に戻して議題にする
- `[NEEDS-DECISION: ADR-XXXX] の参照先が存在しません` → ADR を `proposed` で起票する
- `領域 'xxx' はどの文書からも使われていません` → 語彙が実態に合っていない。`areas.md` の見直しを提案する

## 8. WBS を更新する

`docs/04-wbs/wbs.md` を、`priority: must` / `future` かつ `status != done` の要件から再生成する。

- マイルストーン（`milestone`）ごとに要件をグルーピングし、表には領域（`area`）の列を出す
- 依存関係を明示し、並行実行できる要件を示す。
  **領域が異なる要件はファイル競合が起きにくいので、並行実行の候補になる**
- 見積もりは既存の記載を尊重する。**エージェントが勝手に工数を見積もらない。**
  未記入なら `TBD` にして、見積もりが必要な要件の一覧を PR 本文に書く

## 9. PR を出す

```bash
git switch -c docs/requirements-refine-YYYY-MM-DD
git add docs/
git commit -m "docs(req): 要件の棚卸しと WBS 更新"
git push -u origin docs/requirements-refine-YYYY-MM-DD
```

PR 本文:

```markdown
## 要件の棚卸し

### 判断していただきたいこと（採否）
| ID | 内容 | 提案 | 理由 |

| REQ-0007 | 一括CSV取込をしたい | undecided → must（受入基準 3 件を追加しました） | 前回打合せで方針合意済み |
| REQ-0009 | 多言語対応 | undecided → future | 今回スコープ外。第2フェーズ候補 |
| REQ-0004 | 帳票のPDF出力 | undecided → wont | 既存システムを継続利用する方針のため |

### 判断していただきたいこと（論点）
- ADR-0012「承認は2段階か3段階か」— 選択肢を用意しました。REQ-0005 の着手が止まっています

### 分割を提案する要件
| 元 | 分割後 | 理由 |
|---|---|---|
| REQ-0011 | REQ-0014, REQ-0015（depends_on: REQ-0014） | 見積管理と受注管理が 1 件に混ざっている |

### 自動で実態に合わせた項目
| ID | 変更 | 根拠 |
|---|---|---|
| REQ-0002 | status: in-progress → done | PR #34 マージ済み、受入基準3件すべて充足 |

### 着手可能になる要件（マージ後）
- REQ-0007, REQ-0008（並行実行可。領域が異なる）

### 着手条件を満たさなかった要件と理由
| ID | 不足しているもの |
|---|---|
| REQ-0013 | depends_on の REQ-0009 が未完了 |

### 30日以上動いていないもの
| ID | 経過 | 提案 |
|---|---|---|
| REQ-0004 | 45日 | wont を提案。異論があればお知らせください |

- REQ-0008, REQ-0011
```

マージしない。

マージされると着手可能な要件に取りかかれる。**次は `/implement-requirement REQ-XXXX`** である旨と、
依存関係から見た推奨着手順序を報告する。
